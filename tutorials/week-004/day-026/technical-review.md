# 第 26 天技术校对报告

## 【错误】
#### 1. 练习提示预告 matmul 的判决是"不参与"，实际判决是两行"○ 首登"
- **原文**：“想深一层：如果给图里再放一条”
- **依据**：`matmul` 在 `PURE_OPS` 白名单内（cse.py 第 42 行），`_key` 对 matmul 走保序分支返回合法键（不是 None），所以 `matmul(%a, %b)` 与 `matmul(%b, %a)` 键不同、各自首登。我用 `CsePass` 实测：判决日志打印两行"○ 首登 matmul %m1／%m2"（理由同为"键首次出现——登记进键表当代表"），没有任何一行"不参与"；"不参与"只留给键为 None 的语句（input／debug／mystery／output／坏常量），`_skip_reason` 里也不存在提到"顺序就是语义"的文案——那是 [5] 节 demo 打印的汇总行，不是判决日志。读者按此提示核对会得出"日志与教程不符"的错误结论。
- **置信度**：高。已在 Python 3.11.4 下运行 `CsePass` 于含两条换序 matmul 的图验证；判决日志逐行核对。

#### 2. 常见错误一的"现象"把错值出现的位置写反了
- **原文**：“现象：优化后大 Shape 的 matmul 图运行结果错乱”
- **依据**：按本教程自己的合并方向（后来的并入先来的），被错误合并时是 `%m2 = matmul(%b, %a)`（后出现者）并入 `%m1 = matmul(%a, %b)`，`output` 的第二个槽位（b·a 的位置）被改成读 `%m1`——即"b·a 的位置吐出了 a·b 的值"。我模拟"键对全部双目算子排序"的事故版实测：优化后输出为 `[[[19,22],[43,50]], [[19,22],[43,50]]]`，槽位 0（a·b 的位置）数值正确、槽位 1（b·a 的位置）才是错的。原文恰好说反。
- **置信度**：高。模拟代码按"later 并入 first"的教程约定执行，输出值与 [5] 节的 a·b=[[19,22],[43,50]]、b·a=[[23,34],[31,46]] 一致。

#### 3. "让级联的方向迎着扫描方向走"——级联传染方向与扫描方向是同向，不是"迎着"
- **原文**：“遍历策略都是”
- **依据**：按本节自己给出的方向：DCE 的级联"朝上传染"（消费者死了才暴露生产者的死，从语句列表后面往前面传），而 DCE 的扫描也是反向（从后往前）——两者同向；CSE 的级联"朝下传染"（生产者合并了才暴露消费者的重复，从前往后传），扫描也是正向——同样同向。两种 Pass 的共同设计模式是"让扫描顺着级联传染的方向走"（先访问级联的源头，后访问被传染者），"迎着"（逆向相对）描述的恰是相反的配置。按"迎着"建立心智模型的读者会把方向记反。
- **置信度**：中。"迎着"在口语里偶有"朝着"的松用法，但按最自然的读法（相对、顶着头），技术关系说反了；前一句"方向相反"指的是两种 Pass 彼此的扫描方向相反，容易连带误读。

#### 4. 图 3（images/03-example.svg）[6b] 面板的括注"（合并救活了它）"与本面板内容自相矛盾
- **原文**：“对比 [4]：交换律开着 4 次合并”
- **依据**：README 原文正确区分了两种情形（开着时 %m1 靠合并活下来、关掉时 %m1 死于无人使用），但 03-example.svg 右下 [6b] 面板写的是"3 次合并，%m2 幸存；%m1 无人使用反被 dce 收走（合并救活了它）"——该面板描述的正是交换律关掉的运行，此时 %m1 恰恰死于"没有合并"，括注紧贴"被 dce 收走"读起来指向 %m1，与相邻文字直接矛盾（若指向 %m2 也不成立：%m2 靠 output 直读存活，与合并无关）。括注源自真实输出的尾注"（合并救活了 %m1，对应 [1] 里两种顺序的幸存者之争）"，SVG 压缩时丢掉了限定语。本次审阅未改动该 SVG，仅报告。
- **置信度**：高。SVG 文本逐字核对（"反被 dce 收走（合并救活了它）"位于 [6b] 面板第二行）；[6b] 真实运行与 README 均确认关掉交换律时 %m1 被 dce 删除。

## 【存疑】
#### 1. "照真实 CSE 的做法（如 MLIR）合并后当场删除重复语句"——MLIR 确实在同一 Pass 内删除，但不是每次合并后"当场"删
- **原文**：“且照真实 CSE 的做法（如 MLIR）合并后当场”
- **依据**：查 MLIR 源码 mlir/lib/Transforms/CSE.cpp（llvm-project release/18.x，main 分支结构相同）：`CSEDriver::replaceUsesAndDelete` 只做 `replaceAllUsesWith` 并把重复 op 推入 `opsToErase`，真正的 `rewriter.eraseOp` 推迟到整趟 `simplify()` 遍历结束之后统一执行（注释明确写"Replace all uses, but do not remove the operation yet"）。结论层面成立——真实 CSE 不把清扫留给另一个 dce Pass（MLIR CSE 甚至顺带做 trivially-dead 的 DCE）；但"当场"（每次合并后立即 `remove_statement`）比 MLIR 的实际时序更绝对，BuggyCsePass 的逐次删除是为教学刻意加急的版本。另注：MLIR 对副作用算子根本不会进 CSE 键，教程已把"debug 进键表"单独标为"真正的 bug"，这点处理是妥当的。
- **置信度**：高（依据为 LLVM 官方仓库源码，已核对该文件的关键函数）；影响仅限措辞精度，不影响事故论证的结论。
