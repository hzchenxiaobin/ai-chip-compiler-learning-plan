## 【错误】

#### 1. “使用先于定义”把 Day 17 SSA 闸门保证的方向说反了
- **原文**：“**① 为什么反向**：我们的语句列表满足拓扑序——Day 17 的 SSA 闸门保证"使用先于定义"，所以**任何消费者都排在生产者后面**。从最后一条往前扫，消费者先受审；轮到生产者时，它那些死掉的消费者已经被判死并删除了。`%d1` 在 S4，它的使用者 `%d2` 在 S5——反向扫描先到 S5，`%d2` 判死删掉；再到 S4 时 `%d1` 已经没人用了，接着判死。**三层死链不需要回头，一趟能扫到底。**”
- **依据**：Day 17 的规则原文是“**定义先于使用**”——day-017/README.md（3.4 节代码注释、5.3 节输出、6 节定位与 8 节验收）多处写明 `check_ssa` 检查“单赋值”和“定义先于使用”，通过信息是“每个 SSA 值只有 1 个定义，且定义先于使用”。当天 `Graph.validate()` 的语义也相同：`defined[u] >= i` 时抛出“在定义之前被使用”——即“使用先于定义”是被闸门**禁止**的非法状态，而不是被**保证**的性质。能推出“任何消费者都排在生产者后面”（从而反向一趟成立）的性质恰恰是“定义先于使用”。本句的后半句和整节结论都正确，唯独引用的规则名正好写反。同一反置表述还出现在 code/dce.py 的模块 docstring、`Graph`／`DcePass` 的 docstring 以及 images/02-mechanism.svg（“Day 17 的 SSA 闸门保证”使用先于定义”“）中，属同一笔误的传播，修正时应一并处理（本报告不改文件）。
- **置信度**：高。day-017 README 原文与 day-025 自身 `validate()` 的报错方向均已在仓库核对。

## 【存疑】

#### 1. “Day 16 之前我们没这个保证”与本系列 Day 8/13 的既有契约冲突
- **原文**：“**④ 如果没有拓扑序**：反向一趟的前提是"消费者排在生产者后面"。如果语句可以乱序写（Day 16 之前我们没这个保证），一趟反向就不够了——标准做法是 mark-and-sweep（标记－清除）：从根集合（图输出＋副作用节点）出发，沿"使用者 → 生产者"逆向标记所有活值，再统一清扫没标到的纯算子。我们的线性 IR 有 SSA 闸门保证拓扑序，所以能省掉标记阶段直接一趟——**Day 16 的拓扑排序和 Day 17 的 SSA 在这里变现。**”
- **依据**：本系列在 Day 16 之前并非没有顺序保证：Day 8 给出了定理“只能引用已存在的值 ⇒ 创建序即拓扑序”（day-016 README 的前置准备原文援引）；Day 13 的 3.3 节明确立了“顺序契约：定义先于使用——模型侧的层列表必须按**拓扑序**排列”（并指出 ONNX 规范同样要求），且前端预扫描能区分乱序／拼错／自环三种报错。Day 16 补上的是**可变图**上的机器排序器与环检测（`rewire_input` 改图后仍能保证），Day 17 的 `check_ssa` 才把它变成线性 IR 级闸门。若把“保证”理解为“改图之后的机器强制检查”，原句勉强成立；按字面读则与 Day 8/13 的内容矛盾。更稳妥的表述是“Day 16/17 之前顺序只靠构造期保证和前端契约，改图之后没有闸门兜底”。
- **置信度**：中。day-008（经 day-016 前置援引）、day-013、day-016 原文均已核对；不确定点在作者对“保证”一词 intended 的粒度（构造期契约 vs 机器闸门）。

#### 2. 选做挑战第 4 条括注给出的“反向一趟省掉什么”参考答案与当天实现不符
- **原文**：“4. 顺手想清楚：mark-and-sweep 的成本是 O(语句数＋使用边数)，和反向一趟同量级——那反向一趟省掉的到底是什么？（标记阶段的整张活值表和一趟写集；在内存受限的编译器里这不是小事。）”
- **依据**：mark-and-sweep 的标记阶段只需“值 → 定义语句”的 def 表（O(值数)）＋每值一个标记位；而本天的 `DcePass` 自己进场就要建两张辅助表——`use_count`（O(值数)）和 `users`（**每条使用边存一个算子名**，O(使用边数)），辅助内存与标记法同量级、通常更大（users 表一般超过标记位集）。反向一趟真正省掉的是第二次整图遍历（sweep 并入同一趟）与标记阶段的工作栈，是时间上的常数因子，内存上并没有净节省；“一趟写集”所指不明——若指 sweep 阶段的删除写集，反向一趟同样要删语句、同样有写集。该括注作为练习参考答案，容易让初学者得出“反向一趟更省内存”的结论。
- **置信度**：中。对 `DcePass._use_tables` 与 mark-and-sweep 辅助结构的分析可直接从当天代码核验；不确定点是“一趟写集”的确切含义，若作者另有解释则以作者口径为准。

## 【建议】

#### 1. “判决日志里的 S6、S5、S4、S3”实际出现在改动日志里
- **原文**：“**⑤ S 标号为什么不用重算**：删除第 i 条语句只会移动它后面（下标更大）的语句——反向扫描里那些是**已经扫过**的，再也不会看；还没扫到的语句（下标更小）位置一个不动。所以判决日志里的 `S6`、`S5`、`S4`、`S3` 全是原始位置，人和日志能对上账。”
- **依据**：[4] 展示的判决日志（`print_decisions` 输出）每行只有“✓／✗、op、res、reason”四样，不含任何 S 标号；带 `S6`／`S5`／`S4`／`S3` 的是改动日志（`change_log`，demo 中紧随其后打印的“epoch 1：删除 S6（relu %d3）……”）。结论本身（删除只移动下标更大的已扫语句、删除记录按原始位置记账）正确，但指错了日志——读者在 [4] 的判决日志里找不到 S 标号。建议将“判决日志”改为“改动日志”。
- **置信度**：高。两份日志的实际字段已在真实输出中核对。

#### 2. mystery 的判决理由实际写的是“按有副作用处理”，不含“默认拒绝”
- **原文**：“两个易错点值得指出来。其一，`n > 0` 判断的是**幸存使用**——`use_count` 被删除时的减法持续修正着，所以轮到生产者时这个数字是"幸存世界"的真实值，不是进 Pass 时的旧值。其二，"副作用"和"白名单外"分成两档：`debug` 是我们明确声明有副作用的（理由写"执行时打印"），`mystery` 这种没听过的算子是副作用未知（理由写"默认拒绝"）——处理结果一样都是留，但审计日志能分清"为什么留"。”
- **依据**：`_judge` 对白名单外算子的实际理由串是“算子 {op} 不在纯算子白名单——副作用未知，**按有副作用处理**”（自测 E 的断言也是检查 reason 含“白名单”）；“默认拒绝”四个字只出现在 `is_pure` 的 docstring 和 [3] 的演示解说里，判决日志里没有。两分档的叙述逻辑本身没错，但“理由写‘默认拒绝’”与日志实际文本不符，读者对照日志时会找不到这四个字。建议改为“理由写‘副作用未知，按有副作用处理’”。
- **置信度**：高。reason 字符串与自测断言均已在代码核对。

#### 3. “跑一遍、一行不差才算语义不变”宜注明是抽查而非证明
- **原文**：“> **今日目标**：完成本教程后，你能说出死代码消除（DCE）的完整判据——"结果无人使用＋算子纯"才可删，且必须同时守住三条保留规则（图输出是对外契约、副作用节点删了会改变可观察行为、图输入定义签名）；解释为什么"只看有没有人用"的清扫工会删掉 `debug` 并级联错删三条语句；说清反向遍历为什么一趟就能扫干净多层死链（拓扑序保证消费者先受审＋使用计数的减法维护）；并亲手运行一个带语义对照的 `dce` Pass——删前删后用解释器各跑一遍，输出和打印一行不差才算语义不变。”
- **依据**：`same_behavior` 只在一份输入（%x=3／%x=7）下对照，单点相等是语义不变的必要条件而非充分条件——一个只在其他输入值上分歧的错误 Pass 同样能通过这种验证（[3] 的 BuggyDcePass 恰好靠打印行被抓，但如果事故只在部分输入上显形，单点对照会漏掉）。对 DCE 而言，真正的语义保证来自判定规则本身（删的都是“无使用者＋纯”，对**任意**输入都不产生输出／打印差异），解释器对照是回归网。这是初学者必知的坑：把单输入相等当通用验证范式，会在后续 Pass（尤其含数值舍入／分支的）上翻车。建议在 5.2 或 [4] 补一句“单点对照是抽查，语义保证来自判定规则对所有输入成立”。
- **置信度**：高。属验证方法论问题，不涉及当天代码正确性。

#### 4. 对执行原则 3 的引用少了“为什么可能更快”半句
- **原文**：“**语义对照用的最小解释器**是今天验证体系的半壁江山——学习计划执行原则 3 说"每个优化都要回答：为什么语义不变、如何验证"，`interp` 就是那个"如何验证"：”
- **依据**：学习计划执行原则 3 原文为“每个优化都要回答：为什么语义不变、**为什么可能更快**、如何验证”。引号内的转述少了中间半句。对本天无实质影响（DCE 的收益由 [5] 成本对照单独交代），但按引号回查计划原文会对不上。建议逐字引用，或去掉引号改为明确的转述句式。
- **置信度**：高。计划原文已核对（AI芯片编译器学习计划.md“执行原则”第 3 条）。

#### 5. “当且仅当”判据与“图输入无人读也保留”存在模型张力
- **原文**：“判据一句话：**一条语句是死代码，当且仅当删除它之后，程序的可观察行为完全不变。**在我们的图里，可观察行为就两样：图输出（调用方拿到的返回值）＋ 副作用节点的效果（`debug` 打印的行）。”
- **依据**：按“就两样”的严格口径，无人读的 `input` 删掉之后输出与打印都不变，会落在“当且仅当”的死代码一侧，与 3.2 的“图输入——留（定义签名）”和判定表第二行矛盾；3.2 给出的理由（“运行期调用方按老签名喂数据，`%x` 就没了着落”）实际上把调用约定／签名也算作了可观察行为的一部分。结论都对，只是 3.1 的可观察行为清单没有覆盖这一样。建议在 3.1 或 3.2 显式把“函数签名／调用约定”补进可观察行为的定义，使“当且仅当”与三条保留规则自洽。
- **置信度**：中。张力是否构成问题取决于对“就两样”的严格读法；3.2 已给出正确的直觉理由，仅定义表述未闭合，不影响当天代码与输出的正确性。

#### 6. BuggyDcePass 的括注“规则只有‘结果没人用就删’”与实现有出入
- **原文**：“**[3] 事故重演**：让忘掉副作用的 `BuggyDcePass`（规则只有"结果没人用就删"）上同一张图：”
- **依据**：代码的删除条件是 `res is not None and op != "input" and use_count.get(res, 0) == 0`——除“结果没人用”之外还显式豁免了 `input`（`output` 因 res 为 None 天然不删），类 docstring 也写明“只放过了 input 和 output”。对 [3] 的主图无影响（`%x` 有两处使用），[3] 的输出记录也逐行核实无误；但括注“规则只有……”与实现不完全一致——读者若照括注重实现一个真的“只看结果没人用”的版本，在带无人读输入的图上会连 `input` 一起删，行为与 [3] 记录不同。建议括注补一句“（input／output 仍放过）”。
- **置信度**：高。代码条件与 docstring 已核对；影响仅限描述精度，不涉及当天输出。
