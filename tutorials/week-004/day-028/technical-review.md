## 【存疑】

#### 1. “IEEE 754 规定 -0.0 + 0.0 = +0.0”作为无条件陈述有例外，且机制归因不准确
- **原文**：“IEEE 754 规定 `-0.0 + 0.0 = +0.0`（向最近的偶数舍入）”
- **依据**：数值结论本身在默认舍入模式下正确——本机实测 `struct.pack(">d", -0.0 + 0.0).hex()` 为 `0000000000000000`，5.4 的输出全部复现一致。但两点需要核实：(1) IEEE 754 对“符号相反的两操作数之和恰为零”有专门规定：除 roundTowardNegative 舍入模式下结果为 −0.0 外，其余舍入模式（含默认的 roundTiesToEven）结果为 +0.0。因此“IEEE 754 规定 …=+0.0”作为无条件陈述存在 roundTowardNegative 例外（有趣的是在该模式下 `add(x,+0.0)→x` 对 −0.0 反而位级成立）；(2) 括号“（向最近的偶数舍入）”若读作机制解释则不准确：恰为零的和是精确结果，不发生舍入，且 +0.0 与 −0.0 的尾数相同，“最近偶数”平局规则无法区分两者——结果符号由上述零和符号专门规则决定，而非最近偶数舍入。若读作“在默认舍入模式下”的限定语则可接受。注：本环境无外网，未能在线核对标准原文条款号（记忆为 IEEE 754-2008/2019 第 6.3 节 The sign bit）；数值行为已本机实测。
- **置信度**：高（“表述过于绝对、机制归因易误导”这一判断置信度高；标准条款号未能在线核对，按记忆引用，请以标准原文复核）。

#### 2. “Day 27 的顺序实验就是证据”不支持“串起来照样可能坏”的语义破坏读法
- **原文**：“L4 防组装事故（每个 Pass 单测全绿，串起来照样可能坏——Day 27 的顺序实验就是证据）”
- **依据**：复跑 Day 27 `code/pipeline.py` 及查阅其 README：order A/B/C 三条顺序均收敛到“IR 逐字节相同”的 8 条终点（轮数 3/3/4，总改动 16/15/16），语义对照全绿；Day 27 README 的结论原文是“顺序改变的是路径（哪一轮谁干活），不改变终点”，max_rounds=2 的保险丝实验也明确写明“未收敛不等于错误”。即该实验演示的是“单轮不够／残骸／轮数由顺序决定”，没有演示任何“老积木被新组装碰坏”式的语义破坏。本句前半（集成回归存在的理由，即单测全绿≠集成正确）作为一般工程论断成立，但把它归因于 Day 27 的顺序实验属于证据错位：该实验只支持“组装顺序影响收敛路径与轮数”。若作者本意是“单轮残骸／漏优化”（Day 27 图 3 有“把‘坏顺序’的代价从‘结果错误’降级成‘多跑一轮’”的措辞），建议把“坏”改为“留残骸／漏优化”并点名单轮或保险丝场景，以免与 3.3 节 L4 条目“老积木没被新组装碰坏”及图 2 的同款表述形成语义破坏的暗示。
- **置信度**：中（“所引实验未演示语义破坏”这一点为高置信、已实测；“坏”字是否构成误导取决于读法，宽容读法下引用勉强成立，故列存疑而非错误）。

#### 2. 5.4 的 16 位十六进制位级宜标注为 f64 位模式
- **原文**：“原图（不折）：      %d = -0.0 + 0.0 = +0.0，位级 0000000000000000”
- **依据**：考卷是 f32 图，但解释器用 Python float（f64）求值，`f64_bits` 用 `struct.pack(">d", …)` 打印 f64 位模式（16 个十六进制字符）；f32 的位级应为 8 个字符（+0.0 为 `00000000`、−0.0 为 `80000000`）。结论不受影响（两种宽度下 −0.0 与 +0.0 都只差最高位），第 6 节错误二也已自我声明“今天只对 f64 位级较真”；但在 5.4 位模式首次出现处补一句域说明，可避免初学者把 16 位位模式误当作 f32 的表示宽度。属可读性改进，不影响正确性。
- **置信度**：高（已读源码并实测 `f64_bits` 的 pack 格式）。
