## 【错误】

#### 1. "截断再加"与"提升加完再截断"对 add 恒相等，"溢出时分道扬镳"不成立
- **原文**：“两种理解在不溢出时碰巧一致，溢出时分道扬镳（3.4）。”
- **依据**：3.1 节自己定下的口径是"整数（补码回绕算术）"，而回绕（模 2^32）算术里取模与加法、乘法可交换：(a mod 2^32 + b mod 2^32) mod 2^32 == (a + b) mod 2^32。因此"把 i64 常量截断成 i32 再加"与"提升到 i64 加完再截断成 i32"对 add 永远同值——不溢出时一致，溢出时也一致。本机复现（struct.pack 回绕模拟）：x=2147483647、w=1（i32 溢出）两种算法都得 -2147483648；x=5、w=2^32（即 3.4 的 4294967296）两种都得 5；x=12345、w=2^63-1（连 i64 加法都溢出）两种仍都得 12344。两种理解真正分道扬镳的是与取模不可交换的运算：除法（x=100、w=2^32：先截断变成除以 0，先提升再截断得 0）、移位、比较，或结果不截断而以 i64 宽度被消费的场合。"没定义的提升不折"这一结论本身正确，但该句给出的理由在教程自己的语义模型下为假，需要换成上述真实反例。
- **置信度**：高。数学事实（模算术同余）＋本机数值复现；唯一不确定点是作者若默认"i32 溢出是 UB 而非回绕"则可另作解释，但 3.1 明确写"补码回绕算术"、3.4 的溢出演示（2147483647+1 回绕成 -2147483648）也以回绕为前提。

## 【存疑】

#### 1. "同样的好心放到 const 4294967296 上就是静默的数值错误"对 add 并不成立
- **原文**：“但同样的好心放到 `const 4294967296`（2^32，i64 装得下、i32 装不下）上，就是静默的数值错误。”
- **依据**：接上条：对 add 而言，把 i64 常量 2^32 "当 i32 用"（截断成 0）再相加，与"提升到 i64 相加后截断"结果相同（(x + 2^32) mod 2^32 == x，本机两种算法都得 5），按"好心折掉/求值 add"的字面读法不会产生数值错误。该句真正成立的场景是另一种"好心"：把未截断的 Python 值 4294967296 直接物化成 i32 类型常量（即 3.4 上文说的"写着 i32、值却不在 i32 里"的谎言常量），或把常量用于除法/移位等与取模不可交换的运算。原文把两种情形压成一句，字面因果不成立；若作者本意就是"谎言常量"，建议把句子改写为明确指向"存进图里的常量值"，或换一个除法反例。
- **置信度**：中。数学部分确定；不确定点是作者意图指哪种场景——若指"未截断值直接落图"，则 3.4 整段自洽，只是表述有歧义。

## 【建议】

#### 1. "NaN 同理"不能推出"nan × 1.0 逐位不变"，IEEE 754 不保证 NaN payload 逐位传播
- **原文**：“——乘以 1 连符号零都原样保留（inf、NaN 同理：`inf * 1.0 = inf`，`nan * 1.0` 还是 nan）”
- **依据**：该句前半句的主张是"逐位不变"。"−0.0 × 1.0 逐位不变"与"inf × 1.0 位模式不变"都正确（均已实测）；但 IEEE 754（754-2019 §6.2）只规定 NaN 参与运算的结果是安静的 NaN，payload 是否逐位传播属"推荐"而非强制，信号 NaN 参与运算还会被静默化（位模式必变）。所以"同理"只能读到值层面（结果还是 NaN），读不到位层面。02-mechanism.svg 中"mul(x,1.0)：任何 dtype 都安全，逐位相等"是同一措辞。对结论无影响（值层面 mul(x,1)→x 安全，LLVM 也无条件折 fmul x, 1.0），建议限定为"值不变"或补一句"NaN 的位模式标准不保证"。
- **置信度**：高（标准条文）；不确定点仅是"同理"是否会被读者理解为逐位相同。

#### 2. LLVM 折 fadd x, 0.0 除 nsz 外还有"可证明非 -0.0"的放行路径
- **原文**：“LLVM 的 InstCombine 把 `fadd x, 0.0` 折成 `x` 要求 fast-math 的 `nsz`（no signed zeros）标志”
- **依据**：llvm-project main 分支 llvm/lib/Analysis/InstructionSimplify.cpp 的 simplifyFAddInst 实际条件是 match(Op1, m_PosZeroFP()) && (FMF.noSignedZeros() || cannotBeNegativeZero(Op0, Q))——nsz 或值域分析证明 Op0 不可能是 -0.0，满足其一即折；同文件 simplifyFMulInst 中 "// X * 1.0 --> X" 确实无任何标志要求（README 后半句核对无误）。"要求 nsz"在无额外信息时成立，作为锚点建议补半句"（或能证明 x 不可能是 -0.0）"，正好呼应本 Pass 门卫"靠证据放行"的主题。
- **置信度**：高（对 LLVM main 分支源码逐行核对）。

#### 3. 图 3 的"决策日志与真实输出逐字一致"与 SVG 实际内容有记法出入
- **原文**：“决策日志与真实输出逐字一致”
- **依据**：03-example.svg 中正例 IR 的类型写作 i32<2x3>（真实 ir_dump 打印 tensor<2x3xi32>），决策日志为缩写格式（如"i32 splat (2,3)，值 0 是 add 的单位元"，真实输出分两行、shape 写作 (2, 3) 且行尾多"五道门全过"）。数字与结论全部正确，但"逐字一致"按字面不成立；建议改成"与真实输出一致（摘录）"或统一图内记法。
- **置信度**：高（SVG 文本与 5.3 节输出逐项比对）。

#### 4. 开篇把"测试全绿"归因于"随机数几乎不可能产生 -0.0"，与 3.1 事实 1 的归因（== 看不见）不一致
- **原文**：“单元测试全绿——因为你喂的随机数几乎不可能产生 -0.0”
- **依据**：开篇后文写"模型输出在 == 意义下全对"，即测试以 == 比较；而 == 对 -0.0/+0.0 天生不敏感（-0.0 == +0.0 为 True），即使随机数真的踩中 -0.0，== 型测试照样全绿——"随机数不产生 -0.0"并不是测试全绿的原因（3.1 事实 1 给出的原因才是：== 看不见符号零）。随机数稀有真正解释的是"下游符号敏感计算（1/y 的正负）没在测试里暴露"。两种解释各自成立，但因果指向不同，建议在开篇点破"测试用 ==，== 本来就看不见"，避免读者误以为 == 测试能拦住 -0.0。
- **置信度**：中（叙述歧义而非硬错误，取决于开篇"单元测试"具体比较什么）。
