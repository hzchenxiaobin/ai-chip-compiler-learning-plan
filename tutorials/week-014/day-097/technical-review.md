# 第 97 天技术校对报告

## 【错误】

#### 1. "预热烧掉 C 缺页"的机制归属与 bench 代码不符
- **原文**：“预热 3 次把这些成本全部"烧"掉——协议层面保证计分阶段只剩稳态行为”
- **依据**：本句前文把"C 首次写入缺页"列为预热要烧掉的冷成本，但 `run_bench` 里的 C 是 `std::vector<float> C((size_t)M * N, 0.0f)`（config_bench.cpp:159）：构造函数把 1 MB 全部清零，256 个页在计时开始前就已被写入并完成缺页，之后内核（含 3 次预热）不会再发生 C 缺页。"缺页发生在内核里"只存在于 cold 模式——`run_cold` 用 `calloc`，且代码注释（config_bench.cpp:223）明确写明"calloc：C 的页在内核首次写入时才缺页——冷启动成本全部计入这一次运行"，而那一次是**被计时的**，不是被预热烧掉的。3.2 节对 cold 模式的描述本身准确（含"保证首次写入缺页发生在内核里"），第 4 节第 1 条和图 2 的时间线把两种模式混在了一起。bench 协议中预热真正烧掉的是指令缓存、分支预测器、TLB/缓存状态；C 缺页一项应由 vector 清零在计时外付清。本轮已实际编译运行该代码（GCC 9.4.0 aarch64，30/30 PASS）复核。
- **置信度**：高（代码路径逐一核对：bench 用 vector 清零、cold 用 calloc，两条路径均无"预热烧 C 缺页"的场景）

#### 2. 离群值对应的调度时长"几十微秒"与数据相差约三个数量级
- **原文**：“其中混着 2.15、2.28 这样的瞬时离群值（可能是内核被调度走了几十微秒），中位数稳在 2.448”
- **依据**：n=512 的名义 FLOP 固定为 2·512³ = 268,435,456。按中位数 2.448 GFLOPS 倒推，一次内核约 109.7 ms；按离群样本 2.155 GFLOPS 倒推约 124.6 ms，多出约 14.9 ms；2.28 GFLOPS 的离群值也对应多出约 8.1 ms（样本值见 outputs/samples-512.csv 的 `CSV,2,ijk-128,9,2.1550` 等行）。即这两个离群样本的额外时间是**毫秒量级（约 8～15 ms）**，而"被调度走几十微秒"只能造成约 0.05% 的波动。机制方向（被抢占/邻居干扰）合理，但量级应写成毫秒级（例如被其他线程抢走若干个时间片）。
- **置信度**：高（纯算术，样本与中位数均来自冻结输出）

#### 3. "上界被'只受干扰'封死"把上界的成因写反了
- **原文**：“单次性能样本的上界被"只受干扰"封死、下界被干扰大小撑开——分布天然左偏”
- **依据**：此处"性能样本"指 GFLOPS（= FLOP/时间）。GFLOPS 的上界出现在**没有任何干扰**、只剩有效计算的那一次——干扰只会让时间变长、GFLOPS 变小，因此封死上界的是"不受干扰"；一个"只受干扰"的样本趋近 0 GFLOPS，属于下界方向。本句后半"下界被干扰大小撑开"是对的，前半方向写反（疑为"只/不"笔误）。随后的结论本身正确：对本表 ijk-128 的 21 个真实样本实算，均值 2.4179 < 中位数 2.4484，左偏成立。
- **置信度**：高（逻辑方向明确；若按笔误处理则仅需改一个字）

## 【存疑】

#### 4. "排名（6 和 5）在两次运行间换过位置"未注明口径，中位数排名其实没换
- **原文**：“表里它们的排名（6 和 5）也确实在两次运行间换过位置”
- **依据**：核对 perf-512.txt 与 perf-512-run2.txt：两份表里 ijk-64/ijk-128 的 rk_med 均为 6/5，中位数排名从未互换（两次都是 ijk-128 更快）；真正换位的是 rk_1st（首样本排名）：run1 为 6/5，run2 为 5/6。本节正在论证"中位数口径下不能下结论"，不加限定容易让读者去查 rk_med 列却发现对不上。对照 C 与"错误二"处均正确标注了"单样本口径"，建议此处同样写明是 rk_1st。
- **置信度**：高（两份输出逐行核对）；归为存疑是因为该句存在"单样本口径"的一种自洽读法

#### 5. "-O2 下掉回 3 GFLOPS"的引用口径与编译器版本适用范围需核实
- **原文**：“同一份代码在 `-O2` 下 ikj 集团会掉回 3 GFLOPS 量级（D96 的实测）”
- **依据**：D96 的实测口径是 `-O2 -fno-tree-vectorize`（day-096/README.md 的构建命令与 outputs/bench-scalar.txt，标量版 reorder 2.875 GFLOPS），并非纯 `-O2`。在 GCC 9.4（本教程环境）上 -O2 确实不做自动向量化——GCC 12 才开始在 -O2 启用 very-cheap 自动向量化模型——所以结论在本环境成立；但论断未绑定编译器版本，用 GCC ≥ 12 复现时纯 -O2 可能部分向量化，"掉回 3 GFLOPS"未必再现。建议补"GCC ≤ 11"的适用范围或注明 D96 实测的具体 flags。
- **置信度**：中（D96 的 flags 已核实；GCC 12 起 -O2 启用 very-cheap 向量化是公开的版本变更，但该模型是否会向量化本内核未实测，无法断言）

## 【建议】

#### 6. 图 3 的"工作集 128KB"未计 A tile
- **原文**：“128³ 的工作集（B tile＋C tile = 128KB）虽已超出 64KB 的 L1d，但 L2（512KB/核）接得住”
- **依据**：一个 (i0,j0,k0) 块内三个 tile 都被反复访问：B tile（TK×TN）在内层 k 循环复用、C tile（TM×TN）在 i 循环复用、A tile（TM×TK = 128×128×4B = 64KB）在 j 循环中以广播方式复用，完整工作集为 192KB 而非 128KB。结论（超 64KB 的 L1d、512KB L2 接得住、n=512 上大 tile 更快）不受影响，但初学者按 128KB 估算会漏掉 A 这一块；D98 复盘 516 翻转时该口径还会复用，建议统一为 192KB（或注明"B＋C 128KB，另有 A tile 64KB"）。
- **置信度**：高（对 ikj 内核三个循环的访问矩阵逐一核对）

#### 7. "512 上能下的硬结论"清单里混入了 516 的结论
- **原文**：“今天 512 上能下的硬结论只有三个：ikj 集团整体比 ijk 集团快约 4 倍、ikj-128 是 512 的最优、516 上冠军翻转”
- **依据**：前两条是 512 的结论，第三条"516 上冠军翻转"来自 shape=516 的实验（outputs/perf-516.txt），不属于"512 上"能下的结论。仅影响表述严谨性，不影响任何数据。
- **置信度**：高（纯逻辑归类问题）

#### 8. "±4% 大于约 5% 的差距"的比较口径建议澄清
- **原文**：“比如 516 上 ikj-64 和 ikj-128 只差约 5%，冷样本可能直接改变结论”
- **依据**：516 上 ikj-64 对 ikj-128 的中位数差为 (13.878−13.226)/13.226 ≈ 4.9%；而 3.2 节表里冷样本的单侧偏差最大为 +3.6%（ikj-64，约 4%），严格说 4% 并不大于 5%。要让"冷样本可能改变结论"成立，正确算法是两个配置的冷偏差可反向叠加（本表最大约 3.6% + 2.1% ≈ 5.7%，按 ±4% 两侧估算最多约 8%），足以翻动约 5% 的差距。结论（冷样本不可当成绩）没问题，建议写明比较口径，避免读者拿 4% 与 5% 直接比大小。
- **置信度**：中（若作者本意是"±4% 的散布带总宽约 8%"则原句可自洽，但正文未如此定义）
