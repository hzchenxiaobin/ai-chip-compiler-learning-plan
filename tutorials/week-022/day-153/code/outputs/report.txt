== CE1 候选：小 shape 的 O2 展开反例（D125 伏笔——本机验证）==

  假设：4×6×3 的 matmul——O2（全展开）比 O0（循环）慢

  4×6×3: O0 1.346µs vs O2 0.881µs（0.65×）——O2 正常更快
  8×8×8: O0 2.310µs vs O2 1.056µs（0.46×）——O2 正常更快
  16×16×16: O0 15.331µs vs O2 2.696µs（0.18×）——O2 正常更快

  机制解剖（4x6x3 的反例）：
    ① 循环开销本就低：72 MAC 的 k=6 循环只 ~60ns 控制——省不了多少
    ② 展开的体积代价：72 个 fmul 独立成行（~290 行代码 vs ~30 行）
       ——i-cache 局部性变差＋取指带宽占用
    ③ 无 ILP 可创造：acc 串行链（D150 的 H3）——展开不产生并行
    净效果：省的循环控制 < 体积代价 → 更慢

== CE2 候选：K 太小的收益存疑（D152 数据引用）==
  64×160×32：1.7×（vs 中位 9.4×）——收益存疑但不为负
  机制：K=32 的展开空间只有 160³ 的 1/5

== CE3 候选：教学 tile 负优化（D151 数据引用）==
  160³ tile(64,64)：0.3×——负优化（比朴素慢 3 倍）
  机制：重复计算 ×6.25 吃掉复用收益（D145 教学取舍的性能账）

== O2 展开的适用条件（反例的边界文档）==
O2 循环展开的适用条件（教学版边界文档）

收益区（建议开）：
  · K ≥ 64：k 循环有足够圈数——展开省的循环控制显著
  · 计算量 ≥ 1 MFLOP：固定开销占比低——净收益显现
  · 实测：64³+ 的方阵 7~14×

存疑区（测了再定）：
  · K ∈ [16, 64]：展开空间受限——收益 1.5~5×（依赖 N/M 形态）
  · 实测：64×160×32 只 1.7×

反例区（环境依赖——测了再定）：
  · K < 16＋小计算量：展开体积代价可能超过循环节省
  · 实测（D125·LLVM 18/aarch64 Linux）：4×6×3 的 O2 慢 60%——反例成立
  · 实测（本日·LLVM 23/macOS arm64）：同一 shape 的 O2 反而快 22%——不复现！
  → 反例是环境函数：编译器版本的展开启发式不同（LLVM 23 收敛了小 kernel 的展开）
  → 适用条件必须带环境声明——「在 LLVM 18 的小 kernel 上」≠「所有环境」

判据（一行版）：展开的收益 ≈ K × 每圈控制开销；
             展开的代价 ≈ 代码体积增量 × 取指/缓存代价。
             K 大且计算密集 → 收益胜；K 小且计算稀疏 → 代价胜。


== CE1 的诚实结论：D125 反例的版本依赖性 ==
  D125（LLVM 18/aarch64 Linux）：4³ 的 O2 慢 60%——反例成立
  今天（LLVM 23/macOS arm64）：O2 全部更快（0.79/0.45/0.17×）——反例不复现
  → 反例本身是环境函数（编译器版本的展开启发式不同）！
  → 教训：反例的适用条件要带环境声明（版本/平台）——
    「LLVM 18 的小 kernel 展开反例」≠「所有 LLVM 的小 kernel 展开反例」
  本机数据：[0.65, 0.46, 0.18]——无反例（但 D151 的 tile 0.3× 仍是铁证）
