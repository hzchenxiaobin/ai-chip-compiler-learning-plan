# 第 62 天技术校对报告

校对环境：本机 Python 3.11.4 / numpy 1.26.4 / Ubuntu LLVM 18.1.8（`/usr/lib/llvm-18/bin/mlir-opt`、`mlir-cpu-runner`，Linux aarch64），与 README 声明一致。以下结论均在本机复跑核实：`test_specialize.py` 28/28、`products_lab.py` 8/8；k_blind 动态版 `mlir-opt` exit=0、mini 层 exit=3、`--force` 后 CLI exit=4 且 mlir-opt exit=1（错误文案逐字一致）；特化前后降级 IR 指标（`memref.dim` 1→0、unroll 后 `affine.for` 1→0、load 18→36、行数 55→94、字节 2453→4273、scf 版 23/22 行）；dispatch 三场景 26 个数与冻结 `dispatch_exec.txt` 及 numpy 对拍逐位一致；练习 1/2/3 的预测答案逐项实测；错误 3 的翻倍指纹（2×C2 恰为 440/560/980/1280/1520/2000/2060/2720）核算无误。除下列条目外，README、代码、冻结输出与 4 张 SVG 的其余技术论断（含对 Day 61 术语、第 96/129/130 天计划的交叉引用）均与事实一致。

## 【错误】

#### 1. README 与图 4 的编译耗时数字和它明确引用的冻结产物 `outputs/products_lab.txt` 对不上
- **原文**："- **对应到技术上是**（products_lab.py 实测）：12 次调用的轨迹 `[2,2,4,2,8,2,4,16,2,4,2,32]` 只有 5 个不同 M，于是 5 份特化产物（每份编译 18.0～18.8 ms，中位数×3）+ 1 份通用回退（18.9 ms）= 6 个产物、特化编译总耗时 92.7 ms。产物数量跟着**不同 Shape 数**走，不跟调用次数走——这是特化划算的全部前提（batch 会反复出现）。"
- **依据**：README 5.4 节明确写 "（`outputs/products_lab.txt` 真实输出）"，但该冻结文件的实际数字是：5 份特化各 18.7/18.8/18.7/18.8/18.9 ms、通用版 19.0 ms、特化总耗时 93.9 ms、策略 A 19.0 ms、B/C 112.9 ms——与 README（3.3 节、5.4 节第 1/2 点、第 9 节的 18.0～18.8、18.9、92.7、111.7 ms）和图 4（04-products.svg 内嵌 18.0/18.5/18.8/18.6/18.8、18.9、92.7、111.7 ms）三处互不一致。`make_images.py` 文档字符串称图内数字来自 2026-11-12 的运行，说明冻结产物是在 README/图之后被另一次运行覆盖的（本机今日复跑为 95.2/114.3 ms，证实耗时确有抖动）。问题不在抖动本身，而在「README 声称引用某文件、数字却不在该文件里」：读者按 run_all.sh 复跑或对照 outputs/ 时会对不上账。产物数、字节数、`memref.dim` 计数等其余数字均与冻结产物一致，仅耗时一组不一致。另：图 4 中 "92.7 + 18.9 ≈ 111.7" 按其自给数字应为 111.6。修复方向：以冻结产物为准统一 README、图 4（与 make_images.py 注释），或重新冻结一次输出并同步全部引用处。
- **置信度**：高——直接比对 README、SVG 内嵌文字与冻结文件三方可复核。

#### 2. 练习 2 把 `memref<4x2xf32>` 的第一维说成 N：该声明声称的是 M=4，根本不存在「N=4」失配
- **原文**："把 `matmul_dyn.mlir` 复制成 `mm2.mlir`，把 `%o` 的类型全部改成 `memref<4x2xf32>`（输出声称 N=4，而 B 的 N 明明是 2）。"
- **依据**：按 README 自己第 4 节第 2 点的口径（"`%o` 的 M 跟随 `%a.dim0`、N 跟随 `%b.dim1`"），`memref<4x2xf32>` 第一维是 M、第二维是 N——这个声明说的是 M=4、N=2；B 的 dim1=2 与 `%o` 的 dim1=2 完全一致，不存在 N 失配。实测（本机 mlir-opt 18.1.8）：(a) 该 mm2 动态版 exit=0 属实，但放行的原因是 `%o` 的 M=4 要对的正是 `%a` 的 dim0=?（无从比），并非 "N 的失配和昨天的 K 一样被 `%a` 里的 `?` 藏住"（5.4 节实测答案里这句同样错标了维度）；(b) `--specialize-shape "a=2x3"` 后 `%o` 被推导覆盖成 `memref<2x2xf32>`、(c) 产物 exit=0，两者均复现无误。若作者本意是 N 失配，类型应写 `memref<2x4xf32>`——该变体本机实测同样 exit=0（A 的 M=? 令循环上界含动态维、整段逐维检查被跳过，见第 4 条机制），"被 ? 藏住"的叙事才成立。修复方向：要么把类型改成 `memref<2x4xf32>` 保持「N 谎言」的讲法，要么把括号与 (a) 的解释改成「输出声称 M=4，而 A 的 M 是 ?」。
- **置信度**：高——维度归属由教程自身口径即可判定，(a)(b)(c) 三问均在本机实测。

#### 3. 练习 1 的「第三组与第一组产物相同」与工具实测产物不符
- **原文**："第三组与第一组产物相同（`o` 的 spec 冗余但一致，exit=0）。"
- **依据**：本题三组依次是 `a=4x3`、`a=?x3`、`arg0=2x3,arg1=3x2,arg2=2x2`。实测（本机 specialize.py）：第一组产物 `%a → memref<4x3xf32>`、`%o → memref<4x2xf32>`；第三组产物 `%a → memref<2x3xf32>`、`%o → memref<2x2xf32>`——类型不同，产物并不相同。第三组实际等于 5.3 节主流程（`a=2x3,b=3x2`）的产物；括号里「`o` 的 spec 冗余但一致、exit=0」这半句本身是对的（`arg2=2x2` 与推导一致，仅冗余确认）。修复方向：改成「第三组与 5.3 节主流程的产物相同」或「与只写 `arg0=2x3` 时的产物相同」。
- **置信度**：高——两组产物已实测对比，类型串逐一不同。

#### 4. 图 3 内嵌文字把「循环上界解不出才跳过检查」错误概括成「类型里混进一个 ? 就什么都推不出」
- **原文**："**图 3**：上半部分是降 scf 循环后唯一的差别——M 的上界从 `%dim`（运行期读取）变成 `%c2`（编译期常数）；中间是三次 full-unroll 后的结局——动态版 M 循环卡在 `%dim` 上（affine.for=1），特化版全部直码化（affine.for=0、36 个 load）；下半部分是 k_blind 的两种命运。"
- **依据**：图注本身无误，但它指向的 images/03-example.svg 内嵌文字「第 61 天的结论重演：类型里混进一个 ?，整套静态推断退化为「什么都推不出」」是与源码事实冲突的过度推广——且恰是 day-061/technical-review.md 第 1、2 条已判定为错误的同款表述。真实机制（LLVM 18.1.8 `mlir/lib/Dialect/Linalg/IR/LinalgInterfaces.cpp` 的 `verifyStructuredOpInterface`，已在 release/18.x 源码核实）：先算 `getStaticLoopRanges()`，仅当所有循环上界都静态（`if (llvm::none_of(endLoopRangeValues, ShapedType::isDynamic))`，源码注释 "Verify only static cases..."）才进入逐维比较；进入后 `if (ShapedType::isDynamic(shape[dim]) || shape[dim] == 0) continue;` 只跳过为 ? 的那一维，其余静态维照常比对。本机反例：`memref<2x4xf32> × memref<3x2xf32> → outs memref<?x2xf32>`（类型里有 ?，且在输出侧）exit=1，报 "operand #1 has shape's dimension #0 to be 4, but found 3"——混进 ? 仍查出静态失配。跳过整段检查的触发条件是「喂循环上界的维含 ?」（对 matmul 即 A.dim0/A.dim1/B.dim1），不是「类型里出现 ?」；k_blind（M=?）恰好命中跳过条件，图 3 却把个案写成通用规律。README 正文（3.2 节「`?` 让推断失明」）因限定在 k_blind 语境而无此错，但与图 3 口径不一致。修复方向：把图 3 该句改成「喂给循环上界的维是 ? 时，整段逐维检查被跳过」，并与 3.2 节口径统一。
- **置信度**：高——机制定位到 18.x 源码逐行核实；反例在同版本 mlir-opt 复现，且与 day-61 校对报告结论互相印证。

## 【存疑】

#### 5. 「? 失明 / 特化后点亮」的表述未加版本限定，LLVM 新版行为未核实
- **原文**："**静态检查重新生效**：`k_blind.mlir` 同一处 K 失配，动态版 exit=0 放行，特化后 exit=1 拦下——`?` 让推断失明（昨天），特化把灯重新点亮（今天）。"
- **依据**：该现象及其报错文案（"inferred input/output operand #1 ..."）都是 LLVM 18.1.8 `verifyStructuredOpInterface` 的实现细节（跳过条件已在 release/18.x 源码核实，见第 4 条）；LLVM 19 及之后 linalg 的 shape 验证逻辑有持续重构，本机无新版可测，「任一循环上界动态即整段跳过」的行为与文案在新版是否保持未验证。README 前置准备与 5.3 节都注明了 "本机 Ubuntu LLVM 18.1.8"，但 3.2 节与图 2/图 3 以一般规律口吻陈述该现象。建议在 3.2 节或图 3 处补一句「以 18.1.8 实测为准，验证器行为随版本可能变化」，避免读者在新版环境复现失败时误判。
- **置信度**：中——18.1.8 行为已实测并定位源码；更高版本行为未验证，无法断言已变或未变。

## 【建议】

#### 6. 「加一倍代码体积」与实测比例（约 +7 成）不符
- **原文**："代价是 5 个不同 batch = 5 份产物 92.7 ms 编译加一倍代码体积；"
- **依据**：冻结产物实测：展开后特化版 4273 B vs 动态版 2453 B（+74%）、94 行 vs 55 行（+71%），都不到「加一倍」（+100%）。建议改成「代码体积约增七成（4273 B vs 2453 B、94 行 vs 55 行）」；该句中的 92.7 ms 见第 1 条。
- **置信度**：高——数字直接来自冻结产物。

#### 7. 「每次优化决策都被卡住」的绝对化说法被当天自己的实测反驳
- **原文**："每次循环边界判断、每次优化决策都被这个「运行期才知道」卡住。"
- **依据**：当天实测显示动态版并非「什么都优化不动」：三次 full-unroll 后 `affine.for` 从 3 个降到 1 个、`affine.load`=18——N、K 两层循环（上界 `%c2`/`%c3` 编译期常数）照常完全展开，被卡住的只有依赖 M 的那一层（上界 `%dim`）。建议限定为「每次依赖 M 的边界判断与优化决策」，与 5.3 节的实测口径一致。
- **置信度**：高——依据即本日冻结产物 `matmul_dyn_unr3.mlir`。

#### 8. 退出码 2 的语义列举不全，且「4 = 已写出」在不给 `-o` 时不成立
- **原文**："- **退出码即语义**：0 成功；2 spec 非法（rank / 改静态维 / 未知名字）；3 mini K 对账失败（不写出文件）；4 已写出但 `mlir-opt` 拒收。CI 里可以直接用。"
- **依据**：读 specialize.py `main()` 的返回路径：输入文件不存在（"找不到输入文件"）与未给/空 `--specialize-shape` 也返回 2——CI 若以「2 == spec 非法」做分支，遇到文件缺失会误判为 spec 问题；另外不给 `-o` 时外部验证失败同样返回 4，但既没写文件也没打印产物，「已写出但拒收」的描述只覆盖给了 `-o` 的情形。建议在 5.2 节补一句「输入文件缺失也返回 2；4 表示外部验证失败（给了 -o 时文件会写出但不可用）」。
- **置信度**：高——直接来自 specialize.py 源码控制流，并经 CLI 实测（k_blind 不带 `-o` 不落盘、返回 3）。
