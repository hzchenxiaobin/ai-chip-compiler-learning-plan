审阅对象：`tutorials/week-016/day-108/README.md`、`code/`（tune.py、kernel_gen.py、bench.py、run_all.sh、gen_images.py）、`code/outputs/` 全部 11 份冻结产物、`images/` 全部 3 张 SVG。核实手段：逐条复算 outputs/ 中的数字；在临时目录（/tmp/opencode）实际运行 self-test（33/33 通过）、单进程完整 tune_run、--exp stability 与 --exp cost（均不触碰仓库冻结产物）；diff 确认 kernel_gen.py / bench.py 与 D107 逐字一致；核对 D106/D107/D92/D97 的被引数字（12,970、8.6% 漂移、0.11% 前缀扫描、516 冠军翻转、D92 容量翻转）均在原文中找到。以下逐条给出原文引用与依据。

## 【错误】
#### 1. 摘要把"总槽位数 98"写成了"98 个规则候选 + 2 个投毒探针"
- **原文**：“98 个规则候选 + 2 个投毒探针”
- **依据**：实际空间是 96 个规则候选 + 2 个投毒探针 = 98 个总槽：S1 = 2 tile×6 顺序×2 展开 = 24，S2 = 3×6×2 = 36，S3 = 36 + 2 投毒 = 38，合计 96 规则 + 2 投毒（self-test 断言与 `build_space` 一致）。按摘要字面（98 规则 + 2 投毒）总槽应为 100、筛选记录应为 100 条，与冻结的 `results.jsonl`（110 行 = screen 98 + final 12）和 `tune-table.txt` 尾部"记录数：110 条 = screen 98 + final 12"直接矛盾。README 第 1 节自己写的是正确口径："共 96 个规则候选；S3 另投 2 个 no-tail 探针，总槽位 98"。同一混淆还出现在第 2 节图 1 说明"输入 3 个 shape 的 98 个候选槽 + 2 个投毒探针"，以及 `images/01-overview.svg` 中"① 定空间"框的标签"98 槽/shape"（98 是三个 shape 的合计，每 shape 分别是 24/36/38，把合计标进"每 shape"的框里是双重错误）。
- **置信度**：高（算术与冻结产物可逐条复验）

#### 2. "缺省配置 32³ ijk U=1 慢 17%~24%"的百分比口径错误
- **原文**：“缺省配置 32³ ijk U=1 慢 17%~24%”
- **依据**：决赛数据（tune-table.txt / results.jsonl）：S1 19.08 vs 15.80、S2 65.12 vs 51.53、S3 42.02 vs 32.06 ms。"A 比 B 慢 x%"的通行定义是 (A−B)/B，据此缺省比冠军慢 20.8% / 26.4% / 31.1%，不是 17~24%；17.2% / 20.9% / 23.7% 是"省下的时间占缺省时间的比例" (A−B)/A——那是"省/快"的口径，不是"慢"的口径。文句用了"慢"却配了"省"的数，按字面读数错误。`images/01-overview.svg` 的"缺省 32³ ijk U=1 慢 17~24%"同错；而 03-results.svg 的"快 17%/21%/24%（省 X ms/次）"与正文第 1 节"换来 17%~24% 的执行加速"在"省时"口径下是自洽的——问题只出在"慢"这个措辞配错了基数。
- **置信度**：高（数值复算无歧义；若作者本意即"省 17~24%"，则属表述层面的技术错误，数字本身无需改）

#### 3. "远大于 2×MAD（<0.2%）"里 2×MAD 的数值不实
- **原文**：“决赛 1~2 名差距（7.4%~8.0%）远大于 2×MAD（<0.2%）”
- **依据**：按本系列 D107 自己的口径（bench.py `render_table`：noise = max(MAD₁,MAD₂)/median₁×100，判据 gap > 2×noise），从 results.jsonl 决赛记录复算：S1 决赛 top-2 为 15.80/17.07 ms、MAD 取 max(0.029, 0.017)，2×MAD 口径 = 2×0.029/15.80 = 0.37%；S2 = 2×0.064/51.53 = 0.25%；S3 = 2×0.022/32.06 = 0.14%。三个 shape 里两个（S1、S2）超过 0.2%，"<0.2%"只对 MAD 本身成立（0.18%/0.12%/0.07%）。括号里应写"MAD < 0.2%"或"2×MAD < 0.4%"。`images/03-results.svg` 中"2×MAD 口径 < 0.2% → 差距远大于波动：成立"重复了同一错误数值。定性结论（差距 7.36~8.02% 远大于波动、排名成立）不受影响。
- **置信度**：高（全部数字出自冻结记录，复算过程如上）

#### 4. "90+ 个注定进不了决赛的候选"计数错误（实际 86 个）
- **原文**：“90+ 个注定进不了决赛的候选只烧 11 次调用”
- **依据**：98 个槽位 − 12 个决赛名额（每 shape top-3 ∪ 缺省 = 4，共 3×4）= 86 个，不是 90+。另外 86 个里有 2 个投毒候选死在门上、只烧 1 次门调用而非 11 次（runs_of 对 passed=false 返回 1），"只烧 11 次"严格说只对 84 个过门候选成立。tune.py 的 stability 输出文案与 `images/02-mechanism.svg`（"把 90+ 个进不了决赛的候选挡在 3+7 的便宜协议后面"）重复了同一个 90+。
- **置信度**：高（98−12=86，纯算术）

#### 5. 挑战 B 的预测值"有缓存只有 74 次左右"与所述实验 setup 不符（单进程实测 50 次）
- **原文**：“有缓存只有 74 次左右（跨 shape 的公共配置和决赛复用只编一次）”
- **依据**：挑战 B 要求"在两个新目录各跑一轮完整搜索（不设 --limit）"——即每轮是单个进程。我在临时目录实测单进程完整一轮：`compile_misses = 50`（缓存命中 60 次），与代码结构推演一致（S1 24 + S2 新 12 + S3 新 12 + 投毒 2 = 50，决赛全部命中缓存）。74 = part1 的 24 + part2 的 50，只在"断点续跑两段"场景成立，因为编译缓存不跨进程、part2 从空缓存重编——README 3.1 节自己明确写了这一点。读者照挑战 B 的步骤做会测得 50 而非 74，预测与实验对不上；"差额 = 缓存命中数"的自检在单进程下应改为 110 − 50 = 60 = 命中数（该关系本身仍成立）。
- **置信度**：高（已实际运行复现：单进程 50 miss / 60 hit）

#### 6. "k=5 时摆动缩小"与 stability.txt 的冻结数据矛盾
- **原文**：“中游名次摆动最多 3 位；k=5 时摆动缩小。”
- **依据**：`outputs/stability.txt`：S2 的 k=3 与 k=5 都是"名次摆动最大 3 位"，S3 都是 1 位，只有 S1 从 1 位缩到 0 位。三个 shape 的最大摆动量 k=3 → k=5 是 3 位 → 3 位，整体并没有缩小。正确表述应为"仅 S1 的摆动缩小（1→0 位），S2/S3 不变"。
- **置信度**：高（冻结输出可直接核对；`--exp stability` 重放亦复现同样结果）

#### 7. run-all-log.txt 并不是当前 run_all.sh 的"完整 stdout"
- **原文**：“一键复现的完整 stdout”
- **依据**：冻结的 `outputs/run-all-log.txt`（375 行）里找不到 run_all.sh 第 27~51 行"好奇心实验：绕过门直接给投毒内核计时"那一段的任何输出（poison-timing.txt 的"对照对象：S3 = 90×96×64…"等内容不在日志中），且日志末行是"完成：outputs/ 下 9 份真实运行记录"，而当前脚本末行输出"完成：outputs/ 下 10 份真实运行记录"。该日志显然出自旧版脚本（加投毒实验之前），与 README 5.1 文件树"run-all-log.txt ← 一键复现的完整 stdout"及 5.3"本文所有'实际输出'都来自这次运行"的表述不符：读者重跑 `./run_all.sh` 无法复现这份冻结日志。-poison 部分的来源（单独手工运行还是旧版脚本）在仓库内无记录可证。

## 【存疑】
#### 1. "搜索成本随空间大小是乘法爆炸"的标度关系表述不严谨
- **原文**：“但搜索成本随空间大小是**乘法爆炸**”
- **依据**：在固定 shape、固定协议下，搜索成本对候选数量是线性关系（本场即 98 槽 × 每槽 11/25 次调用，search-cost.txt 的外推也是 12,970×11×单次 的线性乘积）；真正按乘法增长的是两件别的事：搜索空间本身随轴数相乘膨胀（D106：257 亿），以及单次执行成本随 shape 按体积增长（(512/96)³ ≈ 152 倍）。把"成本 vs 空间大小"说成乘法爆炸，容易让初学者以为成本对候选数超线性——本教程恰好是教"算账"的一天，这个边界值得写准。建议改为"空间按轴相乘膨胀、单次成本随 shape 增长，两者相乘才是总账"。
- **置信度**：中（字面口径确实错；但结合后文"12,970 × 11 次 × 7.8 s"的三因子乘积，作者可能本意是"多因子相乘"的粗略说法）

#### 2. "真实 MLIR/LLVM 管线编译一个候选是 0.1~10 s 量级"是未经仓库验证的外部断言，且随后的"Σ编译就是 74 s"只对区间中点成立
- **原文**：“真实 MLIR/LLVM 管线编译一个候选是 0.1~10 s 量级，74 个候选的 Σ编译就是 74 s，直接反超今天的全部测量成本。”
- **依据**：该量级作为数量级估计大体符合业界经验（LLVM/MLIR 全优化管线编译单 kernel 常见数百 ms 到数秒），但教程未给出任何测量或引用来源，本环境（无 MLIR/LLVM 工具链参与，纯 Python 迷你 Lowering）也无法验证，属于凭经验给出的外部断言。另外"74 个候选的 Σ编译就是 74 s"隐含取 1 s/候选（区间中点）：若取区间下端 0.1 s/候选，Σ编译 = 7.4 s，并不"直接反超"68.6 s 的测量成本——"因为 0.1~10 s 所以 74 s"这步推理只在区间中点成立。search-cost.txt 的写法（"换成 1 s/候选的真实后端"）把假设显式化了，更严谨；README 这句宜同样显式标出取的是 1 s/候选。
- **置信度**：中（逻辑缺口明确；量级本身无法在本环境核实，不排除但也不背书）

## 【建议】
#### 1. 记录示例只声明了"样本字段略"，实际还删节了 env 与 stats_ms 的字段
- **原文**：“S3 冠军的真实决赛记录长这样（样本字段略）”
- **依据**：与 `results.jsonl` 中该条 S3 决赛记录逐字段对照：真实 env 还有 `cpu_model`、`clock_res_us` 两个字段未出现在示例里；真实 stats_ms 有 11 个字段（n/median/mean/trimmed_mean/min/max/mad/spread_pct/cv_pct/outliers/outlier_idx），示例只列了 7 个。"（样本字段略）"只覆盖 samples_ms 的省略，初学者拿示例对照真实 JSONL 时会误以为字段丢了。建议把括注改成"（样本与部分 env/stats 字段略）"，或补全字段。
- **置信度**：高（逐字段 diff 过）

#### 2. 03-results.svg 中 S3"省 9.96 ms/次"与 search-cost.txt 的 9.97 ms 不一致
- **原文**：“（S1 19.08→15.80、S2 65.12→51.53、S3 42.02→32.06 ms）”
- **依据**：README 与 search-cost.txt 的 S3"每次省 ms"均为 9.97（由未舍入值 42.023 − 32.057 = 9.966 舍入而来），而 03-results.svg 右侧写"快 24%（省 9.96 ms/次）"（图生成脚本用的是已舍入的 42.02 − 32.06 = 9.96）。0.01 ms 的舍入口径差不影响任何结论，但教程要求"图中数字与 outputs/ 一致"，两处口径宜统一为 9.97。
- **置信度**：高（两处数值均可直接查到）

#### 3. 图 1 说明"3 张每 shape 冠军表"易被读成 3 个文件，实际是 1 份表里的 3 个段落
- **原文**：“输出 110 条自包含 JSONL 记录、3 张每 shape 冠军表、1 份三种时间的搜索成本账”
- **依据**：outputs/ 里只有一份 `tune-table.txt`（内含 S1/S2/S3 三个 per-shape 排名段），并列的"1 份三种时间的搜索成本账"（search-cost.txt）却按文件数计。同一句里"3 张"与"1 份"用了两种计数口径，读者对照 5.1 文件树（单一 tune-table.txt）时会产生"还缺两份表"的误解。建议改为"每 shape 一段的冠军表"或"1 份排名表（3 个 shape 段）"。
- **置信度**：高（文件结构可直接核对；严重度低，属表述歧义）
