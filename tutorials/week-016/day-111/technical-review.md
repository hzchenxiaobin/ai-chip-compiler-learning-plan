## 【错误】

#### 1. 前置准备中 D108 全测基线的候选数 18/24/36 与 D108 冻结记录不符
- **原文**：“D108（全测基线 18/24/36 候选与冠军记录）”
- **依据**：D108 的搜索空间是 cube tile {32,64} ∩ 放得下 ＋ 单 tile × 6 顺序 × U∈{1,4}，实测筛选记录为 S1=24、S2=36、S3=38（36 个正则候选＋2 个 no-tail 投毒探针），决赛各 4 条。依据有三：① inputs/results-d108.jsonl 逐条统计（screen 计数 24/36/38，共 110 条）；② D108 outputs/tune-table.txt 三张表的标题行「[S1] …24 个候选筛选」「[S2] …36 个候选筛选」「[S3] …38 个候选筛选」；③ D108 README 原文「共 96 个规则候选；S3 另投 2 个 no-tail 探针，总槽位 98」（96=24+36+36）。任何口径下都没有 18（18 恰好是 D111 自己 32³ 验收空间「1 组合×6×3」的候选数，疑为串写）。正确写法应为 24/36/36（或含投毒的 24/36/38 条筛选记录）。
- **置信度**：高（三方独立证据一致，且可用当日 inputs/results-d108.jsonl 直接复算）。

#### 2. 图 1 把「平均省 ~97%」与「144→9」的个例配对，算术不成立
- **原文**：“模型以 10~35 µs/候选砍掉 93.8~99.6% 的实测”

## 【存疑】

#### 4. “D110 量过模型误差棒有 +10~23%”在 D110 的冻结记录里没有逐字出处
- **原文**：“D110 量过模型误差棒有 +10~23%”
- **依据**：D110 outputs/accuracy.txt 公布的三个口径：误差（预测−实测）/实测 中位数 +9.9%~+13.4%、单候选范围 +4.1%~+23.6%、分家族平均 +6.5%~+18.4%（近对所在的 j 内层 U=1 家族均值 +17.6~+18.4%、上限 +23.6%）；D110 README 正文只写过「中位数 +9.9%~+13.4%」。「+10~23%」量级与方向都对、大致介于中位数与最大值之间，但不等于 D110 任一公布数字的精确切片，作为「D110 量过」的转述过于含糊（pipeline.py select_topk 文档串第 354 行同句复用，两处需同步）。建议改成可溯源写法，例如「分家族均值 +6.5~+18.4%、单候选最高 +23.6%」。
- **置信度**：中（方向与量级正确、论点不受影响；不确定作者是否取了某张表的其他切片，未能找到精确出处）。

## 【建议】

#### 5. run_all.sh 注释、冻结日志末行与 README 的落盘文件数三处不一致（13 / 11 / 12）
- **原文**：“- [ ] `./run_all.sh` 一路全绿，`outputs/` 落盘 12 个文件”
- **依据**：README 与实际目录一致（4 报告＋acceptance＋self-test＋env＋calibration.json/.txt＋tune-results.jsonl＋tune-summary.json＋run-all-log.txt＝12）；但 run_all.sh 第 9~10 行注释写「产出：outputs/ 下 13 个文件」，冻结 run-all-log.txt 末行写「完成：outputs/ 下 11 个条目」（该行 `ls outputs` 执行时日志自身尚未落盘，少数自己）。三处数字互不一致，按图索骥的读者会在 13/12/11 之间困惑；建议统一为 12，并在需要处说明日志自计数差 1 的原因。
- **置信度**：高（三处均可逐字核对）。

#### 6. 图 3 及其图注的 D108 对照行混用筛选段与决赛段读数
- **原文**：“D108 进程 kij 15.80 vs ikj 16.99 冠军互换”
- **依据**：D108 outputs/tune-table.txt S1 表：kij U=1 的 screen=15.81 / final=15.80，ikj U=1 的 screen=16.99 / final=17.07。图注取的 15.80 是 kij 的决赛值、16.99 是 ikj 的筛选段中位数，属于跨段配对；同口径应为 15.80 vs 17.07（决赛）或 15.81 vs 16.99（筛选）。同进程那一侧（ikj 15.70 vs kij 17.10）用的都是决赛值，两行口径不对称。结论（冠军互换、近对差距 ~7%）不受影响，03-results.svg 内同一句也一并如此。
- **置信度**：高（D108 tune-table 两行原文可查）。

#### 7. 图 3 的 S2 提速与时长和冻结报告不一致（3.9× / 9.4 s vs 4.0× / 9,343 ms）
- **原文**：“基线 7,966~36,941 ms，提速 2.8~4.0×”
- **依据**：冻结报告 matmul-bias-s2-96x96x96.txt 末行为「D108 全测基线 Σwall = 36941 ms（跨进程参考）→ 提速 4.0×」，tune-summary.json 记 bench_wall_ms=9343.0（=9.3 s）；gen_images.py 第 327 行把柱常数写死为 ("S2", 36941, 9353)，于是 03-results.svg 印出「S2 本流水线 9.4 s → 3.9×」。36941/9343=3.95（报告按 .1f 四舍五入为 4.0）。属图源常数抄录误差，S1/S3 两根柱与冻结输出一致，仅 S2 漂了 10 ms/0.1×。
- **置信度**：高（冻结输出与 gen_images.py 常数可逐字比对）。

#### 8. “五项记账”在本文口径下只出现 4 个求和项，初学者数不出第五项
- **原文**：“✓ 闸门：160³ tile 五项 = 102400×3 + 640 = 307,840 B > 256 KiB  [307,840 B]”
- **依据**：「五项」源自 D101/D104（D104 前置准备：「D101 的五项家当记账（A/B/C/bias/staging；×2 只加在 DMA 流入项……）」，第 5 项 staging 以 A/B 的 ×2 体现）。D111 的可测口径是 fp32·single·无 staging，tile_bytes 只算 A+B+C+bias 四项，本行等式右边也只有 4 个加数，「五项＝4 个加数」字面上对不齐。计算本身全部复核无误（128×160×160=266,880、超 4,736 B、160³=307,840、48³=27,840、90×96×64=82,560 均对）。建议在 5.2 ② 的「D104 五项：A+B+C+bias」注释处补半句「staging 项在本口径恒为 0，故只见 4 个加数」。
- **置信度**：高（口径可溯源到 D104/D101，属表述问题而非计算错误）。

#### 9. 现有 SVG 存在非法 text-anchor 属性值（"True"/"False"），数值列对位漂移
- **原文**：“gen_images.py         # 生成 3 张图（固定数字，全部来自真实运行）”
- **依据**：02-mechanism.svg 中有 9 处 text-anchor="True" / "False"（如名次列的 1/5/9/13/17 与 S5 表的 15.70/17.10 等读数）。SVG 规范中 text-anchor 的合法值只有 start/middle/end，非法值按无效属性回退为默认 start，这些数值便从表头「居中」退化为左对齐、与列头错位。根源是 gen_images.py 若干调用点把本想传给 bold 的布尔值按位置参数落在了 anchor 形参上。图仍可解析、可读（XML 合法、tutorial_tools check 通过），不影响结论，但与「数值列对位」的排版意图不符。
- **置信度**：高（SVG 文本可逐处点验；02-mechanism.svg 计 True 2 处、False 7 处）。
