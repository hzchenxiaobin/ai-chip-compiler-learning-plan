## 【错误】

#### 1. 主表输出"读法"把慢尾偏态方向写反（"左偏"应为"右偏"）
- **原文**：“**记录一：主表**（`outputs/bench-table.txt`，实际输出的核心）：”
- **依据**：该行交付的冻结输出 outputs/bench-table.txt 第 23 行（读法脚注，由 bench.py:361 生成）写着"mean−med%>0 说明慢尾在拉均值（性能样本天然左偏）"。慢尾＝偶发大值＝长尾在数轴右侧，均值被拉高、mean>median，这正是右偏（正偏态）的定义；同一句前半句描述的就是右偏特征，后半句却写"左偏"，自相矛盾。耗时/时延类样本通常呈右偏分布也是通行结论。错误同时位于代码与冻结输出，按校对纪律本文不改，仅记录：后续修复需同步改 bench.py:361 并重新生成输出。
- **置信度**：高。偏态命名是教科书事实；错误位置（bench.py:361、bench-table.txt:23）可直接核对。

#### 2. `write_jsonl` 宣称"追加式落盘"，实现却是截断覆盖写
- **原文**：“JSONL 边测边写（断点续跑的地基）”
- **依据**：bench.py:292-296 的 `write_jsonl` 文档字符串写"一行一条记录追加式落盘——D108 的 auto-tuning 边测边写就用它"，但实现是 `open(path, "w")`——每次调用整文件截断重写，不是追加（"a" 模式）。README 第 9 节与该 docstring 宣传的"边测边写／断点续跑"语义均不成立：若按宣传方式逐条调用，每次都会抹掉此前写入的记录，断点续跑恰恰丢数据。今天的冻结输出未受影响（每个文件只整批写一次），但这是交付工具里名实不符的 API 契约，D108 复用时会踩中。
- **置信度**：高。代码行为可直接核对（bench.py:294 为 `open(path, "w")`）。

#### 3. "分配器第一次给出热页"把首次分配的成本方向写反
- **原文**：“分配器第一次给出热页”
- **依据**：首次分配／首次触碰拿到的是冷页，其代价正是首次写入缺页——同句括号里的 C++ 对照写的就是"C 矩阵 256 页的首次写入缺页"（D97 原文可查证）；"热页"（已映射、可复用）是预热之后才出现的状态。把冷启动成本写成"第一次给出热页"与同句括号内容自相矛盾，初学者会得出"首次分配反而拿到热页"的错误印象。应改为"分配器第一次给出的冷页要付首次写入缺页"一类的表述。
- **置信度**：中。方向可确定判反；作者原意（首次分配触发缺页、复用才变热）从上下文可恢复，影响限于单句。

## 【存疑】

#### 1. "D97 的 4/6 翻车发生在忙时段"没有 D97 的证据支撑
- **原文**：“（D97 的 4/6 翻车发生在忙时段；今天长跑实验里 23 个离群、最远 +48.5%，单样本落在离群段就是另一副长相）”
- **依据**：D97 教程全文无"机器忙"的记载；其对 run2 首样本系统性偏慢的解释是"即使预热过，刚进入计分阶段时系统状态仍在'过渡'"，对 5.9% 跨运行漂移的解释是调度／中断／缓存这类锁不掉的 run 级波动。把 4/6 排名翻车归因为"忙时段"是 D107 的推测而非 D97 的实测记录；冻结输出 outliers.txt 第 37 行"是忙时段证据"同源。同句的推理（单样本可能恰好落在离群段）本身成立。建议改为"D97 的 4/6 翻车发生在单样本口径（首样本系统性偏慢）"或删去归因。
- **置信度**：中。D97 原文可查证（无"忙"字、归因为过渡态／run 级波动）；不排除作者另有未落盘的机器状态记录。

#### 2. "range 对象与行提升变量第一次进各自缓存"不是 CPython 的真实机制
- **原文**：“`range` 对象与行提升变量第一次进各自缓存”
- **依据**：CPython 3.11 里局部变量访问是帧内快局部数组的纯下标读写，`range` 对象每次执行 `for … in range(…)` 都新建，两者都没有"缓存"可"进"。3.11 真实存在的首跑变慢机制是 PEP 659 自适应特化（quickening）：函数执行若干次后指令才被改写为特化形态——本机 Python 3.11.4 用 `dis.dis(f, adaptive=True)` 验证可见 BINARY_SUBSCR_LIST_INT、BINARY_OP_ADD_INT、STORE_FAST__LOAD_FAST 等。预热让首跑更快这个方向是对的，但机制描述对不上真实实现，建议改写为"字节码特化（quickening）在最初若干次执行后才生效"。
- **置信度**：中高。LOAD_FAST 无缓存、range 不缓存可从字节码语义确认；特化行为已在本机 3.11.4 上验证。

#### 3. "中位数对哪种样本量都免疫"与 5.4"n=3 时免疫变弱"两处口径互相打架
- **原文**：“能把均值拖走约 +16.2%；中位数对哪种样本量都免疫。样本少，更要中位数。”
- **依据**：单个离群拉不动中位数这一性质对任何 n≥3 都成立（中位数崩溃点 50%，与样本数无关），引文在"单离群"语境下正确；但 5.4 对照 A 又写"n=3 时 median 的'免疫'变弱（第 2 大的样本就是中位数）"，指的是中位数作为估计量的抽样波动随 n 减小而增大——两种"免疫"不是同一概念。并置出现容易让初学者以为 n=3 时一个慢尾就能拉动中位数（实际 n=3 时单个慢离群只会成为最大值，中位数仍是中间样本）。建议统一口径：拉不动是崩溃点意义，变弱的是估计量方差。
- **置信度**：中。统计事实明确（崩溃点、次序统计量方差），判为口径混淆需核实而非硬错误，因为两句各自都能找到成立语境。

## 【建议】

#### 1. "逐位比对（==）"中"逐位"强于 `==` 的真实语义
- **原文**：“内核跑一遍，与参考实现**逐位**比对（`==`，不是误差阈值）”
- **依据**：Python 的 `==` 是数值相等，不是位模式相等（−0.0 == 0.0 为 True，NaN != NaN）。本教程里参考实现与被测内核对每个 C[i][j] 执行同一串 IEEE 双精度运算（乘、加在 CPython 里是两条独立字节码，无 FMA 收缩，已用 dis 核对 BINARY_OP 5/13），结果确实位模式一致，结论不受影响；但门的判定机制严格说是"精确相等"，"逐位"是解释它能成立的原因，不是 `==` 的语义。建议表述为"精确相等（==）；因为累加序列相同，位模式一致"。
- **置信度**：高。`==` 语义确定；对本教程结论无影响，属措辞精确性。

#### 2. 图 3 把"展开省循环开销"与"U=8 机器码 3.2×"并置，易被读成 3.2× 是收益
- **原文**：“D96 在 C++ 里量到"展开省循环开销"，但 CPython 里 `Ci[v3 + u]` 每条语句多付一次加法＋下标”
- **依据**：D96 的 3.2× 是体积账（U=8 机器码 372 条 vs 基线 116 条），是展开的代价而非收益；D96 标量模式实测"展开 j 快 ~17%、展开 k 几乎白干"。03-results.svg 翻车现场①卡片写"D96 的 C++ 账：展开省循环开销（U=8 机器码 3.2×）"，未标注 3.2× 是体积，读者容易当成加速比。建议图内补"体积"二字（README 正文无此问题）。
- **置信度**：中。图内文字，不改不影响正文正确性；D96 原文可查证（372/116 条、~17%）。

#### 3. "5 种 × 展开 U∈{1,8} × 单 tile 对照"的乘号易被误读为笛卡尔积
- **原文**：“7 个真实配置（6 种循环顺序里的 5 种 × 展开 U∈{1,8} × 单 tile 对照）”
- **依据**：按乘法读是 5×2×1=10 个，与"7 个"矛盾；实际构成是 5 个 U=1 配置＋ikj 的 U=8 变体＋96³ 单 tile 对照共 7 个（见 5.3 主表）。建议改为"5 种顺序（U=1）＋ikj 的 U=8 变体＋96³ 单 tile 对照"式列举。
- **置信度**：高。构成与主表可直接核对。

#### 4. 5.4 对照 C 的 tolerance 策略无法用 CLI 复现
- **原文**：“`Protocol(policy="tolerance", tol=1e-6)`（或 `--gc-on` 换包含口径）再跑一次 bench 模式”
- **依据**：bench.py 的 argparse 只有 --exp/--outdir/--config/--warmup/--repeats/--gc-on/--shape，没有 policy/tol 开关（已运行核对）；换 tolerance 门必须 import bench 用 Python API 调 bench_one，"再跑一次 bench 模式"对 tolerance 这半句按 CLI 走不通，--gc-on 那半句可行。建议注明"tolerance 走 Python API"或补 CLI 参数。
- **置信度**：高。CLI 定义可核对；不影响正确性，属可执行性。

#### 5. "三个进程"中位数并列中 57.91 的口径与另两点不同
- **原文**：“同一配置 `32³ ikj U=1` 在三个进程里的中位数分别是 57.36（主表）、57.91（长跑）、62.30（本实验）”
- **依据**：57.36 与 62.30 都是 gc=off、repeats=21 的同协议读数，8.6% 的漂移结论由这两个点支撑（成立）；57.91 出自长跑（gc=on、repeats=201，见 outliers.txt 协议行）。把三种口径的读数并列成"同配置跨进程"而不加注，读者逐条对协议时会困惑。建议补一句"长跑点是 gc=on／repeats=201 口径"。
- **置信度**：高。三个数字与各自协议均已核对；问题仅在呈现完整性。
