## 【错误】
#### 1. “F∘F 不能合并成单个 reshape”与 reshape 语义矛盾（3.3 节）
- **原文**：“`C∘F`、`F∘C`、甚至 `F∘F` 都不能合并成单个 reshape（现场二的数值终审）”
- **依据**：`order='F'` 的 reshape 是 **F 线性顺序上的恒等映射**（numpy 语义：按 F 序读入、按 F 序写出），两跳复合仍是 F 线性恒等，因此 `Reshape_F(Reshape_F(x, s1), s2) == Reshape_F(x, s2)`。本机 numpy 1.26.4 实测 36 组 (s1, s2) 形状组合（6×6）全部相等；教程自己的终审也把“单个 F 序 reshape”当作合法候选（`C∘F == 单个F？ False` 的对照项），故“F∘F 不能合并成单个 reshape”自相矛盾。所引“现场二的数值终审”只测了 `C∘F` 一个方向（`outputs/reshape_merge_lab.txt` 第 6 段），并没有 F∘F 的证据。mini 的 P2 拒绝 F∘F 只是保守选择（漏掉一个合法优化），不构成“数学上不可能”。C∘F、F∘C 在一般形状下确实不可合并（本机抽查未见反例），但注意两个平凡反例存在：`s1 == shape(x)` 时内层是恒等（C∘F 退化为单个 F 序 reshape）、`s2 == s1` 时外层是恒等（退化为单个 C 序 reshape），表述应限定“一般情况”。
- **置信度**：高（36/36 数值验证 + 语义推导；C∘F/F∘C 的两个平凡反例也已实测确认）。

#### 2. 第 6 节“错误 4”的理由把 F∘F 也归入“不保持读入=写出顺序”
- **原文**：“`C∘F`、`F∘C`、`F∘F` 都不保持「读进来的顺序 == 写出去的顺序」这一合并前提”
- **依据**：F 序 reshape 恰恰**保持**「读进来的顺序 == 写出去的顺序」——它按 F 序读、按 F 序写，F 线性顺序在单跳内不变（这正是 `Reshape_F(x, shape(x))` 是恒等、B3 测试通过的原因）。不保持的是 **C 线性**顺序。F∘F 两跳都保持 F 线性顺序，合并前提成立（可合并为单个 F 序 reshape，见错误 1）。该句把“F 序不是 C 线性恒等”错误地推广成“F 序不保持自身的读写顺序”，与教程第 3.2 节“同形状恒等与 order 无关——读 F 序写 F 序，元素各回原位”的表述也直接冲突。
- **置信度**：高。

#### 3. 第 5.3 节混 order 终审的“单个 F 序 reshape”数值与冻结输出不符
- **原文**：“单个 F 序 reshape：[0, 6, 12, 18, 1, 7, 13, 19]”
- **依据**：冻结输出 `code/outputs/reshape_merge_lab.txt` 第 6 段实际打印的是“单个 F 序 reshape：[0, 12, 4, 16, 8, 20, 1, 13]”，且本机复跑逐字节一致。数值上 `np.reshape(B(2,3,4), (24,), order='F')[:8] == [0, 12, 4, 16, 8, 20, 1, 13]`（B 按 F 序读，i 维最快：(0,0,0)=0,(1,0,0)=12,(0,1,0)=4,(1,1,0)=16,…）。README 写的 `[0, 6, 12, 18, 1, 7, 13, 19]` 实为 **(4,6) 中间形状**的 F 序读出值，不是本例 `(6,4)` 的——引用自己的冻结输出时抄错了行，读者对拍会发现“对不上”。同块其余行（C∘F 前 8 个、单个 C 序、两个 False）均与冻结输出一致。
- **置信度**：高（冻结输出 + 本机复跑 + 手算三方一致）。

#### 4. “PyTorch 的 0（保持该维）”张冠李戴——这是 ONNX Reshape 的语义
- **原文**：“真实框架还有 `-1`（推断一维）和 PyTorch 的 `0`（保持该维）语法，mini 不做——它只是 E1/E2 的预处理糖（练习 2 会把它补上）”
- **依据**：“形状里出现 0 表示保持输入该维”是 **ONNX Reshape** 的语义（ONNX 官方文档：”A dimension could also be 0, in which case the actual dimension value is unchanged (i.e. taken from the input tensor)“）。PyTorch 的 `reshape`/`view` **不支持** 0：本机 torch 2.7.1 实测 `torch.arange(24).reshape(2,3,4)` 上 `reshape(0, -1)`、`view(0, -1)`、`reshape(2, 0)`、`view(2, 0, 4)` 全部抛 `RuntimeError: shape '[...]' is invalid for input of size 24`（0 被当作真实维度参与 numel 检查）；`-1` 推断则正常。numpy 同样只支持 `-1`。练习 2 仿造的“预处理糖”应改述为 ONNX 语义，否则读者在 PyTorch 里试 `0` 会直接报错。
- **置信度**：高（本机 torch 2.7.1 实测 + ONNX 官方文档原文；未逐一验证更老的 torch 版本，但 reshape/view 对 0 的拒绝行为在各版本长期稳定）。

#### 5. “只用 P2 跑与双 Pattern 结果一致（测试 G3 的镜像）”——当天没有这个实测，且结论不成立
- **原文**：“今天实测「只用 P2 跑」与「双 Pattern」结果一致（测试 G3 的镜像）”
- **依据**：①当天主实验与 `test_reshape_merge.py` **没有任何“只用 P2 跑”的实验或测试**——全部用 `run_passes(g, TWO_PATTERNS)`；测试 G3 是“唯一使用者时激进版与保守版 IR 相同”，比较对象是激进版 vs 保守版，与 P2-only vs 双 Pattern 无关（“镜像”的说法不成立；P2-only 对照是**第 65 天**测试 C3 的内容）。②结论本身为假：本机单独运行 `merge_consecutive_reshape`——场景 A 的图（恒等 op `%r` 被 `%a`、`%b` 两处使用）applied=0、3 个 op 原样保留，而双 Pattern 得 2 个 op；单个恒等跳（B1 图）P2-only 剩 1 个 op，双 Pattern 为 0。原因：P2 只能消除“链合成恒等”，**独立的恒等 op**（无链伙伴，或恒等值被多处使用）只有 P1 能删——“P1 是 P2 的特例”仅对链形态成立。
- **置信度**：高（测试文件通读 + 本机直接执行两个反例图）。

#### 6. 场景 A 的 `%r` 使用处数写成 3——冻结输出是 2
- **原文**：“A 的 `%r` 有 3 处使用却照样消除（P1 删的是 op 自身）”
- **依据**：冻结输出 `outputs/reshape_merge_lab.txt` 场景 A 明确打印“`%r 的使用者数 = 2（%a、%b 各一）——P1 不看这个`”，返回值是 `[%a, %b]`，`%r` 未被 return；README 第 5.3 节场景 A 的原文引用（“两个消费者使用”）也写的是 2。“3 处使用”是测试 B2 的图（2 个 op + 1 个 return）。同一错误还出现在第 6 节错误 2（“场景 A 那种 `%r` 被 3 处使用的图”，第 416 行）和 `images/03-before-after.svg`（“场景 A：恒等单跳（结果 3 处使用）”）。
- **置信度**：高（与冻结输出、README 自己的场景 A 引用两方对照）。

#### 7. 图 3 SVG 里场景 A 优化后 IR 的类型串笔误：`4xf6xf32`
- **原文**：“五行分别是场景 A/B/C/D/E 的真实 mini IR 文本（左列优化前，右列优化后）”

- **置信度**：高。

## 【存疑】
#### 1. “非连续输入的第一跳被迫拷贝一次”是过度推广
- **原文**：“非连续输入（如 `B.T`）的第一跳被迫拷贝一次，之后的跳都是视图——**合并成一步拷贝次数完全相同**”
- **依据**：对实测的 `B.T` 例子该结论成立（本机复现：`B.T→(6,4)` 拷贝、二跳视图、合并一步值相等，与冻结输出一致）。但作为一般规律过于绝对：numpy 的 reshape 在**非连续**布局下仍可能返回视图——本机实测反例 `q = np.arange(24).reshape(4,6)[:, :2]`（非连续，strides (6,1)），`q.reshape(2,2,2)` 是视图（`np.shares_memory == True`，来自维度可拆分），此时链里的拷贝发生在**第二跳**（`(2,2,2)→(2,4)` 才拷贝）而非第一跳——第 9 节总结的“至多第一跳拷贝一次”同样被此例推翻（唯一的一次拷贝可以在后续跳）。同句“连续输入的整条链全是视图”对 C 序 reshape 成立。“合并成一步拷贝次数相同”在测过的例子上成立，但对任意 C 序链是否恒成立未做完整证明（若链全为视图，直接合并是否必为视图未证）。建议把表述限定在“B.T 这类布局”或加“通常/可能”限定。
- **置信度**：中高（反例已实测；“拷贝次数相同”的一般性既未证实也未证伪）。

## 【建议】
#### 1. `merge_consecutive_reshape` 的防御性自检顺序与“就不动”注释不符
- **原文**：“continue       # 产物非法就不动（防御，正常构造不出非法）”
- **依据**：代码中 `outer.input_id, outer.in_shape = inner.input_id, inner.in_shape` 的改写发生在 `verify_reshape(...)` 检查**之前**；若校验失败走 `continue`，`outer` 已被改写而 `inner` 未删除，图并非“不动”（语义上仍是这次合并本身，但 IR 留下了未被删除的死中间值）。由于链上 numel 守恒、形状都合法，该分支在当前构造下不可达，无正确性影响；但注释（及 README 第 5.2 节“③防御性自检——合并产物再过一遍三关 Verifier”的叙述）与实际控制流不符。建议先构造并校验 `(in_shape, out_shape)`、通过后再改写 `outer`，或把注释改为“校验失败时保留改写结果但不删 inner”。
- **置信度**：高（控制流可直接读出；不可达性由“链上每个 op 单独合法 ⟹ numel 传递相等”保证）。

#### 2. `verify_reshape` 代码 docstring 的练习编号指向错误
- **原文**：“**给 mini 加 `-1` 推断**：仿真实框架，允许 `out_shape` 里出现至多一个 `-1`”
- **依据**：`code/reshape_merge_lab.py` 中 `verify_reshape` 的 docstring 写“真实框架还有 -1（推断一维）等语法，mini 不做（练习 3 扩展）”，但当天必做练习里 `-1` 推断是**练习 2**，练习 3 是“构造多使用者反例”；README 第 3.1 节（“练习 2 会把它补上”）指向正确。从代码 docstring 跳转的读者会被引到错误的练习。属交叉引用失配，不影响正确性。
- **置信度**：高。
