## 【错误】

#### 1. 「ui8 根本不是合法类型」——ui8 是 MLIR builtin 的合法整数类型，被拒的是 arith 算子
- **原文**：“它的整数类型是 **signless** 的（`ui8` 根本不是合法类型，实测报 `must be signless-integer-or-float-like`），符号在**操作**（`extsi`/`extui`）里而不在类型里”
- **依据**：用教程同一台 mlir-opt（Ubuntu LLVM 18.1.8）实测 `func.func @ui8_arg(%x: ui8) -> ui8 { return %x : ui8 }`，解析、回显、`--canonicalize` 全部通过（exit=0）——`ui8` 是 builtin `IntegerType` 的无符号变体（`i8`/`si8`/`ui8` 三种符号性都是合法类型，`si8` 同样可解析）。报错的真实来源是 arith 算子的操作数约束：`arith.bitcast`、`arith.addi` 等要求 signless 整数（对 `ui8` 上的 `arith.addi` 实测同样报 "must be signless-integer-like"），报错文本的主语本来就是 op（"'arith.bitcast' op result #0 must be…"）而不是类型不存在。所以「ui8 根本不是合法类型」「ui8 类型不存在」是错误结论；本句的后半段「符号在操作（extsi/extui）里」对 arith 是成立的，正确的说法是「builtin 整数有 i8/si8/ui8 三种符号变体，但 arith 的算子只接受 signless 整数」。同一错误还出现在 5.3 节⑧的对照读法、第 8 节验收清单（“ui8 类型不存在”）、`cast_elim_lab.py`/`test_cast_elim.py` 的注释与测试描述，以及 `02-mechanism.svg`（“ui8 类型不存在”）和 `04-verdicts.svg`（“ui8 不存在（signless）”）的标注中（按本次约定不改代码与已有图片，仅在此报告）。
- **置信度**：高（本机直接复现；与报错文本自身的主语一致）。

#### 2. 场景 E 的四个 op 里没有 widen，f32→f16 被标成「精度扩展」
- **原文**：“场景 E（四类反例单跳：widen/narrow/signflip/domainflip → 全保留）：”
- **依据**：场景 E 实际构造的四个 op 是 `f32→f16`、`f32→bf16`、`f32→i32`、`i8→ui8`，按当天 `classify_cast`（本机复核）分别是 narrow／narrow／domainflip／signflip——图里**没有任何 widen op**（widen 的例子应形如 `f16→f32`），「四类反例」实际只覆盖三类。且冻结输出与 README 引用的行“四个 op 分别是精度扩展（f16）、精度缩减（bf16）…”把 `%w`（f32→f16）标成精度扩展，与 3.2 节判定表“f32 → f16 精度缩减（narrow）”直接矛盾（f32→bf16 同为 narrow）。测试 E1 只检查「4→4 零应用且数值不变」，不校验分类，因此拦不住这个错标；`03-before-after.svg` 场景 E 的说明（“扩展/缩减/域翻转/符号语义一个不动”）继承了同一错误。要真正凑齐四类，`%w` 应改为 `f16→f32` 之类的 widen 跳（按约定未改代码，仅报告）。
- **置信度**：高（`classify_cast` 逐 op 复核 ＋ 教程自己的 17 对判定表对照）。

#### 3. 「本实验随机对拍里实测撞到过负数转 ui8 的警告」——当前代码不可能发生
- **原文**：“负浮点转无符号整数是 C 的未定义行为（本实验随机对拍里实测撞到过：`i32→i8` 回绕出负数再转 ui8，numpy 直接警告）”
- **依据**：随机对拍的值域被显式压到非负有界（int 0..127 / float 0.125..7.875，见 5.3 节正文与 `cast_elim_lab.py` 第 5 节的打印）：链上 int→int 保序不回绕（值 ≤127 放得进 i8）、float→float/bf16 截断不产生负数、float→int 结果落在 0..8——任何中间值都不可能为负或超过 127，因此 `i32→i8` 回绕出负数、再进 ui8 触发 numpy 警告在**当前交付的代码里不可能发生**。本机复跑同种子（67）的 300 组随机链并捕获全部 warnings：无一负值、无任何警告。而且 5.3 节自己写明「值域取非负有界……回绕与负值的翻车现场由判定表和场景 F 显式承担」，与「实测撞到过」互相矛盾——这句应是早期未限值域版本的开发遗留，把它当作当前实验的实测事实陈述是错的。
- **置信度**：高（300 组复跑 ＋ 值域推导 ＋ 教程内部矛盾三重证据）。

#### 4. 「cast 跨类型时是有损变换」被 widen 类反例推翻
- **原文**：“转置/reshape 是形状世界的**无损重排**，cast 跨类型时是**有损变换**”
- **依据**：widen 类全部跨类型且无损：`f16→f32`（教程自己的 3.2 节表：“值集扩大、信息不丢”，且第 6 节实测 1003 个值含 ±inf/NaN 全部原样）、`i8→i32`／`ui8→i32`（符号/零扩展逐值保真）。「跨类型 ⇒ 有损」与当天五分类直接矛盾。准确的说法是「跨类型不再保证恒等：narrow/domainflip 可能改数值、signflip/reformat 改解释、widen 无损但也不是恒等」——判据要保守的原因是「不再保证恒等」，不是「必然有损」。
- **置信度**：高（反例全部来自教程自己的判定表与实测）。

## 【存疑】

#### 1. 「整数回环有折叠、浮点回环没有」是 LLVM 18.1.8 的快照结论；19.x 起「有损方向一律保留」不再无条件成立
- **原文**：“整数回环有折叠、浮点回环没有——stock 的规则是拼图，不是原则。”
- **依据**：18.1.8 本机复现成立，且与官方源码一致：llvm `release/18.x` 的 `ArithOps.cpp` 中 `TruncIOp::fold` 显式实现了 `trunci(sexti/zexti(a)) → a`（同宽时，⑤ 折叠的机制即此，`trunci∘extui` 同样折叠），而 `TruncFOp::fold` 只做常量折叠——不对称是 18 的结构性事实。但查 `release/19.x` 同一文件：`ExtFOp::fold` 新增了「两个 op 都带 `fastmath = contract` 时 `extf(truncf(x)) → x`」的折叠——即新版本里**有损方向**（`f32→f16→f32`，即 ④ 的形态）在显式允许精度松弛的标志下会被 stock 折叠；`TruncFOp::fold` 在 19.x 仍无 `truncf∘extf` 规则（③ 的结论目前仍稳）。因此 README 5.3 节「④⑥ 有损方向一律原样保留（正确）」与第 6 节「`extf∘truncf` 永远不许」的绝对表述，在 19+＋contract 标志下不再无条件为真（无 fastmath 标志时行为与 18 一致，教程的测试正是无标志形态，结论在其声明的版本与配置下没有问题）。另外 ① 的同型 `extf` 报错文本在新版本已改为 "result type must be wider than operand type"（18.1.8 是 "cast incompatible"，源码中 `verifyExtOp` 要求严格更宽），换版本复跑会看到不同文案。本机只装了 llvm-18，19+ 的行为依据官方源码而非本机执行；contract 折叠引入的确切小版本未逐一考证。
- **置信度**：高（18.1.8 本机复现 ＋ 18.x/19.x 官方源码比对；「哪个小版本引入 contract 折叠」不确定）。

## 【建议】

#### 1. f32 的「尾数 24 位」与 f16/bf16 的「10/7 位」在同一张表里用了两种口径
- **原文**：“f32     32   float   1+8+23（尾数 24 位）”
- **依据**：f32 的「24」把隐含的前导 1 计入（存储位是 23），而 f16/bf16 的「10」「7」只数存储位（有效位分别是 11、8）。两种说法各自都常见，但同一张表混用会让初学者把 f32→f16 的精度损失算成 24−10=14 位（实际有效位损失是 24−11=13 位）。建议统一为存储位（23/10/7）或有效位（24/11/8）并加半句「含隐含 1」；3.3 节「尾数 24 位裁成 10 位」与现场二「f16（10 位尾数）」沿用了同一混用口径。本次新增的图 3 已按「存储位 ＋ 注明含隐含 1」标注，供修订时参考。
- **置信度**：高（口径不一致本身确定；对初学者的误导程度是判断）。

#### 2. 「arith 把 cast 按方向拆成 extf/truncf/extsi/extui/trunci」漏了域翻转一族
- **原文**：“arith 把 cast 按方向拆成 extf/truncf/extsi/extui/trunci”
- **依据**：arith 的 cast 家族还包括 `sitofp`/`uitofp`/`fptosi`/`fptoui`（浮点↔整数，正是五分类里 domainflip 的 arith 对应物）；本机实测 `sitofp∘fptosi`（i32→f32→i32）交 `--canonicalize` 同样原样保留 2 个 op。当前列举容易让读者以为 domainflip 在 arith 里没有对应 op；补全家族清单也更能支撑「stock 是拼图」的结论（域翻转回环同样没有折叠规则）。
- **置信度**：高（MLIR 官方 op 清单 ＋ 本机实测）。

#### 3. 选做 (c) 的提示把「舍入模式」说成决定性因素，与子集判据无关
- **原文**：“（提示：bf16 的舍入模式——截断还是就近——决定答案；今天 mini 的仿真选了截断。）”
- **依据**：该问的判据是「f32 的值集是否 ⊆ bf16」（回环 T→W→T 安全当 T ⊆ W，选做 (a) 自己的定义）——无论截断还是就近舍入，f32 都不是 bf16 值集的子集：本机计算截断得 0.099609375、就近舍入得 0.10009765625（0x3DCD0000），都不是 0.1，即两种舍入模式下答案都是「不该在表里」；舍入模式只影响「具体丢成哪个值」。提示中的因果链会把读者引去证一个不影响结论的分支，建议改成「舍入模式只决定丢成什么值；f32 ⊄ bf16 才是不进表的原因」。
- **置信度**：中高（两个数值均已验证；对出题意图的解读存在一定不确定度）。
