 搜索成本账：编译时间 / 执行时间 / 搜索成本，三种时间分开记
==============================================================================
 一、总账（本次真实运行，含断点续跑各段）
   候选槽 98 个（筛选段）+ 决赛 12 个；调优分 2 段执行，进程墙钟合计 68.7 s
   编译：74 次 / 缓存命中 36 次 / Σcompile = 22.9 ms
   （断点续跑的代价：编译缓存不跨进程，第二段要重新编译它新测的候选）
   筛选段 bench Σwall = 57.1 s；决赛段 bench Σwall = 11.5 s
   内核调用：按记录逐条数 1,358 次（分段记账合计 1,358 次，两者应一致）
   差额 0.1 s = 循环开销 + 报告/IO——诚实不是免费的：
   参考实现每个候选都要跑一遍给门对答案，已含在 bench wall 里

 二、三种时间（今天的核心概念，数字全部实测）
   编译时间：平均 0.31 ms/候选（一次性；本环境是迷你 Lowering，
              真实 MLIR/LLVM 管线是 0.1~10 s/候选量级，这一格会反超测量）
   执行时间：决赛中位数 15.8~65.1 ms/次（每次生产调用都付；排名口径）
   搜索成本：68.7 s（本场一次性）= Σ编译(23 ms) + Σ测量(68.6 s) + 记账
   本环境 编译:测量 ≈ 1 : 2,990——纯 Python 里编译几乎白送；
   换成 1 s/候选的真实后端，Σ编译 = 74 s 直接反超 Σ测量：循环结构不变，账全变

 三、摊销账：搜索成本什么时候回本
   shape      缺省 ms     冠军 ms     每次省 ms       搜索成本分摊 s      回本调用数 N
------------------------------------------------------------------------------
   S1         19.08     15.80       3.28            8.0        2,433
   S2         65.12     51.53      13.59           37.0        2,720
   S3         42.02     32.06       9.97           23.7        2,377
------------------------------------------------------------------------------
   N_break-even = 搜索成本分摊 ÷ 每次省下的执行时间；
   结论：每 shape 约 2,377~2,720 次调用回本——
   每天跑一次的脚本回不了本；推理服务百万次/天，几分钟就回本。
   搜索成本是『一次性投资』，执行时间是『每次都付』——两种时间不能混。

 四、把循环放大到 D106 全空间会怎样（外推估算，非实测）
   本场筛选段 98 个候选花 57.1 s（小 shape、纯 Python）
   D106 的 12,970 个候选是为 512³ 生成的：96³ 冠军 52 ms × (512/96)³ ≈ 7.8 s/次（量级估算）
   全空间按 v0.1 筛选协议 ≈ 12,970×11×7.8 s ≈ 13 天——
   而且这是下界：tile 外壳和慢顺序让多数候选更慢。
   这就是为什么真实调优器必须有 cost model 预剪（D110）和分层搜索：
   循环本身今天已经立起来了，『测得起』是另一门功课（D106 的老警告）。
