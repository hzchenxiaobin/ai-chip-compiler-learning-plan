## 【错误】

#### 1. tile=128 的并发成因解释与当天复用的 cost model 实现相矛盾
- **原文**：“**翻车的是并发**（累加器 128×128×4 = 65,536 B 恰好占满 64 KiB 寄存器堆，并发 = 65,536 ÷ 65,536 = 1 < 3）”
- **依据**：当天主实验复用的 `day-076/code/cost_model.py` 中 `_resource_side()` 计算 R4（tile=128）的寄存器占用是 `reg_demand = 128×128×4 + 64 lanes×4 = 65,792 B`（累加器＋bias 在飞），随后 `reg_tiles = max(1, 65536 // 65792) = max(1, 0) = 1`——整除结果本来就是 0，并发 1 来自 `max(1, …)` 的下限钳位，而不是「65,536 ÷ 65,536」；占用也并非「恰好占满」，而是超出 64 KiB 达 256 B。D75/D76 案例表 R4 行写的都是「占用 65,792 B 超过寄存器堆」，D73 教程的常见错误一节更明确写了「当 reg_demand > regfile（tile 128 的 65,792 B 超 64 KiB）时整除得 0」。我在本机复算 65536//65792 = 0 与源码一致。判决结果（refuse、并发 1、评分不变）本身正确，错的是对并发 1 从何而来的解释。
- **置信度**：高。已读 cost_model.py 源码逐行核对并独立复算；当天冻结输出由我复跑逐位一致。

#### 2. §5.4 引用的 4a 检查行与冻结输出不一致，「真实运行结果」被静默改写
- **原文**：“[PASS] 4a tile 只动「更快」列：评分不变（ΔB 与 tile 无关）、并发 3→1、”
- **依据**：README §5.3 开头声明「以下输出为 2026-11-13 在本机的真实运行结果（……完整输出在 `code/outputs/`）」，但冻结输出 `code/outputs/week11_review.txt` 第 72 行（以及我在同环境复跑的结果）该行是「[PASS] 4a tile 只动「更快」列：评分不变（ΔB 与 tile 无关）、并发 4→1、auto fuse→refuse；合法列与数值列纹丝不动」。README 引用块把「4→1」改成了「3→1」并重新折行——引用内容与它自称的真实输出不符。补充：代码里 4a 的检查名（week11_review.py:317）写的就是「并发 4→1」，其中 4 是 P0（不融合）的并发，与本处 tile64→tile128 的对比口径（P3 并发 3→1）不符；语义上 README 的「3→1」是对的，但正确做法是保持引用逐字一致并另行说明代码标签的口径问题，而不是改写“真实输出”。
- **置信度**：高。复跑输出与冻结输出逐字节一致，唯独 README 引用不同。

#### 3. 「epilogue 2/K = 3.125%」把 D73 的指令复杂度增量误标进活集（资源）账
- **原文**：“账三 · 资源：活集 16,384 → 16,640 B（＋256 B bias 在飞，epilogue 2/K = 3.125%）”
- **依据**：D73 教程对 2/K 的定义是**指令复杂度**轴的增量：「每个输出元素 MatMul 需要 K 条 MAC 指令，epilogue（bias add + relu max）只要 2 条，增量 = 2/K——K=64 时 3.1%」。而资源轴的活集增量是 bias 在飞 256 B：占累加器 16,384 的 1.5625%（恰好等于 1/K）、占 16,640 的 1.538%。把 2/K = 3.125% 放进「账三 · 资源」行并紧跟「＋256 B bias 在飞」，读者会得出「活集涨了 3.125%」的错误结论（实际 1.5625%）。冻结输出该行本身就把两个口径并列（「epilogue 增量 = 2/K = 3.125%，256/16640 = 1.538%」）而未调和；`test_week11_review.py` 的 A4 检查 `abs(2/K - 0.03125) < 1e-12` 只验证 2/64 的算术、没有把 2/K 绑定到任何测得量；`images/03-shape-anatomy.svg` 也写着「＋256 B（2/K = 3.125%）」，同样承接了这个误标。
- **置信度**：高。D73 原文定义与算术均可复核。

- **置信度**：高。数字可由当天冻结输出与 cost_model.py 直接复算。

#### 5. 「16 例都是 fp32、epilogue 型融合」与案例库事实不符
- **原文**：“（16 例都是 fp32、epilogue 型融合、静态 Shape、组外路径被 L4 拦截）”
- **依据**：按 `day-076/code/cost_model.py` 的案例库逐例核对：A4 是 **int8** 全链（正是被 L5 拦下的 dtype 负例），「16 例都是 fp32」至少错这 1 例；翼 B 的 R1/R1ctl/R2/R2ctl 用 `cand_mm_mm()` 构造，算子链是 (matmul, matmul)、模式名是 `experimental.matmul_matmul`，**不是 epilogue 型融合**（epilogue 型指 MatMul＋逐元素尾链；MM→MM 在 D73 里就是资源反例），加上翼 A 的 A1（relu→matmul）也不是 epilogue 链，「都是 epilogue 型」至少错 5 例。第 0 格（合法∧不正确）的适用前提应缩窄表述（如「合法子集的数值语义沿用 D50/D52 定义、静态 Shape」），否则读者会把结论范围放大到不成立的案例集合。
- **置信度**：高。依据案例库构造代码逐例核对（wing_a_cases/wing_b_cases）。

## 【存疑】

#### 1. R1ctl「数值上……逐位相等（今天 §2 对拍）」的证据归属不成立
- **原文**：“无组外使用者：数值上独立执行与融合执行逐位相等（今天 §2 对拍），”
- **依据**：当天 §2 没有对 R1ctl（2048×64×1024×2048 的 MM→MM）跑过数值：2e 的 MM→MM 对拍只有一个 2×2 固定实例（A0@B0 再 @C2），随机 12 组（2f）与独立验收的新 8 组都只覆盖 matmul→add→relu 链。§3 巡检表对合法例的「正确✓」写的是「§2 模式级对拍＋12 组随机」——是模式级口径；§1 现场一写成对 R1ctl 这个具体 Shape「逐位相等（今天 §2 对拍）」，证据强度被夸大了一级。§3.2 与验收清单中「R1ctl 数值全对」同此。数值结论本身在「两次执行同 k 升序＋整数域」的口径下大概率成立，未被当天实验证伪，但作为「证据已到位」的叙述过于绝对。
- **置信度**：中高。覆盖事实明确可数；数值断言本身无法由当天实验证伪。

#### 2. 「L5 dtype、L6 拓扑序（后两条 D75 补）」按行文位置会被读成 L5 也由 D75 新增
- **原文**：“L5 dtype、L6 拓扑序（后两条 D75 补）”
- **依据**：D75 新增的规则是 L3b（边形状）与 L6（组内拓扑序）两条——D75 教程总结与 cost_model.py 注释一致；L5 dtype 自 D50 起就存在，D74 的规则集就是 L1–L5（D75 正是用 d74_can_fuse 回归对照证明 L3b/L6 在 D74 规则集下漏网，已在 day-075/code/test_negative_cases.py 核实）。规则列表共 7 项，「后两条」按位置最自然的读法是末尾的 L5、L6，其中 L5 的归属与事实不符；若作者本意是「L3b/L6 这两条 D75 补」，括号位置也应移动。`code/review-onepage.md` 的「D75 新增 L3b 边形状与 L6 组内序」是准确表述，可作对照。
- **置信度**：中。存在「后两条＝L3b/L6」的另一种善意读法，但按行文位置读会得到错误事实。

#### 3. 「D73–D76 四天的教程里……只有一句『数值语义 D50/52 已证』」的出处归属与仓库不符
- **原文**：“「数值语义 D50/52 已证」——四天没跑过一个数。”
- **依据**：全仓检索结果：精确短语「数值语义 D50/52 已证」只出现在 D76 的 `code/cost_model.py`（E4 假设清单与 ledger_bytes 注释，共两处）；D73/D74/D75 的 README 与实验代码均无此句（它们只引用 D50/D52 作规则出处，或写「数值上也能算」）。「四天没跑过一个数」这半句属实（四天的实验均为结构/账本口径，无数值执行），但「四天的教程里……全部只有一句」按字面读与仓库事实冲突——严格说只有 D76（代码注释）带了这句话。作为「复盘翻判决日志」的叙事性概括可以理解，故列为存疑而非错误。
