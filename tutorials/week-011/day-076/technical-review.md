# 第 76 天技术校对报告

校对方式：完整阅读 README.md、`code/cost_model.py`、`code/test_cost_model.py`、`code/run_all.sh`、`code/outputs/` 两份真实输出与 4 张 SVG；在临时目录复跑主实验与独立验收（31/31、33/33 通过，输出与 `code/outputs/` 逐字节一致），并核对 D71–D75、D61/D62 的相关口径。逐项结论如下。

## 【错误】
#### 1. 决策理由把「staging ok」写成三门槛之一，且该字符串在 staging 失败时仍照印不误
- **原文**：“理由：评分 64 B > 0 且三门槛全过（零 spill / staging ok / 寄存器并发 240 ≥ 3）”
- **依据**：教程对 auto「三门槛」的正式定义是「评分 > 0 / 零 spill / 寄存器并发 ≥ 3」（README §2 第 4 步原文「auto 的三道硬门槛（评分 > 0 / 零 spill / 寄存器并发 ≥ 3）」、§3.3 三分法、假设 E5），staging 被明确设计为「只警告不否决」（E5、§5.3 检查 5d、图 2 右下「未计价 1：staging 失败 → 只警告」）。但这行理由把「staging ok」列为三门槛内容，口径自相矛盾；更实质的问题是该字符串在 `cost_model.py:486-488` 的理由模板里是写死的字面量、不读 `declared.staging_ok`。本机实际运行 `CostModel(Machine()).evaluate(cand_skinny(64, 4096, 64, out_users=2), "auto")` 验证：同一份报告既打印「理由：评分 16,384 B > 0 且三门槛全过（零 spill / staging ok / 寄存器并发 3 ≥ 3）」，又在未计价清单里打印「staging 警告：输入分块 2,097,152 B 超出剩余 SRAM（……只警告不否决）」——`staging_ok=False` 却印「staging ok」。冻结输出 `code/outputs/cost_model.txt` 第 128 行（决策结果表 R3keep 行）同样带着「……三门槛全过（零 spill / staging ok / …」，而同一文件第 93 行（检查 5d）写明 R3keep 的 staging 警告。另外今日目标中「评分 > 0 且过三个硬门槛才融」与 §2 三门槛定义（已含评分 > 0）重复计数，说明「三门槛」在文内存在两套口径。测试未拦住它，是因为没有任何断言检查 fuse 理由文本与 `staging_ok` 的一致性。
- **置信度**：高（本机运行复现 + 源码 `cost_model.py:486-488` 可直接看到硬编码 + 冻结输出第 128/93 行自相矛盾）。

#### 2. R4 的 65,792 B 被标成「累加器」，实际累加器只有 65,536 B（恰好等于 64 KiB）
- **原文**：“（R4：累加器 65,792 B > 64 KiB）”
- **依据**：按本教程自己的口径，65,792 B 不是累加器：`cost_model.py` 的 `_resource_side`（约 296–298 行）先算 `fs.reg_demand = tm * tn * m.itemsize`（注释「累加器块」，R4 P3 tile128 为 128×128×4 = 65,536 B），再加 `m.lanes * m.itemsize`（注释「bias 在飞」，64 通道 × 4 B = 256 B），合计 65,792 B。第 73 天 README 图 2 的原话是「65,792 B（tile 128×128）的累加器恰好填满 64 KiB、epilogue 的 256 B 降级到第 2 级 SRAM」；第 75 天写的是「占用 65,792 B 超过寄存器堆」。累加器单独等于 65,536 B = 64 KiB，恰不大于；「> 64 KiB」成立的是单 tile 占用（累加器＋bias 在飞）。按 128×128×4 手算的读者会对不上数（这正是本系列强调的「逐位核对」场景）。应写成「单 tile 占用（累加器 65,536 ＋ bias 在飞 256 = 65,792 B）> 64 KiB」。
- **置信度**：高（代码注释、D73/D75 原文、128×128×4 的算术三方一致）。

## 【存疑】
#### 1. 「MLGO 用强化学习从实测性能回流去校准内联代价」与首个生产模型的目标函数不符
- **原文**：“Google 的 MLGO 更进一步，用强化学习从实测性能回流去校准内联代价”
- **依据**：MLGO 确实以强化学习训练 LLVM 内联决策（首个生产部署的内联模型用进化策略训练，替换 LLVM 的内联启发式，在 Google 生产构建与 Fuchsia 上线），但该模型的优化目标与奖励是**代码体积**（inlining-for-size，训练收益来自链接后二进制体积差），不是「实测性能」；以运行时性能为反馈的是 MLGO 框架的其他组件（如寄存器分配 eviction 的性能模型，当时仍在推进中）。此外模型是整体替换内联代价启发式，而非「校准」它。本环境无法联网核对官方仓库（webfetch 超时），以上来自对 MLGO 论文与开源仓库的既有了解；建议改为「用强化学习（进化策略）训练内联策略，首个生产部署的模型以代码体积为目标函数」并加注出处，或先在可联网环境核实。
- **置信度**：中（「强化学习训练内联」方向正确，「实测性能回流」细节存疑；未能在线核实，以 google/mlgo 官方文档为准）。

## 【建议】
#### 1. 「-1 当未知维度」被归为「D61 口径」，而 D61 恰好明确否定 -1 可表示未知
- **原文**：“M 从 2048 拧成 −1（未知维度，D61 口径）”
- **依据**：第 61 天的口径与此相反：D61 明确写「`-1` 在 shape 语义里就是负数维度，直接非法」（Day 60 实测 `negative dimensions are not allowed`），其 mini 表示用 `None`/`Sym` 表示未知维度，并把「负数」与「未知」两套语义彻底分开；D61 真正传下来的纪律是「未知 ≠ 任意、先特化」。-1 当未知维度是本系列 Python 候选结构自带的记号（D75 的 `Op` docstring 已如此写，D76 沿用），把它归到「D61 口径」会让回读 D61 的读者困惑。建议注明「-1 是本教程 Python 侧的未知维度记号，语义沿用 D61 的『未知 ≠ 任意』」。`cost_model.py:115` 的注释「未知维度用 -1（D61 口径）」同理。
- **置信度**：高（D61 原文可查）。

#### 2. 对 D75 选做挑战的「引子」一句是转述，却用直角引号呈现为原话
- **原文**：“选做挑战里留了一句话：「同一张图上 keep 亏、重算却账面为正——这是明天统一计价的引子」”
- **依据**：D75 选做挑战的实际原句是「一句话解释『为什么同一张图上 keep 亏、重算却账面为正，而保守策略两个都不放』——这句话就是明天 D76『统一计价、形式排序』的引子」，语义一致但字面不同。用「……」引用号容易让读者以为是逐字引用；建议改为转述（如「D75 的选做挑战留了个引子：……」）或按原句引用。
- **置信度**：高（D75 原文已逐字核对）。

#### 3. CostReport 的输出在一处数成「四样」、另一处数成「五样」
- **原文**：“**输出**是四样东西（itemized 评分明细、fuse/refuse 决策、可归因的理由、融合前后的 mini-IR 对照）”
- **依据**：§4 第 4 步写「CostReport：评分明细、决策、三类可归因理由、形式提示、IR 对照——五样东西一起返回」，把形式提示（hints）计入后是五样；§3.1 与今日产出只列四样（未含 hints／unpriced）。两处计数不一致，建议统一口径，例如「四样主输出，另有形式提示与未计价清单两个附加字段」。
- **置信度**：高。

#### 4. 拒绝理由的「类数」在正文、代码检查与图 3 之间不统一（三类 vs 四类）
- **原文**：“我能定位「拒绝理由」的归属：合法性 / 评分 ≤ 0 / spill 一票否决 / 并行度门槛四类前缀各自来自哪一层”
- **依据**：本行（§8 验收）用「四类前缀」，而主实验检查 7d 写「cost model 把 D75 的四层判据归成三类」、图 3（03-decision-table.svg）底注写「拒绝理由归三类」却紧接着列出四组（合法性 8 例 / 评分 ≤ 0 3 例 / spill 一票否决 1 例 / 并发门槛 1 例）。按「合法性 / 评分 / 门槛（spill＋并发）」归并为三类说得通，但同一教程两种数法容易误读，建议统一为一种说法，例如「三类归属、四个理由前缀」。
- **置信度**：高。
