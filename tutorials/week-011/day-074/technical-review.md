## 【存疑】

#### 5. 「RewritePattern 拿不到机器卡/tile/workload」作为对 MLIR 的普遍论断过于绝对
- **原文**：“RewritePattern 匹配的是图结构，拿不到机器卡（`Machine`）、拿不到 tile、甚至拿不到完整的 workload——收益判断需要的输入它根本没有”
- **依据**：在 MLIR 里，`matchAndRewrite(op, rewriter)` 的签名确实只传操作和重写器、不传机器模型，这一点成立；但 RewritePattern 子类普遍可以通过构造函数捕获任意上下文（所在 Pass 的参数、目标特性等），上游大量 Pass 正是这样把配置注入 Pattern 的，所以“收益判断需要的输入它根本没有”作为对 RewritePattern 的一般性描述不成立——不注入是本系列 D51 朴素实现的选择，不是机制的必然。就本教程自身的玩具 Pass 而言该论断为真，且“信息不在签名里、要靠注入”反而更能支撑“接口边界应显式化”的论点。建议措辞限定为“matchAndRewrite 接口本身不提供这些输入；不经构造函数注入就拿不到，本系列的 Pattern 没做注入”。我未能在本仓库核对 MLIR 源码逐版本行为，此条基于 MLIR 通行实践。
- **置信度**：中（“模式可经构造函数携带上下文”是 MLIR 常识性用法；具体版本细节未逐条核实）。

## 【建议】

#### 6. 「第 50/52 天的 RewritePattern」的出处应更精确
- **原文**：“回顾第 50/52 天的 RewritePattern：`Add + Relu → FusedAddRelu`，匹配上就替换。”
- **依据**：D50 只定义融合算子并明确零 Pattern；`Add + Relu → FusedAddRelu` 的 RewritePattern 由 D51 实现，D52 加多使用者约束，D53 定义 `mini.fused_matmul_bias`（本日 P2 的模式名）。写成“第 51–53 天的融合 Pattern”或“第 50～53 天的融合工作”更便于读者回查原文。D72/D73 用“第 50/52 天的融合算子”尚可（D50 确实定义算子），本句把它安在 RewritePattern 头上则不准。不影响技术正确性。
- **置信度**：高。

#### 7. §3.3 类比的账本数字与真实账本有约 0.5 MiB 出入
- **原文**：“类比：财务总监看同一份报表（ΔB +64 MiB、spill −32 MiB），激进派说「净赚 32 MiB，干」”
- **依据**：真实账本（P3 tile=2048，`outputs/fusion_gate_lab.txt` 第 53 行与检查 4c）：ΔB = 64 MiB、spill 流量 = 33,030,656 B ≈ 31.5 MiB、净收益 = 34,078,208 B = 32.5 MiB（导言与 §5.4 用的正是 +32.5 MiB）。类比把 31.5 四舍五入成 32、32.5 又写成 32，前后两处各自取整后与正文精确数字对不上。建议改成“spill −31.5 MiB、净赚 32.5 MiB”或注明是约数，避免与同页的精确值打架。
- **置信度**：高（数值均可在真实输出中复算：67,108,864 − 33,030,656 = 34,078,208）。

#### 8. conservative 策略的拒绝条件描述不完整（漏了“净收益 ≤ 0”）
- **原文**：“**conservative**（默认）拒绝 `spill > 0` 或收益未知的候选”
- **依据**：`decide` 的实现里 conservative 还拒绝零 spill 但净收益 ≤ 0 的候选（`fusion_gate_lab.py:338-340`，理由“保守策略：净收益 0 B ≤ 0（基线是 0）”），验收 D9 正是用 `ProfitReport(delta_b=0, net_gain=0)` 验证了这条分支；假设 B4 的措辞同样只列了 spill 与收益未知两条。图 4 的策略速查卡（“只收零 spill 且 net>0”）倒是完整的。按本句字面实现会漏掉 net≤0 的拒绝。建议在 §3.3 与 B4 补上这一条，保持描述与行为一致。
- **置信度**：高（行为已由 D9 与本地复跑证实）。
