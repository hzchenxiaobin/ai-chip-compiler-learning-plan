## 【错误】

#### 1. 图 4 SVG 里 int8 的两遍税占比分数算错：8/36 = 22.2%，不是 44.4%
- **原文**：“下排右是 dtype 缩放条（144 B → 72 B → 36 B，两遍税占比不变），最右的框把这笔税指给明天：Day 72 将计算融合后哪些趟可以不发生。”
- **依据**：该图注指向的 `images/04-chain-ledger.svg` 中实际写有“两遍税占比不变（64/144 = 32/72 = 8/36 = 44.4%）：所有项同比缩放”（由 `code/make_images.py:652` 生成）。64/144 = 32/72 = 0.444 正确，但 int8 口径下中间两遍税是 C、E 各 4 B ×（写一遍＋读一遍）= 2 × 8 = 16 B，占总流量 36 B 的 **16/36** = 44.4%；式中的“8/36”算出来是 22.2%（只对应单个中间 Tensor 的 8 B 税，相当于漏乘 2）。README 正文本身无错（§5.4 写“它占总流量的比例不变（44.4%）”，与 `chain_ledger(2,3,2,1)` 的 16/36 = 44.4% 一致），错误仅存在于 SVG 图内文本及 `make_images.py` 源码，应改为 16/36 后重新生成图片。
- **置信度**：高——纯算术核对（16/36 = 4/9 = 44.4%），SVG 原文已逐字确认存在。

#### 2. “实测 DRAM 流量远超 12n²”：当天并无任何 DRAM 流量实测，且缺少缓存限定条件
- **原文**：“B 的每一行会被反复读 M 遍，实测 DRAM 流量远超 12n²”
- **依据**：`flops_bytes_lab.py` 与 `test_flops_bytes.py` 只做公式与计数对拍，`code/outputs/` 里没有任何 DRAM 流量测量记录；“实测”一词与教程自己的口径声明冲突（§3.3“今天是记账，不是测量（测量在第 107/109 天）”，§5.3 亦声明实测基准属 Day 107/109）。同时该论断在技术上需要“矩阵超出缓存容量”的前提才在 DRAM 层面成立：方阵 n = 256 时 B 仅 256 KB，可整体驻留常见 L2（A100 的 L2 为 40 MB），此时 DRAM 流量并不远超 12n²——§6 错误 3 的定位三问之一“B 能装进缓存吗？”正是这个前提。应删去“实测”，或改写为“当矩阵超出缓存容量时，DRAM 流量会远超 12n²”。
- **置信度**：中——“实测”是无测量支撑的过度声明（几乎可确定需删），且无缓存限定时该句对 cache 内的 shape 不成立；若把“实测”宽松解读为“业界常识性结论”则语义勉强自洽，故不给满置信。

## 【存疑】

#### 3. “任何现实硬件”“永远访存受限”的绝对化表述（结论工程上成立，但不可证伪且未说明峰值口径）
- **原文**：“都远低于任何现实硬件的平衡点，在这条小链上全员访存受限”
- **依据**：Add 的 AI = 1/12 ≈ 0.083、Relu 的 AI = 1/8 = 0.125，要变成算力受限需要硬件 balance < 0.125 FLOP/B（相当于 19.5 TFLOPS 配约 156 TB/s 带宽）。现有 GPU／NPU／CPU 的公开峰值口径 balance 都远高于此（A100 FP32 为 12.54，低精度张量加速器更高），结论在现实工程里成立；但“任何”“永远”（§3.3“逐元素算子在现实硬件上永远访存受限”、§7 必做 1“矩阵-向量乘永远访存受限”同款句式）是不可证伪的绝对化说法。另有一个教程未提的真实细节：张量加速器的“峰值算力”（如 A100 FP16 Tensor 312 TFLOPS）只对 GEMM 类算子成立，逐元素算子跑在 CUDA 核／向量单元上（A100 非张量 FP32 为 19.5 TFLOPS）——逐元素算子应对照哪个峰值会差一个量级。建议保留结论，补“按公开非张量峰值口径”或改写为“在所有常见加速器的公开峰值口径下”。
- **置信度**：高（表述绝对化本身确定；结论对现实硬件成立无已知反例，“永远”本身无法核实为真）。

## 【建议】

#### 4. “每翻一档 shape，AI 翻一倍”与紧邻扫描表的 ×4 档位容易被误读
- **原文**：“AI 随 n **线性**爬升（每翻一档 shape，AI 翻一倍）”
- **依据**：紧邻数据表的档位是 16→64→256→1024→4096（每档 n×4），AI 相应 ×4（2.67→10.67→42.67→170.67→682.67，输出与公式均如此）。“翻一档……AI 翻一倍（×2）”若指表中一档则与数据不符；若指“n 每翻一倍，AI 翻一倍”则与 AI = n/6 的线性关系一致，但与表档位不对应。建议改为“n 每翻一倍，AI 翻一倍（表中每档 n×4，AI 恰 ×4）”。不影响正确性，仅指代歧义。
- **置信度**：高（数字事实无争议，问题仅是措辞歧义）。

#### 5. 图 3 图注“交点标在 n = 76”措辞：数学交点是 75.24，n = 76 是取整后的临界档
- **原文**：“虚线是 A100 FP32 的平衡线 12.54，交点标在 n = 76”
- **依据**：折线 AI = n/6 与 12.54 的精确交点在 n = 6×12.54 = 75.24（非整数、不在扫描档位上）；n = 76 是取整后的临界规模（AI = 76/6 = 12.67 > 12.54）。SVG 图内的标注“临界 n = 76（AI = 12.67 刚过 12.54）”本身准确，问题只在 README 图注用了“交点”一词。建议图注改为“临界点标在 n = 76（AI = 12.67 刚越过平衡线，数学交点在 75.24）”。
- **置信度**：高。

#### 6. “第 57 天的 `元素字节 = numel × itemsize`”出处引用与第 57 天实际内容不对应
- **原文**：“第 57 天的 `元素字节 = numel × itemsize`（今天所有字节公式的底座）”
- **依据**：第 57 天（`tutorials/week-009/day-057`）讲的是 Shape／Stride／Storage Offset／Contiguous 与物理偏移公式，其 README 与 `code/layout_lab.py` 只把 itemsize 用作 stride 的字节单位（“f32 每格 4 字节”），全文没有出现 numel × itemsize 的总字节公式（grep 无 numel/nbytes 命中）。“每元素 itemsize 字节”的概念确实承接第 57 天，但这条总字节公式本身是 numpy 基础（`ndarray.nbytes` = size × itemsize），今天代码第 3 节正是用它对账的。建议改为“第 57 天的 itemsize（每元素字节数）＋ numpy 的 numel × itemsize”，避免学习者去第 57 天找一条不存在的公式。
- **置信度**：中——概念衔接是真实的，仅公式出处归属不精确；不排除作者有意把两者并称。

#### 8. compulsory 下界可补一句缓存行粒度／ECC 的现实常数因子
- **原文**：“这就是 compulsory traffic（强制流量）的理想下界。”
- **依据**：真实硬件按缓存行（典型 64 B）粒度搬运并附带 ECC／tag 开销，小张量的“必须流量”会被向上取整（例如读 24 B 实际至少搬一个 64 B 缓存行），所以元素级公式是比工程可达下界更低的“理想化下界”。方向上与 `flops_bytes_lab.py` 文档字符串“真实硬件流量只会 >= 这个数”一致，不构成错误；作为初学者容易踩的坑（小张量场景理论值与实测差距里有对齐开销的一份），可在 §3.2 或错误 3 补一句“还有缓存行对齐、ECC 等常数因子，本模型全部忽略”。
- **置信度**：高（技术事实无争议；是否值得补充属于编辑取舍，故列建议）。
