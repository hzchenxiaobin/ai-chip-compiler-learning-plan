#### 2. “把两条检查对调，该拒的候选还是会被拒”与自己的实现和第 6 节矛盾
- **原文**：“就算把两条检查对调，该拒的候选还是会被拒（只是先做了无用功）”
- **依据**：这句话对本教程自己的检查链不成立，两种读法都有反例，且其中一个反例正是第 6 节“错误三”自己描述的现象。(a) 若“对调”指先跑空间估算再做预算判定（判定跟着估算走）：`buffering="triple"` 的负例 p4 会被**放行**——`estimate()` 的 `factor = 2 if cand.buffering == "double" else 1` 把 "triple" 静默按单缓冲记账（临时目录实测合计 197,120 B ≤ 262,144 B），非法候选变成 fail-open 的 ✓，比“被拒”严重得多。(b) 若“对调”指只把 `estimate()` 挪到前面、参数校验仍在判定前跑：`dtype_in="fp64"` 会在 `estimate()` 里抛未捕获的 `ValueError`——第 6 节错误三原文“程序直接抛 `ValueError: 未知 dtype_in: 'fp64'`，而不是返回 `BAD_PARAM` 判定”说的正是这件事，即“该拒的候选”根本没有“被拒”，是程序崩了。“对调不改变结果”只对“每道检查都是定义在未校验输入上的全函数”成立，而 `estimate()` 的文档字符串明确写“假定输入已被参数校验放行（库函数信任调用方）”。这句话想表达的“短路只省功夫、不改结论”在理想化前提下没错，但配上本实现的具体例子就错了，建议删掉括号里的对调断言或改成“前提是每道检查各自全设防”。
- **置信度**：高（两个反例均在临时目录实际运行验证；与第 6 节错误三的原文直接冲突）。

#### 3. 支持表里的 `int32` 会让过滤器崩溃（KeyError），违背 fail-closed 承诺
- **原文**：“消息里列出全部 5 个可选值（fp32/fp16/bf16/int8/int32）”
- **依据**：`BAD_PARAM` 的报错把 `int32` 列为合法输入 dtype，`_check_params` 的查表 `DTYPES` 也确实含 `"int32"`，`DTYPE_DOWN` 甚至专门为 `"int32"` 配了 `None`；但 `ACC_AUTO = {"int8": "int32", "fp16": "fp32", "bf16": "fp32", "fp32": "fp32"}` 没有 `"int32"` 键，`estimate()` 执行 `DTYPES[ACC_AUTO[cand.dtype_in]]` 时抛未捕获的 `KeyError: 'int32'`。临时目录实测：`ResourceFilter().check(TileCandidate(64, 64, 64, "int32", "single"))` 直接崩溃，不返回任何 Verdict。这正打在 5.2 节代码注释“设防的责任全部在 ResourceFilter——fail-closed 的前提是判定层全设防”和 3.2 节的承诺上：参数关放行、空间关崩盘，是“认识的输入”绕过了整道闸门。教程的实验从未喂过 int32 输入，58 项断言因此没有暴露它。修复方向：给 `ACC_AUTO` 补 `"int32": "int32"`（int32 输入按 4 B 累加），或把 int32 从“可选输入”里拿掉（它现在更像只为查 acc 字节数而存在）。
- **置信度**：高（已实际运行复现崩溃）。

#### 5. 01-overview.svg 的“超 525,312 B（300%）”把利用率数字安到了溢出量上
- **原文**：“12  256³ fp32·single +bias          787,456 B   300.4%   ✗ SRAM_OVERFLOW  超 525,312 B”
- **依据**：README 的判定表（即本行）里 300.4% 是“利用率”列（合计/预算 = 787,456/262,144 = 3.004），数字本身正确；问题出在引用的 `01-overview.svg` 右下角把它压成了“超 525,312 B（300%）”。同图第 8 行的对应标签是“超 66,048 B（25.2%）”，其口径是溢出/预算（66,048/262,144 = 25.2%，与 `fallback.txt` 的“超出 66,048 B（预算的 25.2%）”一致）；按同一口径，525,312 B 对应的是 **200.4%**（525,312/262,144），不是 300%。同一张图两行两种口径，初学者拿 525,312 去复算 300% 必然对不上。另外图 3 注（第 188 行）“256³ 超 3 倍预算”是同款歧义——严格语义“超出 3 倍”应为预算的 4 倍，实际合计是预算的 3.00 倍、超出 2.00 倍，建议改成“是预算的 3 倍”或“超预算 2 倍”。
- **置信度**：高（两个百分比均可直接复算；SVG 文本已核对）。

#### 6. 33³ 的 padding 项数写错：是四项，不是三项（bias 也在 padding）
- **原文**：“候选 `33³ int8·single`（奇数 tile，三项都要 padding）”
- **依据**：33³ int8·single 在对齐 32 B 下有**四个**非零项发生 padding：A 1,089→1,120（+31）、B 1,089→1,120（+31）、C 4,356→4,384（+28）、bias 132→160（+28），合计 +118 B——这正是 D101 报出的 +118 B（6,666→6,784），而 118 = 31+31+28+28 必须包含 bias 的 28。对齐 64／128 B 时 bias 同样要 padding（132→192／256）。“三项”漏数了 bias；本教程反复强调“生死在零头里”，bias 的 28 B 正是零头的一部分（128 KiB 档 int8 128³ 被 512 B 的 bias 挤出去，用的就是这个记账项）。第 5.4 节“2 幂 tile（64³）三项天然落在网格上”是同款措辞（64³ 的 bias 256 B 恰好天然对齐，但那是运气，不是“只有三项要对齐”）。该误数继承自 D101（其第 80 行同样写“三项”却给出 +118 B），仍应修正。
- **置信度**：高（逐项手算，并与 estimate() 实测 6,784／6,912／7,040 B 一致）。

#### 8. “一行记账逻辑都没有新写”与事实不符——记账在本文件里重新实现了一遍
- **原文**：“今天**一行记账逻辑都没有新写**”
- **依据**：`resource_filter.py` 的 `estimate()`（第 129–145 行）在本文件内完整实现了五项记账（五处 `align_up`、factor、`Breakdown`），与 D101 的 `estimator.py` 是两份独立实现，没有任何 import 或复用关系。作者想说的显然是“记账**规则**一条没改”，但“一行没写”的字面会让读者以为存在一个可直接 import 的 D101 模块；而双份实现真正的工程代价——D101 若改规则，D104 不会跟着变——恰好值得在学习“过滤器是账本的消费方”时点破一句。建议改为“记账规则一条没改（但代码是复刻的）”。
- **置信度**：高（两份源码均已在手边比对）。

#### 9. “每条出路……重新过同一道闸门”在代码里只重过了一半
- **原文**：“每条出路本身也是一个候选，必须**重新过同一道闸门**验证。”
- **依据**：`_fallbacks()` 对每条出路只执行 `estimate(alt)` 加 `bd.total <= self.budget`（`resource_filter.py` 第 240–242 行），没有重新跑 `_check_params`／`check()`。因为出路是用 `dataclasses.replace` 在已合法候选上改一个合法字段构造出来的，参数必然合法，结果与“重过整道闸门”等价；但字面承诺与实现有出入，若将来 fallback 的构造逻辑变复杂（比如按预算反推 tile 尺寸），这个缝隙就会变成“出路没过参数关”的坑。建议要么把措辞收紧为“重新过空间估算与预算判定”，要么让出路真的调用 `check()`（顺带还能复用短路计数器把这件事变成可断言的）。
- **置信度**：高（代码逐行对照）。

#### 10. “D97 的 CPU 冠军”这一定语叠加了 D97 实验里不存在的变量
- **原文**：“D97 的 CPU 冠军、D103 的纸面最优——`128³ fp32·double +bias`”
- **依据**：D97 的冠军是 ikj-128（512³ 上 128³ tile、FP32、ikj 循环序，13.59 GFLOPS），D97 的 CPU 实验里根本没有“缓冲策略”这个变量；“fp32·double”的完整定语是 D101 起的 NPU 侧表述（D101 原文：“12 组配置里唯一被拒的恰好是 D97 的 CPU 冠军（FP32·128³·双缓冲 = 328,192 B > 256 KB）”），且 D97 自己注明换到 516 上冠军翻成 ikj-64。沿用系列简称没问题，但严格说“冠军”只覆盖 128³ fp32 的部分，“double”是后续叠加的配置；建议首次出现处点一句“D97 冠军的 tile/dtype＋D101 起的双缓冲假设”，避免读者去 D97 找“double buffering”。
- **置信度**：高（D97 README 已核对）；影响小，属表述粒度问题。

#### 11. `parse_bytes` 的 docstring 声称支持 “256KB”，实际会抛 ValueError
- **原文**：“**实验一：把预算收紧。** `--budget 128K` 重跑，或直接看预算扫描（`outputs/budget-sweep.txt` 实际输出）：”
- **依据**：README 里出现过的预算写法（256K／128K／192K／131072）实测全部可用（`parse_bytes("192K")` = 196,608），教程正文不受影响；但 `resource_filter.py` 第 58 行 docstring 写“接受 256K / 256KB / 262144 / 1M 等写法”，其中无 i 的 “256KB” 实测抛 `ValueError: invalid literal for int()`——代码里 `t.endswith("K")` 只认以 K 结尾的串，`replace("IB", "")` 处理不了单独的 “B” 后缀（“256KB” 落到 `int("256KB")`）。这是代码注释与行为不符（README 未引用该 docstring，故按建议级处理）：修 docstring，或在 `int(t)` 前补一个 `t.endswith("B")` 分支。
- **置信度**：高（已实际运行验证四种写法，仅 “256KB” 失败）。

#### 12. 选做挑战把 `tm × tn` 称作“输出块行数”不准确
- **原文**：“`tm × tn ≤ 16,384`（输出块行数上限，模拟 Vector 单元的约束）”
- **依据**：`tm × tn` 是输出块的**元素个数**（128×128 = 16,384），“行数”只对应 `tm` 一个维度；16,384 这个取值显然按 128×128 的元素数设计（模拟 Vector 寄存器文件能装下的输出块元素量）。叫“行数上限”会让认真按字面做的读者写出 `tm ≤ 16,384` 的检查、或对不上 16,384 的来历。建议改为“输出块元素数上限（tm × tn）”。练习本身的机制设计（便宜先行、独立计数器、补三类断言）没有问题。
- **置信度**：高。
