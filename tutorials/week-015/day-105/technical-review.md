# 第 105 天技术校对报告

> 校验方式：在 /tmp 的代码副本上实际运行 `tile_story.py`（默认、`--tile 32`、`--tile 128`、`--buffering single`、`--self-test`，35/35 通过），并用脚本统计依赖边数；数字逐项对照 D99~D104 的已发布输出（main-first/skip-first.txt、order-sweep.txt、reuse.txt、main-tile.txt、compare-modes.txt、fill-drain.txt、sweep-tile.txt、filter-table.txt）与 D102/D103 的 README。仓库冻结产物未被改动。

## 【错误】
#### 1. story.txt 印出"单缓冲同块 17.5078 µs"，与 D102、自检和本文 5.4 的 16.5078 µs 直接矛盾
- **原文**：“单缓冲一个输出块 16.5078 µs”
- **依据**：本文声称该数字来自 D102（D102 main-tile.txt 第 49 行与自检第 16 项均为 16.5078 µs），但当天主交付物 story.txt 第 87 行实际印着“（单缓冲同块 17.5078 µs——D102 的轮流值班，见 5.4）”。原因是 tile_story.py 中 act3_print 的 `single_blk = bias_t + 2*load_t + n_k*(2*load_t + comp) + st.dur` 把已计入“填充”的首圈搬运对又计了一遍（0.0078+1+16+0.5=17.5078，多 1 µs）。已本地复跑验证：默认输出第 86–87 行即 17.5078，而 `--self-test` 第 16 项断言 single 块合计 16.5078125 µs 通过——同一程序两处自相矛盾。
- **置信度**：高（输出与代码均已核对；错误在代码/冻结输出，不在 README 正文，但 README 声称“全部与 D102/D103 的已发布数字对账一致”被该行证伪）。

#### 2. 单缓冲块时长的分解式加起来不等于 16.5078 µs（多算 1 µs）
- **原文**：“块合计 16.5078 µs = 填充 1.0078（②） + 8×(搬 1＋算 1) 轮流值班（③） + 写回 0.5（④）”
- **依据**：1.0078 + 8×(1+1) + 0.5 = 17.5078 ≠ 16.5078。“填充 1.0078”已经包含首圈 A[0,0]/B[0,0] 搬运对（buffering-single.txt 时间线 0.0000–1.0078：bias＋A＋B），其后只剩 7 对搬运和 8 次计算（1.0078+7×2+1+0.5=16.5078）。D102 原版分解“块合计：16.5078 µs = bias 0.0078 + 8×(Load 1 + Compute 1) + Store 0.5”（main-tile.txt 第 49 行）自洽；本文把“bias 0.0078”改成“填充 1.0078”却没有把 8× 改成 7×，引入 1 µs 重复计数。
- **置信度**：高（算术与两份输出均可直接复算）。

#### 3. “错误四”引用的 32³ 闸门数字（12,416 B／4.7%）是单缓冲口径，与本文默认的双缓冲及同文选做挑战（7.9%）矛盾
- **原文**：“现象：闸门放行了 32³（12,416 B，利用率 4.7%），有人就选它——结果 kernel 比 64³ 慢一截。”
- **依据**：本文主角、run_all.sh 与 tile_story.py 默认都是 double。32³ 双缓冲五项合计 = 2×4,096+2×4,096+4,096+128 = 20,608 B，利用率 7.9%（实测 `python3 tile_story.py --tile 32` 判定行“✓ 放行（利用率 7.9%）”）；12,416 B 是 32³ 单缓冲（4,096×3+128）的数字，4.7% = 12,416/262,144。D103 sweep-tile.txt 也列明“32³ 单缓冲空间 12,416／双缓冲空间 20,608”，同文选做挑战更直接写“利用率从 31.3% 掉到 7.9%”。错误四若不改数字，就必须标明“32³ 单缓冲”。
- **置信度**：高（已运行验证 + 三处交叉印证）。

#### 4. 选做挑战的答案方向“搬运总字节没变”不成立——A/B 流量几乎翻倍才是变慢主因
- **原文**：“搬运总字节没变，但块数从 64 涨到 256，每块都要重新填充／排空，DMA 的碎片更细”
- **依据**：本模型每个输出块完整重搬自己的 A/B 切片（tile_story.py 模块 docstring 自述“相邻块之间不复用行/列块”），A 流量 = M×K×4×(N/tn)：64³ 为 8 MiB、32³ 为 16 MiB（B 同），搬运总量约 17 MiB→33 MiB。实测 `--tile 32`：DMA 忙 544.5→1057.0 µs、内核 608.5→1089.0 µs——若“总字节没变”，DMA 忙不可能翻倍。D101 reuse.txt 的账“Tile 每翻一倍，A+B 流量减半”（反向成立）与代码 docstring“缩 tile → HBM 流量上升”都指向流量翻倍，而非碎片变细。
- **置信度**：高（已运行实测；与 D101 已发布数据一致）。

#### 5. “同步点的‘数量’没变”与本文自己的输出和 D103 的对账表都矛盾（S2 数量变了）
- **原文**：“同步点的"数量"没变，变的是"等了多久"”
- **依据**：本文 5.3 引用的 story.txt 印“S2×6（…WAR 距离 2）”，5.4 引用的 buffering-single.txt 印“S2×7（…WAR 距离 1）”——同一块 C[0,0] 的 S2 从 7 对变成 6 对；kernel 级 D103 compare-modes.txt 明写“S1/S2/S3/S4 次数 512/511/64/63 → 512/510/64/63”及“S2 从 511 → 510（距离 2 使最初两圈没有前任读者）”。S1/S3/S4 确实不变，把结论推广到“同步点”整体不成立，应改为“S1/S3/S4 的数量没变，S2 少了最初一对”。
- **置信度**：高（两份输出与 D103 对账表三方一致）。

#### 6. “S2 有 510 条边”的计量单位错误：依赖 DAG 里 S2 边实为 1020 条
- **原文**：“本周真实运行：S2 有 510 条边”
- **依据**：build_ops 对每个有前任读者的 (b,k)，同时给 A 和 B 两个 load 各加一条指向 reader 的依赖边；实测统计 double 模式 load→compute 的 WAR 边共 1020 条、S2 load 对为 510 对。510 的正确单位是“对/次数”（D103 compare-modes.txt 的口径是“次数 510”，本文同段自己也写“load 对应该有 510 对”）。写成“条边”会误导读者按 DAG 数边（会数出 1020），且与同段“数 S2 的边数”的排查指令直接冲突。
- **置信度**：高（已运行统计验证：510 对、1020 条边）。

#### 7. 双缓冲“稳态 8×1 双忙”不实：末圈那 1 µs DMA 空闲，只有 7 µs 真正双忙
- **原文**：“k=0..7 八圈累加，乒乓槽让搬运与计算重叠，稳态每圈 1 µs 双忙”
- **依据**：double 模式下 block 0 的 DMA 在 8.0078–9.0078（c[0,7] 末圈）无任何事件（story.txt 时间线：B[0,7] 于 8.0078 完工后，下一条 DMA 是 9.0078 的 store[0]），块内 DMA 忙仅 7.5078 µs，与计算重叠的只有 7 µs。D103 fill-drain.txt 对同一个 9.5078 µs 的分解是“稳态 7×1（算 c[k] ‖ 搬 A/B[k+1]，双忙）+ 排空 1.5（末圈 1 DMA 闲＋写回 0.5 计算闲）”。数值上 1.0078+8+0.5=9.5078 没错，错在把末圈那 1 µs 也标成“双忙”（story.txt 第 86 行、图 2 图注“稳态 8×1.0 双忙”同病）；只有流水线模式下末圈因预取才真双忙。
- **置信度**：高（时间线可直接核对；属标签级错误，数值拆分本身正确）。

## 【存疑】
#### 1. “estimate 一行不改”言过其实：少掉第五项 staging，函数结构也不同
- **原文**：“`estimate` 一行不改”
- **依据**：D101 estimator.py 与 D104 resource_filter.py 的 estimate 都是五项记账（a/b/c/bias/staging，Breakdown 数据类，含 acc_dtype 与 align 参数）；D105 的 estimate 只有四项（a/b/c/bias，返回 dict，TileConfig 没有 staging 旋钮）。所列三条规则（×2 只加流入项、C 恒按累加精度、逐项 align_up）确实一致，主角配置下数字也一致（staging 默认关闭为 0），但“一行不改”字面不成立，宜改为“记账规则一字不改”并说明 staging 项在本例为 0。
- **置信度**：高（已逐行比对 D101/D104 源码）；只影响表述与出处，不影响任何数字。

## 【建议】
#### 1. 5.2 的“两幕”与全文“四幕”口径不一
- **原文**：“再用两幕"戏"串起来”
- **依据**：同文今日目标、5.1 文件树、story.txt 与第 9 节均为“四幕”（第一幕~第四幕，act1~act4）；5.2 的“两幕”只与第 1 节“旅程分两幕：编译期／运行期”的另一种二分法吻合，两种切法混在同一天容易让读者以为 story.txt 只有两幕。
- **置信度**：高（纯一致性问题，不影响技术内容）。

#### 2. 概念题编号两处口径不一致，且“每天一概念一数字”对 D99 不成立
- **原文**：“12 题覆盖六天（每天两题：一题概念、一题数字/排错）”
- **依据**：第 8 节验收写“概念题（第 1/3/5/7/10/11 题）”，把第 9 题（数值题：距下界差多少）排除、把第 10 题计入，与“每天两题：先概念后数字”的读法（应为 1/3/5/7/9/11）不一致；且 D99 的第 1、2 题都偏概念（第 2 题问“改变的是什么”，非数字题）。第 8 节的分类更贴近题目本身，5.3 宜对齐它。
- **置信度**：高（题目内容可直接核对）。

#### 3. “下一块计算无缝续上”与同表数字矛盾：块边界仍有约 0.52 µs 计算空档
- **原文**：“下一块计算无缝续上”
- **依据**：story.txt 同段：c[0,7] 于 9.0078 完工，c[1,0] 9.5156 才开工，中间 0.5156 µs 计算在等 bias[1]（DMA 链）和 S4 的 store[0]；全 kernel 计算气泡 33.5 µs 正是 63 个块边界各约 0.5 µs 攒出来的（545.5−512−1.0078≈32.5）。“无缝”若指“不用等首圈填充即可续上”（比双缓冲早 1 µs）成立，但字面与相邻数字冲突，宜补一句“边界仍有约 0.5 µs 气泡”。
- **置信度**：高（数字可从同表直接相减）。

#### 4. “块级规划发生在 Lowering 之后”未点明是哪一次 Lowering，与 D101 的表述易打架
- **原文**：“图级规划发生在编译早期，块级规划发生在 Lowering 之后”
- **依据**：本系列 D92 的总览图把 Tiling/循环变换画在“Lowering（图算子层→循环/内存层）之后”的同层 IR 变换，而 D101 README 明说空间判定“必须发生在 Lowering 到目标代码之前”——两次“Lowering”指的不是同一条边界。D105 裸用“Lowering 之后”两种读法都通，但初学者拿着 D101 的句子会对不上，宜写明“图级 Lowering（图→循环层）之后、目标代码生成之前”。
- **置信度**：中（属表述歧义而非硬伤；两种边界在本系列内部均有出处）。

#### 5. 周测第 3 题讲解引用的 D100 例子与 D100 已发布分配表不符
- **原文**：“参考答案带出处”

- **置信度**：中（可能本意是“偏移 512 的房间”；已对照 D100 main-first.txt）。

#### 6. 图 1 图注“六件工具是六个站点”与图中画法有出入
