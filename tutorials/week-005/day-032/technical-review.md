## 【错误】
#### 1. fold_demo.mlir 的常量 op 数量写错：文件里有 3 个 `arith.constant`，不是“两个”
- **原文**：“打开 `code/fold_demo.mlir`：9 条 op 里有两个常量、一次乘法、还有一条 cast 链（`extf`→`truncf`、`index_cast`→`sitofp`）。”
- **依据**：`code/fold_demo.mlir` 中共有 3 条 `arith.constant`（`%a = arith.constant 2.0 : f32`、`%b = arith.constant 3.0 : f32`、`%zi = arith.constant 0 : index`），加上 mulf／extf／truncf／index_cast／sitofp／addf 共 9 条不含 return 的 op，含 return 共 10 条。5.3 节实验⑤的枚举“9 条 op（两个常量、一次乘法、`extf`→`truncf`、`index_cast`→`sitofp` 两条 cast 链、一次加法、return）”把 return 计入后只有 2+1+2+2+1+1=9 项，恰恰是漏数了 `%zi`；同一段下文“`index_cast`／`sitofp` 两级转换作用在常量 0 上”又承认了这个常量，前后自相矛盾。图 3（现图 5）面板 B 的“把 9 条折成 1 条”沿用了同样的计数。另外 3.3 节说“一条 cast 链”、5.3 节说“两条 cast 链”，两处表述也不一致。正确说法应为“10 条 op（含 return，其中 3 条是常量）折成 1 条常量加 return”。
- **置信度**：高（逐行数过文件，且教程自己的叙事已引用第三个常量）。

#### 2. 第 6 节错误 1 把 `dense<[1.0, 2.0]>` 的形状说成“1×2”，实际形状是一维的 `[2]`
- **原文**：“现象：`dense<[1.0, 2.0]>`（形状 1×2）配 `tensor<2x3xf32>`。”
- **依据**：`dense<[1.0, 2.0]>` 是一维张量字面量，形状为 `[2]`（1 个维度、2 个元素）；“1×2”按 MLIR 形状记法对应的是二维形状 `[1, 2]`（`tensor<1x2xf32>`）。教程自己引用的报错原文 `inferred shape of elements literal ([2]) does not match type ([2, 3])` 打印的就是 `([2])`——若字面量形状真是 1×2，报错应打 `([1, 2])`。本机重放探针确认报错为 `([2]) vs ([2, 3])`（已逐字符核对）。初学者照“形状 1×2”去对照报错里的 `([2])` 会对不上号。应改为“形状为 `[2]`（一维、2 个元素）”。
- **置信度**：高（报错信息本身即是最直接的证据）。

#### 3. “逐元素张量计算由 linalg 承接，那是第 10 周之后的路”与本仓库计划及相邻教程均不符
- **原文**：“MLIR 生态里逐元素张量计算通常由 linalg 承接，那是第 10 周之后的路”
- **依据**：技术论断本身成立（one-shot-bufferize 对 linalg 逐元素 op 有完整支持，对 tensor 形态的 arith.addf 无规则，本机实测 `error: op was not bufferized`），但周数指向经查证是错的：(a) `AI芯片编译器学习计划.md` 通篇没有出现 linalg，第 10 周的主题是“Layout 与冗余算子消除”，第 10 周及之后的任何一周都不涉及 linalg；(b) 次日 Day 33 的今日目标就写着“能独立跑通 `linalg.matmul` 的五级台阶（图/张量层 → 缓冲区层 → 循环层 → CFG 层 → LLVM 层）”，linalg 在第 5 周就已登场，且走的正是与今天实验⑥同一套 bufferize＋lowering 管线；(c) 逐元素形态的 `linalg.generic` 最早出现在第 9 周 Day 60（Broadcast 规则）的教程里，也在第 10 周之前。无论按哪种口径，“第 10 周之后”都不成立。建议改为“后面的路（Day 33 就会初见 linalg.matmul）”或删去周数。
- **置信度**：高（计划文件、Day 33／Day 60 教程与 bufferization 报错均已逐一核实；不确定点：仅“作者是否另有所指”这一主观可能，无客观依据支持）。

## 【存疑】
#### 1. “种类是有限的、可枚举的”过于绝对，MLIR 的类型集合并非有限
- **原文**：“种类是有限的、可枚举的；具体的数是无限的。”
- **依据**：MLIR 的类型空间是无限的：仅 tensor 一族就有 `tensor<2x3xf32>`、`tensor<2x4xf32>`、任意维数与元素类型的组合，再加各方言自定义类型，不存在“有限、可枚举”的边界。3.3 节第二层论证“每个数都得是一个新类型，类型集合无限爆炸”隐含了“正常情况下类型集合有限”的前提，这个前提不成立。真实的区别是：类型是**结构化的、被大量值共享的、总量小而稳定**的数据，而常量数值与 op 一一对应且数量无界；uniquing 的收益是“同构类型全局一份”，不是“类型总数有限”。图 1 中“种类有限：i32 / f32 / tensor…”一句同样表述。建议改为“种类少而稳定、可被所有同形值共享”。
- **置信度**：中高（结论方向正确、表述失准；不确定点：若把“种类”理解为 i32／f32／tensor 这类**类别名**而非具体类型实例，则勉强可辩，但与下文“具体的数是无限的”对仗时读者必然按“类型实例”理解）。

#### 2. “类型出现在且只出现在三个位置”与教程自身内容冲突，且第二项“op 的结果签名”不准确
- **原文**：“MLIR 里类型出现在且只出现在三个位置”
- **依据**：过于绝对，反例就出现在本教程内部：(a) 3.2 节和图 2 自己展示了属性里也带类型——`value = dense<…> : tensor<2x3xf32>`（TypedAttr）与 `function_type = (…) -> …`（TypeAttr），这是第四种“出现位置”；(b) 复合类型内部嵌套类型（选做练习 (a) 的 `tuple<i32, f32>`、`memref<2x3xf32, strided<[3, 1]>>`）；(c) 第二项把冒号后的签名统称“op 的结果签名”，但 `arith.addf %x, %bias : tensor<2x3xf32>` 的尾随类型覆盖的是**操作数＋结果**的合并签名，`tensor.dim %arg0, %c0 : tensor<?x?xf32>`（实验④）冒号后写的更是纯操作数类型。3.1 节同一页还写着“后面每次使用都要再声明一次”，说明使用处文本上也在重复类型。若把三个位置理解为“值类型的 IR 存储位置”，块参数与 op 结果才是真正的两处，`function_type` 只是派生的 TypeAttr。
- **置信度**：中高（“且只出现在”这一绝对化表述可被教程自身证伪；不确定点：作为给初学者的简化框架，删去“且只”并补一句边界说明即可，未必算硬错误）。

## 【建议】
#### 1. “属性能被读出来参与计算，类型不能”表述过强，与 3.4 节自述矛盾
- **原文**：“属性能被读出来参与计算，类型不能。”
- **依据**：Verifier 和 Pass 经常读类型参与编译期计算——3.4 节自己就写着“静态维（数字）：编译期已写死，Verifier 可以直接用它做检查”，one-shot-bufferize 依据类型决定改写哪些 op 也是例证。想表达的准确意思是“类型不承载具体数值，无法像 `value` 属性那样被读出来做数值折叠”（同段下文“类型不承载运算”就是正确说法）。建议首句直接用后一种表述，避免读者得出“Pass 不能用类型做计算”的错误结论。
- **置信度**：高（反例在同一天的教程文本里即可找到）。

#### 2. “今天的例子会见到六块铭牌”中列出的 `value = 0 : i32` 在当天代码里并不出现
- **原文**：“今天的例子会见到六块铭牌：`value = 0 : i32`（标量常量）”
- **依据**：当天 7 个代码文件及 8 个探针中没有任何 `value = 0 : i32`（探针③用的是 `value = 0 : i64`；当天实际出现的标量常量是 `%scale = arith.constant 2.0 : f32` 与各 `index` 常量，实验④的 generic 输出里是 `value = 0 : index`）。`0 : i32` 是 Day 30 的例子（Day 30 README 的 `%c0 = arith.constant 0 : i32`）。图 2 属性家族横幅里也画了 `value = 0 : i32` 这块铭牌。建议把示例换成当天真实出现的 `value = 2.0 : f32` 或 `value = 0 : index`，或注明这块铭牌来自 Day 30。
- **置信度**：高（已 grep 全部代码文件与探针确认）。

- **置信度**：高（存在自洽读法，故列为建议而非错误；不确定点仅是作者本意取哪种口径）。
