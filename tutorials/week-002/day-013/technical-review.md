## 【错误】
#### 1. 图 2 说明与 SVG 符号表中的 %v 编号与代码实际的对象身份不符
- **原文**：“`"A"` 查到 `%v0`、`"C"` 查到 `%v5`——一个名字只能查到一个对象”
- **依据**：`%vN` 在本系列中唯一可对应的真实编号是 `Value::id()`（节点侧的 `%n0`～`%n3` 是真实打印的编号，值侧编号由 `Graph::values_` 创建顺序分配）。用 `lower_model_to_graph(target_model())` 实测打印 `g.values()` 的 id：A=0、B=1、**bias=2、C=3、D=4、Y=5**。因此 `"C"` 解析到的是 id 为 3 的对象，`%v5` 实际是 `Y`；`images/02-mapping-mechanism.svg` 的符号表同样写成 “bias→%v4、C→%v5、D→%v6、Y→%v7”（%v2、%v3 没有任何对象对应，图中 “n2 的第 0 槽 → %v5” 也随之错位——实际 add%n2 第 0 槽指向 id=3 的 %C）。该编号在 LLVM/MLIR 惯例下同样对不上（按结果顺序 C 应为 %2 或 %3）。图注以“查到”的口吻给出具体编号，等于教给读者错误的对象身份。修法二选一：改成实测编号（bias→%v2、C→%v3……），或只用名字表述（“C” 查到 %C）回避编号。
- **置信度**：高。实测依据充分（Value id 逐个打印核对）；唯一保留意见是 %v 编号从未出现在任何真实输出里、属于“图内自造编号”，但既然给出了具体编号，就应与代码的实际身份一致。

## 【存疑】
#### 1. “`Add(x, 常量)` 可以在编译期算掉一部分”对运行期 x 过度承诺
- **原文**：“第 24、47 天的常量折叠能直接吃它（`Add(x, 常量)` 可以在编译期算掉一部分）”
- **依据**：常量折叠成立要求操作数在编译期全部已知。本图里 x 是 `matmul(%A, %B)` 的结果、A/B 是运行期输入，此时 `Add(x, 常量)` 在编译期算不出任何一部分（唯一例外是 c=0 之类的代数恒等，那属于计划第 23 天的代数化简 `Add(x, 0) → x`，不是“算掉一部分”）。更稳妥的说法是“变体 A 的 bias 能**参与**折叠——例如别的 Pass 把 x 折成常量后整个 add 可在编译期算掉，或利用已知常量做代数化简；变体 B 永远没机会”。按字面读会让人以为对动态 x 也能部分求值。同段“前者的数据编译期可见，将来能参与常量折叠”（3.4 节）用词准确，可参照。
- **置信度**：中。不排除作者本意是“某些路径下（x 亦变为常量时）能算掉”，主论断（编译期可见性的合同差异）本身正确且已由实验支撑；但括号里的例子放在本图场景（x 恒为运行期值）下按字面不成立。

## 【建议】
#### 1. “14 组构造失败”与测试文件的实际块数对不上
- **原文**：“**映射的纪律**（23 条——14 组构造失败逐个断言消息内容：重名×3、乱序、拼错、自环、算子名拼错、常量作为层、权重数据不符、属性放错层、输入个数、输出拼错、输出写两次）”
- **依据**：`tests/test_frontend.cpp` 第 3 节实际有 **15 个** `lower_fails` 构造失败测试块：重名×3（图输入撞名、权重撞图输入名、两层同输出名）、乱序、输出遮蔽图输入（“已存在”）、真自环（“名字成环”）、"C" 不存在、biasx 拼错、算子名拼错、常量作为层、权重数据不符、属性放错层、输入个数、输出拼错、输出写两次——逐块数即 15；而按句中类别枚举加总只有 13（重名×3 计 3 组）或 14（把两种“自环”各算一组），无论哪种口径都凑不出与实际块数一致的“14 组”。23 条断言数本身核对无误，仅组数口径需澄清。
- **置信度**：高（逐块清点；不影响任何代码行为，仅是描述与实物的计数偏差）。

#### 2. “模型其余部分一字不动”与实验代码及其 diff 矛盾
- **原文**：“只改一个参数：把 `bias` 从 `weights` 挪到 `inputs`（模型其余部分一字不动）”
- **依据**：`experiments/weight_position_ab.cpp` 里变体 A 的 `name` 是 `"A-bias-as-weight"`、变体 B 是 `"B-bias-as-input"`（第 51／65 行），README 自己引用的 diff 第一处（1c1）正是这行图名变化。除 `name` 字段外确实一字不动，但“一字不动”按字面不成立；改成“除图名外一字不动”即可自洽。
- **置信度**：高（代码与日志两处证据；影响仅限表述严谨性）。

#### 3. 冻结产物的代码注释与 README／实测不一致（README 本身正确）
- **原文**：“ASan 报 `heap-use-after-free READ of size 2`，退出码 1；普通构建下是未定义行为”
- **依据**：实测 `bugs/err_outlived_graph.cpp`（g++ 9.4.0，ASan）确报 `READ of size 2`、退出码 1，free 栈顶 `std::default_delete<Value>::operator()`、`Graph::operator=(Graph&&)` 位于 Graph.h:22——README 此处全部正确。但该文件头注释第 7 行写“heap-use-after-free READ of size 32”，与实测和 README 均不符，读者按注释预期会困惑；另外 `tests/test_frontend.cpp` 头注释写“三组问题”，实际测试分四节（README 的“分四组”才是对的）。本次按规则不改冻结产物，仅提示后续版本同步这两处注释。

#### 4. “消息只有指针没有名字”与 add_constant 实际报错内容不符
- **原文**：“`add_constant` 的工厂守卫本可以拦（消息只有指针没有名字），前端多写三行预检查”
- **依据**：`add_constant` 的工厂守卫实际抛出的消息是“constant: 数据个数 N 与元素数 M 不符（f32<2x2>）”（src/Graph.cpp:158）——既没有指针也没有名字，只有类型与计数。结论本身成立（工厂报错认不出“哪个权重”，前端预检查才能点名 `"bias"`），但“只有指针”的字面描述不准确，改成“消息里只有类型和个数，没有名字”更贴合实物。
- **置信度**：高（消息文本直接核对；属低影响的措辞问题）。
