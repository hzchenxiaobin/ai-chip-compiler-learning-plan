## 【错误】

#### 1. 拷贝被 `= delete` 时，不写 `noexcept` 的移动照样被容器使用，"直接编译不过"不成立
- **原文**："不写 `noexcept`，容器会默默退回拷贝——而我们的拷贝是 `= delete` 的，直接编译不过。"
- **依据**：本机实测：把 `Buffer` 的移动构造/移动赋值中的 `noexcept` 去掉（拷贝仍是 `= delete`），`std::vector<Buffer>` 的 `emplace_back` 触发扩容时可以正常编译并执行，且日志显示扩容搬运旧元素走的正是移动构造（`[move-ctor]` 出现，`std::move_if_noexcept` 在 `is_copy_constructible` 为 false 时返回右值引用，不会退回拷贝）。教程的因果链只在"拷贝可用"时成立：本机对照实验证明，对拷贝可用的类型（非 noexcept 移动 + 可用拷贝）扩容确实退回拷贝；但对本教程的 `Buffer`（拷贝已删除）这一前提不成立，"直接编译不过"是错误论断。同句前半句"`std::vector` 扩容时只有在移动构造保证不抛异常时才敢用移动"也属于过度推广（漏了"或类型不可拷贝"这一分支）。`src/Buffer.h` 注释"标准容器只对 noexcept 的移动放心（否则扩容时会退回拷贝以保证安全）"有同样的过度推广，但未断言编译失败。正确表述应为：移动构造非 `noexcept` 且拷贝可用时，容器扩容退回拷贝；拷贝被删除时即使不写 `noexcept` 也用移动（此时 `noexcept` 的价值是异常安全而非可编译性）。
- **置信度**：高。已在同版本 g++ 9.4.0/libstdc++ 上双向实验验证（非 noexcept + 删除拷贝 → 编译并移动；非 noexcept + 可拷贝 → 退回拷贝）；依据 C++ 标准 `std::move_if_noexcept`（[utility.swap]/相关及容器的 relocation 要求）语义。

#### 2. 图 2（02-copy-vs-move.svg）左侧析构顺序与 C++ 规则及正文相反
- **原文**："**图 2**：左右两幅对照同一块 `16 字节 @ 0x…ee0` 的命运。左（红）：隐式拷贝抄指针——两个对象的 `data_` 同时指向堆上这一块，两个析构函数各 `delete` 一次，运行期 `free(): double free` 崩溃。右（绿）：移动——`b` 接管指针、`a` 被清空成空壳，堆块自始至终只有一个主人，收尾只有一次 `delete`。底部是今天的 Rule of Five 清单：五个函数各有交代。"
- **依据**：SVG 中左侧面板（`images/02-copy-vs-move.svg` 第 52–53 行文本）将析构顺序标注为"`~a：delete[] 0x…ee0 ← 第一次`"在上方、"`~copy：delete[] 0x…ee0 ← 同一块，第二次！`"在下方。但按图中代码 `Buffer a(16, "a"); Buffer copy = a;`（同一作用域先构造 `a` 后构造 `copy`），C++ 规定析构按构造的逆序执行：`~copy` 先运行、`~a` 后运行——README 自己的 §3.1 代码注释也写明"~copy 先 delete 一次，~a 再 delete 一次 → double free"（README 第 54 行）。图与正文、语言规则相矛盾（虽然两次 `delete` 导致崩溃的结论不受顺序影响，但执行顺序画反了；顺带一提，本机复现的崩溃日志里两次 `[dtor]` 都打印名字 "a"，与析构顺序无关，不构成对图顺序的支持）。修复应交换图中两行或改正"第一次/第二次"的标注。
- **置信度**：高。析构逆序是 C++ 语言规则（[class.destroy]，同一作用域内构造的逆序）；与 README 第 54 行原文交叉比对确认。

## 【存疑】

#### 1. "所有权"定义按通用术语衡量过于绝对
- **原文**："**所有权**（ownership）：任意时刻，每块堆内存恰好有一个负责释放它的对象。"
- **依据**：这句话描述的是**独占**（unique）所有权的规则。作为术语定义过于绝对：共享所有权（`std::shared_ptr`、引用计数、GC）允许同一块堆内存有多个所有者，由"最后一个释放者"负责归还；第 9 节自己就把"引用计数"列为合法选项，说明作者知道反例存在。作为本教程/本项目的设计规则它成立且应遵守，但作为"所有权（ownership）"的一般定义需要加限定（如"独占所有权"或"我们采用的所有权规矩"），否则初学者把它当作术语的通用定义带走，到第 5 天学 `shared_ptr` 时会产生"书上说每块内存只能有一个主人"的困惑。
- **置信度**：高（共享所有权是标准反例，且教程 §9 已自证）；定级为存疑而非错误，因为小节标题"一句话立规矩"表明这是设计规矩的表述语境。

## 【建议】

#### 1. Rule of Five 一节的"编译器默认行为"表述可更精确，且漏了"std::move 退回拷贝"这个关键坑
- **原文**："昨天写了析构函数的那一刻起，编译器就不再替你生成可靠的拷贝和移动了。"
- **依据**：准确的规则分两半：用户声明析构函数后，(a) 隐式拷贝构造/拷贝赋值**仍然会生成**（自 C++11 起被标记为 deprecated，但从未从标准移除——这正是第 2 天 double free 得以发生的原因，也和 §3.1"不自己写，编译器就各生成一份默认的"自洽）；(b) 隐式移动构造/移动赋值**完全不生成**（被析构函数抑制）。"不再生成可靠的拷贝和移动"靠"可靠的"一词含糊带过，初学者容易读成"写析构后编译器不生成拷贝了"。本机实测验证：`struct D { ~D(); M m; };`（`M` 仅可移动）下 `D d2 = std::move(d);` 报 `error: use of deleted function 'D::D(const D&)'`，证明隐式移动确实不存在、`std::move` 退回选择拷贝构造——"写了析构后 `std::move(x)` 静默变成拷贝"是初学者必知且本节未明说的坑。另，§3.4"忘掉任何一行，缺的那个就退回编译器的危险默认"对两个移动槽位也不准确（移动槽位没有"危险默认"可退，缺了就是没有，`std::move` 落到拷贝上），括号里把它映射到第 6 节错误二（手写移动漏了清空两行）也不属于"退回默认"的情形。
- **置信度**：高（语言规则 + 本机 static_assert/编译实验双重验证）；归为建议，因为原文有"可靠的"限定词，不算硬错误。

#### 2. "19 条断言"与测试文件中实际的 `assert` 语句数（21 条）不一致
- **原文**："`tests/test_move.cpp`——19 条断言，把今天的所有权规矩逐条钉死："
- **依据**：`grep -c "assert(" tests/test_move.cpp` 实测为 21 条 `assert` 语句。编号 ①–⑲ 只标了 19 个检查点：⑩ 之后的 `assert(b.size() == 0);` 和 ⑰ 之后的 `assert(a.data() != nullptr);` 两条没有编号、被并入了前一编号。教程从顶部产出、§5.2、§8 验收到测试程序的打印（"all 19 assertions passed"）统一使用 19，若按语句数核对则对不上；初学者逐条数 `assert` 会得到 21 并怀疑自己抄漏/抄多。建议后续版本把编号补齐为 21 或明确"19 个检查点、21 条 assert 语句"。测试本身全部通过，不影响技术正确性。
- **置信度**：高（可机械复核）。

#### 3. 错误二的复现输出需要说明 stdout 缓冲问题，否则重定向运行时看不到完整日志
- **原文**："复现方法：复制一份 `Buffer.cpp`，删掉移动构造里的 `other.data_ = nullptr; other.size_ = 0;` 两行，然后编译运行："
- **依据**：本机实测：`abort()` 不会刷新 stdio 缓冲，当 stdout 不是终端（重定向到文件或管道）时，展示的那段"[ctor]/[move-ctor]/[dtor]…"日志会随缓冲一起丢失，`./err2 > log.txt` 只能看到 `free(): double free detected in tcache 2` 一行；直接在终端运行（行缓冲）才能看到完整日志。第 2 天 README 的错误二已明确记录"用 `stdbuf -o0` 关闭输出缓冲后的完整日志；直接运行时缓冲区里的日志会随 abort 丢失"，本节复现步骤没有沿用这个提示。输出本身真实（我用 `stdbuf -oL` 复现出逐行一致的日志，exit 134 也一致），仅复现说明缺一行关键操作提示。
- **置信度**：高（本机两种运行方式对照实测）。

#### 4. 对已释放指针的保存值做比较/打印，严格标准语义下是实现定义行为
- **原文**："        assert(c_old != c.data());   // ⑨ c 旧地址已不是它的"
- **依据**：`c_old` 保存的是已被 `delete[]` 的地址（失效指针值）。C++17 [basic.stc.general] 规定：对失效指针值，解引用和传给释放函数是未定义行为，**任何其他使用**（包括比较、传给 `printf` 打印——`main.cpp` 里 `printf("-- c 旧地址 %p 已归还...")` 同类）是实现定义行为。在本机 g++/Linux 上按地址值比较/打印完全正常（真实运行已验证），教程用法在本平台没有问题，且"保存旧地址对比"是常见调试手法；但既然本教程对标准语义一贯严谨（如对 `name_`"有效但未指定"的处理），建议后续版本加一句脚注说明这是平台层面成立的操作，避免读者在会对失效指针值触发陷阱的实现上照搬。
- **置信度**：中。标准条款（C++17 措辞"implementation-defined"）依据明确；但对该条款是否值得在入门教程中提及存在编辑判断空间，本平台行为已实测无害。
