## 【错误】

#### 1. 5.4 节实验指引无法复现其展示的"真实输出"
- **原文**：“先预测：日志会少掉什么？`alive` 何时归零？然后运行（我实际执行过）：”
- **依据**：正文只要求把 `Buffer* p = new Buffer(64, "heap");` 与 `delete p;` 两行换成 `Buffer h(64, "heap-to-stack");`（其余不动）。按此字面修改后在本机实际运行，第 3 段输出为：

  ```text
  == 3. 堆对象：new 出来的必须手动 delete ==
  [ctor] Buffer "heap-to-stack" 出生：在堆上拿到 64 字节 @ 0xaaab14302f50
  -- 刚 new 完，alive = 1 --
  -- delete 之后，alive = 1 --
  [dtor] Buffer "heap-to-stack" 销毁：归还堆上 64 字节

  main 结束，还活着的 Buffer 数量 = 0
  ```

  与教程所示输出（段标题为"== 实验：new/delete 换成栈对象 =="、两行 alive 文案为"-- h 在栈上 --""-- 作用域结束，alive = 0 --"、且 `[dtor]` 位于两条 alive 打印之间）不符：所示输出只能来自一个把段标题、printf 文案和打印位置都重写过的独立实验程序，而非正文给出的两行替换。字面替换还会出现一条误导性日志"-- delete 之后，alive = 1 --"（此刻既没有 delete、析构也尚未发生），与"先预测再运行验证"的教学设计直接冲突。应给出实验用的完整程序，或如实展示字面替换产生的输出。
- **置信度**：高。在同一环境按正文指引逐字执行（sed 精确替换两行）验证；其余实验细节为推断，但所示输出与字面替换输出不相容这一点由运行结果直接证明。

#### 2. 错误二"直接运行时日志会随 abort 丢失"对终端直跑不成立
- **原文**：“现象（用 `stdbuf -o0` 关闭输出缓冲后的完整日志；直接运行时缓冲区里的日志会随 abort 丢失，只剩最后一行报错）：”
- **依据**：stdout 连接终端时为行缓冲（isatty 为真），每条以 `\n` 结尾的 printf 在 abort 发生前就已逐行刷出；glibc 的 `abort()` 不会刷 stdio 缓冲。本机实测（与教程相同环境）：用伪终端运行（`script -qec ./double_free /dev/null`），`[ctor]` 与两条 `[dtor]` 全部可见，随后才是经无缓冲 stderr 打印的 `free(): double free detected in tcache 2`；只有把 stdout 接到管道或重定向（全缓冲，如 `./double_free | cat`）时，缓冲区里的日志才随 abort 丢失、只剩报错。即"直接运行（在终端里）"并不丢日志——教程把输出被管道/重定向接管时的现象当成了默认行为，在终端复现的读者会看到与描述不符的结果。建议改述为"输出重定向或经管道（全缓冲）时日志会随 abort 丢失；终端直跑因行缓冲通常能看到日志"。
- **置信度**：高。同一环境分别以伪终端（行缓冲）与管道（全缓冲）两种方式实测，结论互补且与 glibc 缓冲规则一致。

## 【存疑】

#### 1. "编译器用"必然崩溃"代替了"读到随机垃圾""把 g++ 的实现行为推广为编译器通则
- **原文**：“本机 g++ 9.4 检测到这种代码后直接把返回值替换成了空指针，所以 `p = (nil)`、一访问就段错误——编译器用"必然崩溃"代替了"读到随机垃圾"。”
- **依据**：前半句已在本机验证为真：按教程相同方式（`g++ -std=c++17 -Wall -Wextra`）编译同一程序，运行确得 `p = (nil)`、exit 139；反汇编 `make_buffer` 可见编译器在调用析构之前显式执行 `mov x19, #0x0`，即刻意以空指针作为返回值（g++ 9.4 · aarch64 实测）。但"返回局部对象地址"在 C++ 标准中是未定义行为，把返回值替换为空指针是 GCC 的实现选择而非语言保证；句末"编译器用……代替……"若读作编译器通则则过于绝对——换用其他编译器（如 Clang）或不同版本时，`p` 可能仍是失效的栈地址而非空指针，届时现象更接近"读到随机垃圾"而非必然崩溃。本机未安装 clang，无法实测其他编译器的行为。建议补一句"这是 g++ 的实现行为，不是标准保证"。
- **置信度**：g++ 9.4 空指针替换为高（运行结果与反汇编双重验证）；其他编译器行为为中（本机无 clang 未验证，仅依据"标准未定义 + 该行为非标准要求"推断）。

## 【建议】

#### 1. "命令附在每条里"未兑现，错误二、三与 3.4 节实验缺少可直接复现的完整材料
- **原文**：“以下三个错误都在本机真实复现过，报错原文照抄。复现用的是独立的单文件程序（和 `Buffer.cpp` 一起直接用 `g++` 编译），命令附在每条里。”
- **依据**：实际只有错误一附了编译命令。错误二给出了完整程序，但未给 g++ 编译命令与 `stdbuf -o0 ./double_free` 的运行命令；错误三只给 `make_buffer` 的"复现核心"，打印 `p = (nil)` 的调用方 `main` 从未出现（所示警告行号 `dangling.cpp:6:12` 对应的文件布局也无法从正文还原）；3.4 节异常实验同样只给输出未给代码。本人按合理解释重建这些程序后均复现成功（错误三重建布局下警告行号恰为 6:12、`p = (nil)`、exit 139），说明论断本身无误，补齐命令与代码后读者即可逐步复现。
- **置信度**：高。

#### 2. ctest"真实输出"省略末行且未标注省略
- **原文**：“100% tests passed, 0 tests failed out of 1”
- **依据**：本机实测 `ctest --test-dir build --output-on-failure`（教程给出的同一条命令）在该行之后还会输出一行 `Total Test time (real) = 0.00 sec`。5.3 节对构建输出专门注明了"configure 的中间行省略"，此处省略却未标注；建议补一句省略说明或收录该行，保持"真实输出"口径前后一致。
- **置信度**：高（实测）。

#### 3. 泄漏一节可补一句"进程退出后操作系统兜底回收"，防止误读泄漏的实际危害
- **原文**：“现象：程序正常结束，exit code = 0，但计数器说有对象没死：”
- **依据**：初学者容易从"exit 0 + 64 字节无声漏掉"推出"这次泄漏在本进程内已造成持续伤害"。事实是进程退出后操作系统会回收其全部地址空间内存，此刻真正可观察的危害是"析构没有运行"——若 Buffer 管理的是文件句柄、锁、全局统计这类非内存资源，同样写法就会在程序存活期间造成真实损害；对长期运行的进程（编译器常驻服务正是如此）内存才会持续流失。补一句能防止误读，并与本系列的编译器工程主线呼应。此条为内容补充建议，原文本身并无错误表述。
- **置信度**：高（进程退出回收地址空间是通用操作系统语义）。

#### 4. 图 2 阅读指引"顺时针"与图面布局不符
- **原文**：“看图时盯住序号：构造从 ① 顺时针排下去，析构完全倒着来。”
- **依据**：图 2 右下日志面板是自上而下的 ①–⑩ 纵向列表，整张图没有任何环形或顺时针动线，"顺时针"对不上任何可见路径，读者会短暂找不到所指。改为"自上而下按 ①→⑩ 排"或"沿日志列表向下读"更贴合图面。图中序号与真实日志顺序、析构倒序关系本身核对无误（③④⑦⑧⑩ 与正文一一对应），无技术问题。
- **置信度**：高（图文对照可查，属指引措辞与图不符，非技术性错误）。
