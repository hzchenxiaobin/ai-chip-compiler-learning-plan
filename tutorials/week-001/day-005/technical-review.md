# 第 5 天技术校对报告

> 校对环境（与教程声明一致）：Linux aarch64 · Ubuntu 20.04 · g++ 9.4.0 · CMake 3.20.5 · Ninja 1.10.0。
> 本机完整复跑了 README 5.1～5.4、第 6 节全部命令与程序（普通/ASan/UBSan 三种构建、9 个 bugs 程序、6 次距离实验），所有声明的输出、退出码、报告关键行均逐条核对通过；以下仅列出核对中发现的问题。

## 【错误】

#### 1. 测试注释声称"四个方向全部抛 out_of_range"，实际只断言了三个方向
- **原文**："// --- ③ 边界检查：四个方向全部抛 out_of_range ---"
- **依据**：`at()` 的边界检查条件有四个（src/Tensor.cpp:40：`i < 0 || i >= rows_ || j < 0 || j >= cols_`），但 tests/test_tensor.cpp 的 ③ 组只断言了三个方向：`at(2,0)`（i≥rows）、`at(1,3)`（j≥cols）、`at(-1,0)`（i<0）；j<0 方向（如 `at(0,-1)`）从未被测试，README 的节选里更只展示了两个 try 块。本机复跑 `./build/tests/test_tensor` 输出 "all 16 assertions passed"，确认实际断言内容如上。注释与测试事实不符：应补一条 `at(0,-1)` 断言，或把注释改为"三个方向"。
- **置信度**：高

## 【存疑】

#### 1. "比 unique_ptr 多一次分配（控制块）"对教程自己使用的 make_shared 情形不成立
- **原文**："比 `unique_ptr` 多一次分配（控制块）、多一份原子开销"
- **依据**：标准语义是 `std::make_shared<T>(args...)` 只做**一次**分配，把对象和控制块放进同一块内存（cppreference《std::make_shared》："This function typically performs a single allocation"）；3.1 节示例和 `bugs/exp_shared.cpp` 用的正是 `std::make_shared<Tensor>(std::move(a))`。只有从裸指针直接构造（`std::shared_ptr<T>(new T)`）才会比 `unique_ptr` 多出一次控制块分配。本机实测（重载全局 `operator new` 计数，g++ 9.4.0）：`make_shared<T>` 1 次、`make_unique<T>` 1 次、`new T` + `shared_ptr(p)` 2 次。按教程自己的示例代码，shared_ptr 的真实代价是"一次**更大**的分配＋原子计数"，而非"多一次分配"。建议限定为"非 make_shared 构造（如 `shared_ptr<T>(new T)`）时多一次分配"，或改为"控制块带来的额外空间（make_shared 时合并成一次更大的分配）＋原子计数开销"。
- **置信度**：高（对上述事实本身）；归入存疑是因为这是常见的教科书式简化，在 `shared_ptr(new T)` 情形下字面成立，只是在与本教程示例（make_shared）搭配时过于绝对。

## 【建议】

#### 1. 3.4 节把泄漏和 double-free 归入"踩到非法状态被当场抓获"，与 5.3 节自己的表述矛盾
- **原文**："越界、use-after-free、double-free、泄漏（配合 LeakSanitizer，下称 LSan）都是"踩到非法状态"被当场抓获"
- **依据**：泄漏不是"踩"出来的——LSan 在**进程退出时**扫描堆、对照根集清点（教程 5.3 节自己写明"ASan 构建（LSan 在进程退出时清点）"；本机复跑 bug_leak_asan 也确认报告出现在退出阶段，之前程序照常运行）；double-free 由 ASan 分配器的元数据/隔离区（quarantine）检查发现，也不是影子内存上的"踩到非法状态"。真正由影子检查在访问当场拦住的是越界和 use-after-free 两类。建议把"当场抓获"限定到后两者，泄漏单独立一句"由 LSan 在退出时清点"。
- **置信度**：高

#### 2. weak_ptr "不参与计数"表述过宽
- **原文**："解法是 `weak_ptr`（弱引用，不参与计数），第 10 天展开"
- **依据**：`weak_ptr` 的拷贝与析构会原子地增减控制块中的**弱引用计数**——教程 3.3 节自己也说控制块"里面存着强引用计数（`use_count()`）和弱引用计数"；`weak_ptr` 不参与的只是决定释放时机的强（所有权）计数。建议改为"不参与强引用（所有权）计数"。
- **置信度**：高

#### 3. "报告三要素"卡实为四项，与图 3 图注的"四要素"叫法不一致
- **原文**："右下角"报告三要素"卡对应真实报告的四个关键行"
- **依据**：同一 README 的图 3 图注写"报告四要素齐全"，而 images/02-ownership-asan-mechanism.svg 中该卡标题为"报告三要素（真实摘录）"、实际列出 4 行（`WRITE of size 4`／`bug_oob.cpp:13`／`Tensor.cpp:30`／`ABORTING, exit 1`，本机复跑逐一验证过均为真实输出）。"三/四"前后不一致，统一为"四要素"即可。
- **置信度**：高（不一致确凿；纯命名问题，不影响技术内容）

#### 4. 图 2 图注"三张卡的箭头都指向同一块堆数据"与 SVG 实际绘制不符
- **原文**："**三张卡的箭头都指向同一块堆数据**：Tensor 的数据只有一个，差别只在"谁负责释放"——这是 3.1 节契约的图形化"
- **依据**：核对 images/02-ownership-asan-mechanism.svg：六格"堆上 24 字节"数据条画在"独占"卡**内部**，只有一条 `data_` 箭头从该卡的代码框指向数据条；"借用"卡没有任何指向数据的箭头（只有文字），"共享"卡里 s1/s2 的箭头指向卡内自己的"同一块 Tensor 数据"文字框而非六格数据条。图注描述的"三张卡的箭头都指向同一块堆数据"在图中并不存在。建议改图注（如"三张卡描述的是同一块堆数据的三种持有方式"），或在 SVG 中补画借用/共享指向数据条的箭头。
- **置信度**：高（对 SVG 内容的核对；影响仅限图文一致性，不影响技术正确性）

#### 5. UBSan 的"计算"框架覆盖不了它自己举的"空指针解引用"例子
- **原文**："UBSan：抓**计算本身没有定义**的行为——有符号整数溢出、空指针解引用、移位越界这类"
- **依据**：空指针解引用属于**访问类** UB，由 `-fsanitize=undefined` 包含的 `null` 检查在解引用处拦截，不是"计算结果无定义"（有符号溢出、移位越界才是计算类 UB）；三个例子确实都在 `-fsanitize=undefined` 的覆盖范围内（本机已验证有符号溢出一例的真实输出）。建议把"计算"放宽为"操作/求值"（如"这步操作 C++ 标准没规定结果"），与后半句"这个计算的结果"同步微调。
- **置信度**：高（事实层面）；影响小，属表述精度问题

#### 6. 前置准备允许"任何支持 -fsanitize=address 的编译器"，但全部命令依赖 GCC 专属的 -static-libasan
- **原文**："构建环境同前四天（CMake ≥ 3.16、Ninja、g++ 或任何支持 `-fsanitize=address` 的编译器）"
- **依据**：`-static-libasan` 是 GCC 的选项（GCC 手册 gcc/Link-Options 有记载）；Clang 不接受该选项（Clang 默认静态链接 ASan 运行时，另有 `-shared-libasan` 做反向控制）。本机报错与修复均按教程复现成功（g++ 9.4.0），但读者若换用 clang，正文所有带 `-static-libasan` 的命令都会失败。建议在 5.3 节的说明框里加半句"该选项为 GCC 专属，Clang 用户直接去掉即可（Clang 默认就是静态链接）"。
- **置信度**：高（-static-libasan 为 GCC 专属）；中（Clang 端的具体行为未在本机实测，本机未安装 clang，依据为 Clang 官方文档对 ASan 链接方式的说明）
