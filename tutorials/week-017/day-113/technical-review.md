# 第 113 天技术校对报告

校对方式：在与冻结运行相同的机器上复核（aarch64 Linux、Python 3.11.4、llvmlite 0.50.0 内嵌 LLVM 22.1.0）。在 /tmp/opencode 临时目录完整重跑 `run_all.sh`，21 个产出文件与 `outputs/` 冻结版本逐字节一致；另做了 pass 隔离实验、TargetMachine 交换实验、LLVM 编号规则实验、"忘传值"负例实验来核实正文归因。无法离线核实的点在条目中明确标注。

## 【错误】
#### 1. 5.2 ③ 的代码注释把"分支变 select"归给 instcombine（实测归 simplifycfg）
- **原文**：“npm.add_instruction_combine_pass()      # ② 目标无关：常量折叠 / 加零消除 / 分支变 select”
- **依据**：在冻结环境上做单 pass 隔离实验（输入 outputs/step_dead.ll）：只跑 instcombine，结果仍是 4 个基本块、br＋phi 形态，没有 select；只跑 simplify_cfg，立刻得到 `%9 = select i1 %6, i32 %7, i32 %8` 并合并成 1 块。菱形→select（LLVM 里的 FoldTwoEntryPHINode 类变换）是 SimplifyCFG 的职责。该注释还与教程自己的正确表述冲突：§3.2 写"simplifycfg 证明 hi/lo/merge 菱形等价于一条 select"，5.2 末段写"4 块并 1 块来自 simplifycfg"。同句中"常量折叠 / 加零消除"归 instcombine 是对的（instcombine 单独运行即折叠 (2+3)×4、消 a+0，实测验证）；错的只有"分支变 select"。注意 pipeline.py 的 docstring 第 7 行也有同样措辞，本次按约束不改代码，仅留痕。
- **置信度**：高（本机单 pass 隔离实验复证，冻结输出可对账）。

#### 2. §3.2 声称"x86_64 想一条指令做条件选择也做不到"，与自家汇编证据和 5.3/常见错误 4 的正确归因矛盾
- **原文**：“x86_64 想一条指令做条件选择也做不到，所以是 5 条不是 4 条”
- **依据**：冻结输出 step_x86_64.s 里的 `cmovll %ecx, %eax` 就是单条指令的条件选择——与 aarch64 的 csel 同类（教程自己的图 5 图注也写"csel 一条完成条件选择"），所以"一条指令做条件选择做不到"不成立。5 条 vs 4 条的真实原因是教程在 5.3 与常见错误 4 里给出的那个：aarch64 的 subs 在算 a−20 的同时置位标志、csel 直接连用（比较免费搭车），而 x86_64 的 leal 不置位标志，比较必须单独一条 cmpl——多出的一条是"比较不能搭车"的代价，与能否单条做条件选择无关。若把"条件选择"读成"比较＋选择"整体，aarch64 也用了两条（subs＋csel），该句的因果同样不成立。
- **置信度**：中（取决于对"条件选择"一词的读法；但两种读法下该句的技术内容都不对，且与教程其余三处的正确表述不一致）。

#### 3. §5.3 range 推导"假分支 a−20 ≤ 0（a=20 时取最大 0）"忽略 i32 回绕，与同 bullet 的 nuw 注记自相矛盾
- **原文**：“真分支 a+20 ≥ 41（a=21 时取最小）、假分支 a−20 ≤ 0（a=20 时取最大 0）”
- **依据**：i32 的 add/sub 无 nsw/nuw 标志时按模 2³² 回绕，这是定义行为。假分支 a≤20 时，a∈[INT_MIN, INT_MIN+19] 的 a−20 回绕成 [INT_MAX−19, INT_MAX] 的正数：例如 a=INT_MIN 时 @step 实际返回 INT_MAX−19（不是 ≤0 的数），"假分支 a−20 ≤ 0"与"取最大 0"（实际最大值是 INT_MAX，在 a=INT_MIN 处取得）都不成立。同一个 bullet 末尾教程自己写了"（a 接近 INT_MIN 时 a−20 会回绕）"，前后矛盾。最终结论不受影响——回绕落点仍落在并集 [41, +∞)∪(−∞, 0] 内，所以 sccp 给出的 range(i32 41, 1) 与"1..40 不可能是返回值"是对的（LangRef："The pair a,b represents the range [a,b). … The range is allowed to wrap."）——但把"忽略回绕的推导"当方法教是危险的：例如对 f(a)=a>0?100:a−20 用同样的推导会漏掉真实值域里的 [INT_MAX−19, INT_MAX] 段。第 3 行今日目标和 5.4 对照 A 使用了同一推导句式，应一并修。修法不是改结论，而是把中间步骤改成"忽略回绕时……回绕的极端取值仍落在并集内，故值域不变"之类的限定表述。
- **置信度**：高（模运算可直接手算验证；range(i32 41, 1) 本身与冻结输出一致且语义正确）。

#### 4. 常见错误 2 的"现象"描述与 step.ll 的实际编号不符（5 与 6 之间没有空隙）
- **原文**：“块标签从 6: 蹦出来，5、6 之间还有空隙。”
- **依据**：step.ll 的槽位池 0..11 完全连续，没有任何空隙：%0=参数、%1=入口块（不打印）、%2~%5=入口块四条指令、6=^hi、%7、8=^lo、%9、10=^merge、%11=phi。%5（icmp）之后紧接着就是槽位 6——"5、6 之间还有空隙"不成立。读者真正会困惑的"空隙"只有两处：%0→%2（缺的 %1 是入口块），以及块标签 6→8→10（中间的 7、9 分别是 %7、%9 两条指令结果）。opt_before_step.ll（真 LLVM 重排版）编号与 step.ll 完全一致，可逐行核对。属低严重度错误，但"现象"小节的职责就是准确描述输出。
- **置信度**：高（直接对照 outputs/step.ll 与 outputs/opt_before_step.ll）。

#### 5. §5.1 目录树中对照实验产物计数"IR×4＋汇编×4"与实际 10 个文件（IR×6＋汇编×4）不符
- **原文**：“const5 / dead 两组对应产物（IR×4＋汇编×4）”
- **依据**：实际两组对照产物共 10 个文件：汇编 4 个（const5/dead × aarch64/x86_64）加上 IR 6 个——step_const5.ll、step_dead.ll（导出的 .ll）与 opt_before/opt_after × 2 组。按目录树自带的口径合计（主产出 3＋优化前后 2＋两目标汇编 2＋变体 8＋stats 3＋日志 1）只得 19，与同一棵树写的"outputs/ # 21 个文件"（实际 21，ls 与临时目录重跑均验证）自相矛盾，差额正是没被计进"IR×4"的两条导出 .ll。建议改为"IR×6＋汇编×4"或把两条导出 .ll 单列。
- **置信度**：高（ls 计数与重跑产物清单一致）。

## 【存疑】
#### 1. "无溢出的 x≥21"这一动机性解释无法证实，且按 x86 比较语义找不到成立的读法
- **原文**：“x>20 写成无溢出的 x≥21”
- **依据**：把 `icmp sgt x, 20` 发成 `cmpl $21, %edi`＋cmovll（x>20 等价于 x≥21）这一改写本身是真实且被冻结输出证实的（step: $21；const5: $26）。但"无溢出"的说法有问题：x86 有符号比较用 SF/OF 组合判读，`cmp` 计算的差无论是否回绕，"大于/小于"判定都正确——两种写法都不存在需要规避的溢出；且当常数取 INT_MAX 时 C+1 反而不可表示，谈不上更"无溢出"。本环境无 LLVM 源码可查，未能核到该改写的真实动机（推测是后端把"大于＋常数"规范化为"小于＋常数＋1"的偏好，属代码生成规范化而非溢出规避）。同一措辞还出现在 5.4（"x>25 的无溢出写法"）、图 5 图注（"= 20+1 的无溢出写法"）和练习 2(d)（"按'x>30 的无溢出写法'算"）——按 C+1 规则预测立即数是对的，但建议把"无溢出"改为"等价写法"或"规范化写法"，除非能给出依据。
- **置信度**：中（改写事实为真、已验证；"无溢出"动机无法证实，且与比较指令语义不相容——不排除作者另有所指，但找不到自洽读法）。

#### 2. "那 3 个 pass 只读 IR 不看目标，所以挂在哪个目标上结果都一样"作为一般性论断过强
- **原文**：“但那 3 个 pass 只读 IR 不看目标，所以挂在哪个目标上结果都一样”
- **依据**：就本例我实测成立：把 PassBuilder 分别挂在 aarch64 与 x86_64 的 TargetMachine 上（其余条件相同），跑出的优化后 IR 逐字节一致（含 range(i32 41, 1) 与 add nuw）。但"不看目标"作为一般性表述过强：在新 PM 里 instcombine/simplifycfg 会消费由目标派生的 TargetLibraryInfo/TargetTransformInfo 分析（如按 triple 识别 libc 函数、部分折叠决策带成本模型），换 libc 或目标（例如换成 windows 目标）时这些 pass 的输出有可能不同。本实验在两个 linux-gnu 三元组间通常不会有差异，所以教程"换一个 TargetMachine 挂着，跑出的优化后 IR 一模一样"对本例是可复现事实；但"这正是'目标无关'的可操作定义（不依赖，而不是碰巧相同）"把单例实验提升成了一般性定义——更稳妥的说法是"这三类 pass 属于目标无关层：本例实测不依赖目标；它们仍会读由目标派生的库/成本信息，复杂 IR 上可能有差异"。未能在本环境构造出两个 linux 目标间结果不同的反例 IR。
- **置信度**：中（本例结论已实测；一般性论断基于对 LLVM pass 依赖（TLI/TTI）的了解，未能离线给出具体反例）。

## 【建议】
#### 1. "SSA 值"的统计口径未说明（不含函数参数 %0），初学者自己数会得到 8
- **原文**：“优化前 @step：4 块 / 11 条指令 / 7 个 SSA 值”
- **依据**：pipeline.py 的 stats() 只数"有结果的指令"（以 % 开头的行）。但在 LLVM 术语里函数参数 %0 同样是 SSA 值，按槽位数 %0、%2~%5、%7、%9、%11 共 8 个。教程在常见错误 3 里专门讲了"指令数"的口径问题，却没有给"SSA 值"口径留同样的注解；建议在 5.2 ③ 首次出现该数字处加一句"SSA 值＝有结果的指令数（不含参数 %0）"，避免验收时对不上账。
- **置信度**：高（口径可直接从 stats() 源码读出；是否需要补充属编辑判断）。

#### 2. 入口块"从不显示"只给了现象没给原因（入口块不可作为跳转目标），这是初学者必知的一条规则
- **原文**：“入口块占 %1 但从不显示，于是第一条指令结果是 %2”
- **依据**：LLVM 文本 IR 里入口块标签省略的深层原因是：入口块不可能有前驱（不允许任何跳转指向它），因此永远不需要打印标签供别处引用；LangRef 也明确"basic blocks and unnamed function parameters are included in this numbering"（若入口块无名而参数都有名，入口块甚至拿 0 号）。最优的证据就在冻结输出里：opt_before_step.ll 的前驱注释写着 "; preds = %1"——那个从不显示的 %1 在这里现身。补一句因果，读者就能从"记规则"变成"推规则"，也顺便解释了为什么手工写 .ll 时不能跳转入口块。
- **置信度**：高（本机实验验证 %1 保留给入口块：把首条指令写成 %1 会被真 LLVM parse 拒绝；LangRef 原文已核对）。

#### 3. §5.4 说 const5 变体"其余逐字不变"，实际还改了常量名与值名（%c4→%c5、%s20→%s25）
- **原文**：“函数改名 @step5，其余逐字不变”
- **依据**：diff step.mlir 与 variants/step_const5.mlir：除函数名与文件头注释外，还改了 `%c4 = llvm.mlir.constant(4 : i32)`→`%c5 = …(5 : i32)`，以及 %s20→%s25（含 4 处引用）。语义上确实只是"乘数 4→5"，但"逐字不变"字面不成立；建议改为"除乘数 4→5 及随之改名的 %c4/%s20 外不变"。
- **置信度**：高（diff 可证）；影响小。

#### 4. 图 1 图注的方位词（左列/右列/底部）与 01-overview.svg 的实际布局对不上
- **原文**：“看三处——**左列**是前 16 周在 MLIR 里搭起的四层”
- **依据**：01-overview.svg 里四个 MLIR 层画在顶部一排四卡（不是"左列"）；"右列是门后的世界（LLVM IR 和汇编/机器码）"实际是下方并排的两张卡；"底部标出那扇门"的 mlir-translate 箭头位于中下部（Dialect 框与 LLVM IR 卡之间），底部一行其实是第 17 周路线。读者按图注找"左列"会找不到对应物。若把"左列/右列"理解成"门左侧/门右侧的世界"勉强可通，但建议把方位词改成与图一致（顶部一排/中间/下方两卡/底部路线）。
- **置信度**：中（图与注的物理布局不一致是事实；是否算措辞风格问题取决于读法）。
