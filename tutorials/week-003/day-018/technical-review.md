- **置信度**：高（Day 17 的 S1 起编号已核对 day-017/README.md 原文；不确定点仅为作者是否默想 0 起编号，但该编号法在两天教程中均无定义，且与被引用日的惯例相反）。

## 【存疑】
#### 1. "LLVM、MLIR 的标准做法"与两者现行实现不符，表述过于绝对
- **原文**：“它是教科书和工业编译器（LLVM、MLIR）的标准做法”
- **依据**：已核对 llvm-project 主线源码：LLVM 现行支配树构建基于 Semi-NCA 算法（`llvm/include/llvm/Support/GenericDomTreeConstruction.h` 文件头注释明确写 "construct immediate dominator information … based on the Semi-NCA algorithm"，引 Georgiadis 2005）；MLIR 的 `DominanceInfo` 直接实例化 `llvm::DominatorTreeBase<mlir::Block>`（`mlir/lib/IR/Dominance.cpp`，`domTree->recalculate(*region)`），走同一条 Semi-NCA 构建路径——两者都不再用教程这里的"全集初始化 + 交集迭代"算法。迭代方程确实是教科书经典写法、曾是 LLVM 多年前的实现、至今仍被不少编译器采用，但把 LLVM、MLIR 并列为该迭代法的"标准做法"已经过时。建议弱化为"教科书标准做法，工业编译器广泛采用（LLVM 历史上长期使用，现行实现改为 Semi-NCA）"。
- **置信度**：高（直接核对 raw.githubusercontent.com 上 LLVM/MLIR 主线两份源文件）。

#### 2. CHK 论文年份"2001 年"未能在线核实
- **原文**：“Cooper–Harvey–Kennedy 2001 年把它整理成工程上最常用的迭代形式”
- **依据**：Cooper–Harvey–Kennedy《A Simple, Fast Dominance Algorithm》是 Rice 大学技术报告，流传版本有 2001 与 2006（修订版）两种署名年份，不同文献引用不一。本次尝试在线核实未成功（Rice 作者主页上的 PDF 返回 404，DBLP 与 Semantic Scholar API 拒绝访问，Wikipedia 抓取超时），无法确认"2001 年"是否准确，按规则明确说明：未验证。建议去掉精确年份（写成"Cooper–Harvey–Kennedy 的技术报告"）或补一个可溯源出处。
- **置信度**：低（年份未核实；不能排除作者所据版本确实署 2001）。

## 【建议】
#### 1. "CSE/融合可能改变支配关系"的因果关系不准确
- **原文**：“任何改图的操作（比如 CSE 把使用替换成别处定义的等价值、融合把计算挪进别的块）都可能改变支配关系”
- **依据**：CSE 把使用替换成别处定义的等价值、融合把计算挪进别的块，这两类操作本身不增删 CFG 的边或块，块级 Dom 集不变；真正变化的是"哪个定义喂给哪个使用"，即"定义支配使用"这条合法性判定的结果变了，而不是支配关系（Dom 集）变了。直接改 Dom 集的是改 CFG 的操作（如本实验加边 `B2→B6`、删块、并块）。结论"改完必须重查"正确且重要；建议把因果拆成两层表述：改 CFG 会改 Dom 集，改 def-use（CSE/搬移）会改判定结果，两者都要求重查。
- **置信度**：高。

#### 2. 块级"定义支配使用"规则缺同块内顺序的提醒
- **原文**：“**每个使用，都必须被它的唯一定义支配。**”
- **依据**：教程全程按块粒度判定（`d ∈ Dom(u)`）。当定义与使用位于同一个块时，块支配它自己，`d ∈ Dom(u)` 自动成立——但同块内"使用写在定义前面"仍是非法 SSA，此时必须叠加 Day 17 的语句顺序检查。当天脚本也查不出这种情况：`check_def_dominates_use` 只比较块级 Dom，`DEF_USE` 模型不记录块内语句顺序。真实编译器对这条规则是两层的：MLIR 的 `properlyDominatesImpl` 对同块情形专门用 `isBeforeInBlock` 要求定义先于使用（`mlir/lib/IR/Dominance.cpp`，已核对源码）。这是初学者必知的坑：块级支配不能替代块内顺序。建议在 3.4 节或第 6 节补一句"定义与使用同块时，还要沿用 Day 17 的顺序检查"。
- **置信度**：高（脚本行为经代码审查确认；MLIR 行为经源码核对）。

#### 3. 选做挑战的"实测结果"描述不完整
- **原文**：“我实测的结果是：未通过的报错消失，取而代之的是一行"多处定义，汇合处需要 φ 函数选择版本"的提示”
- **依据**：本地复现（Python 3.11.4，把 B3 行改成 `(["b", "t"], ["x"])` 后运行）：`[5]` 的完整输出除该提示外还会打印"通过：每个使用都被唯一定义支配。"，且退出码变为 0。注意脚本对多处定义的名字是直接跳过支配检查（`len(sites) > 1` 走 notes 分支、不进 problems），所以这行"通过"对 `t` 并不成立——`t` 的两个定义（B2、B3）都不支配 B5（Dom(B5)={B0,B1,B5}），不插 φ 的话该使用仍是非法的。建议补全实际输出（含"通过"行与退出码 0），并点明该提示是"跳过检查、交给 φ 处理"，避免读者误以为检查真的通过。
- **置信度**：高（本地复现运行）。

#### 4. 错误二的复现指令未说明只改初始化那一处
- **原文**：“我把副本里 `set(order)` 改成 `set()` 后带 `--loop` 运行，脚本当场崩溃”
- **依据**：仓库文件里有两处 `set(order)`：第 78 行初始化（`dom = {b: … else set(order)) for b in order}`）与第 87 行循环体（`new = set(order)`）。只把初始化那一行改成 `set()` 才能复现教程展示的全部现象（`--loop` 打印完 B0 行后崩溃于 `idom_of` 的 `max()` 空序列，Traceback 行号 304/270/149 与仓库文件一致；默认菱形 `[4]` 仍报"一致"）——两种情况均已实测。若两处都改（例如做全局替换），默认模式也会当场崩溃，与"这个 bug 在没有回边的菱形上完全隐藏"的说法矛盾。建议把指令写明："只把初始化那一行的 `set(order)` 改成 `set()`，循环体里的 `new = set(order)` 保持不动"。
- **置信度**：高（两种改法均实际运行验证）。
