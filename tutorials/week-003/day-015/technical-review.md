## 【错误】
#### 1. 声称「真实日志的完整输出」的引文与真实日志不一致
- **原文**：“两份 CFG 结构完全相同（4 块 4 边），diff 只有一行：”
- **依据**：README 5.4 节称该代码块是「真实日志（`experiments/threshold.log`）的完整输出」，但该行与日志实际内容不符：`experiments/threshold.log` 第 8 行（以及 `threshold_ab.cpp` 中对应的 `printf`）原文是「两份 CFG 的结构完全相同（4 块 4 边的菱形），diff 只有一行：」，比 README 引文多了「的」和「的菱形」两个词。我在临时目录重跑 `bash experiments/threshold.sh` 并与冻结日志逐字节 diff（完全一致），证明差异出在 README 引文一侧。教程的核心卖点之一是「全部真实执行」，把编辑改写过的文本标注为真实完整输出违反了这一点（SKILL.md 质量底线也禁止不按实际结果呈现执行输出）。修复只需把该行改回与日志逐字一致。
- **置信度**：高（直接 diff 验证，重跑结果与冻结日志一致）。

#### 2. 代码注释对 LLVM 的描述失实：IRBuilder 并不会自动放终结符占位
- **原文**：“**错误一：块尾忘了写终结符——「单一出口」被破坏（`bugs/err_missing_term.cpp`）**”
- **依据**：该行引用的 `bugs/err_missing_term.cpp` 头部注释称「LLVM 里 builder 会自动放终结符占位，我们的迷你 CFG 选择把它留给 Verifier 点名」。查 LLVM 官方源码（llvm-project main 分支）：`llvm/include/llvm/IR/IRBuilder.h`（3112 行）中没有任何自动插入终结符的逻辑，终结符只能通过显式的 `CreateBr`／`CreateRet` 等方法创建；而 `llvm/lib/IR/Verifier.cpp` 第 250～257 行明确先检查「First check that every basic block has a terminator」，缺失时报告 “Basic Block in function '...' does not have terminator!”；LangRef 也只规定「every basic block in a program ends with a 'Terminator' instruction」并说明由验证 pass 保证 well-formed。也就是说 LLVM 的做法与迷你 CFG 完全一致（都留给 Verifier 点名），注释把两者对立起来的说法是错的，会误导初学者对真实 LLVM 行为的预期。
- **置信度**：高（已核对 LLVM main 分段源码 IRBuilder.h 与 Verifier.cpp，错误消息原文可在 Verifier.cpp 第 257 行找到）。

#### 3. 图 3 计分板写「两个 CFG 同构」，但两张图并不同构
- **原文**：“两个 CFG 同样是 **4 块、5 条指令、4 条边**——有没有环不是块数决定的，是边决定的”
- **依据**：`images/03-paths-and-loop.svg` 第 107～108 行在「4 块 · 5 指令」下标注「两个 CFG 同构」。同构（isomorphism）是精确的图论术语：同构映射保持邻接关系，因此也保持环的存在性。菱形 `leaky-scale` 是无环图（b0→b1/b2→b3 的菱形），循环 `sum-1-to-n` 含有 b1→b2→b1 的有向环，二者不可能同构；度数序列也对不上（菱形中出度 2 的块 b0 入度为 0，循环中出度 2 的块 b1 入度为 2）。README 正文自己的表述（本条原文引用的那句「同样是 4 块、5 条指令、4 条边——有没有环不是块数决定的」）才是准确的：两张图只是**计数相同**，结构并不相同——这正是当天要教的重点，图里用「同构」一词反而削弱了这一课。建议把图中标注改为「两个 CFG 规模相同」或「同样 4 块·5 指令·4 边」。
- **置信度**：高（无环图与有环图不同构是图论基本事实；两图度数序列亦不一致）。

## 【存疑】
#### 1. leader（首指令）的三条规则少了「紧跟无条件跳转的指令」
- **原文**：“编译原理教材里把「每块的第一条指令」叫**首指令（leader）**：入口指令、跳转目标、以及分支指令的下一条，各自开启一个新块。”
- **依据**：经典教材（龙书 Aho/Sethi/Ullman，及与其一致的通行表述，可参见 GeeksforGeeks「Basic Blocks and Control Flow Graph in Compiler Design」）给出的三条规则是：(1) 中间代码的第一条指令是 leader；(2) **条件或无条件跳转的目标**是 leader；(3) **紧跟在条件或无条件跳转之后**的指令是 leader。教程句中「分支指令的下一条」按本教程自己的用词习惯（jump＝无条件跳、cond_branch＝条件跳，全文严格区分「跳」与「分支」）最自然的读法是「条件跳转的下一条」，漏掉了「紧跟无条件跳转的指令也是 leader」这半条——在经典三地址码划分算法里这决定切分点。教程同时声明「今天我们手工建块，不写自动划分」，且本教程的 IR 每块必须以终结符收尾、不存在块间 fall-through，所以对本日例子无实际影响；但既然句子明确援引教材，就应与教材一致。若作者本意是「分支指令」广义涵盖无条件跳转，则建议改为「跳转/分支指令的下一条」消除歧义。
- **置信度**：中（教材规则的表述已核实；是否构成错误取决于「分支指令」的读法，按教程自身术语习惯更可能被误读）。

#### 2. 「真实 JIT 里同样要有 step/time limit 保护」是过度推广
- **原文**：“真实 JIT 里同样要有 step/time limit 保护”
- **依据**：主流 JIT（HotSpot、V8、LLVM ORC）执行的是用户程序语义：用户写出死循环是合法程序，JIT 编译出的机器码**没有**也不应有逐步/限时刹车——终止由嵌入方通过中断/看门狗等外部机制处理，而非 JIT 内建的 step limit。与「燃料」最接近的真实实践是可选的沙箱/嵌入特性（如 Wasmtime 的 fuel metering／epoch interruption，属于 opt-in 配置而非 JIT 必备项），以及**编译器内部**的解释执行工具（常量折叠、符号执行、部分求值）为避免不自终止而设的步数预算——后一种才是与 mini-cfg 解释器真正同类的场景。建议把括号内容改为「编译器内部的模拟执行（常量折叠、解释求值）同样要带步数/时间预算」或「沙箱运行时（如 Wasmtime）提供可选的 fuel 机制」。未能逐个核对各家 JIT 官方文档，无法 100% 排除个别 JIT 内建 step limit 的例外，故列为存疑。
- **置信度**：中（主流 JIT 行为属于编译器领域常识，方向把握大；但本轮未能逐一取得各 JIT 官方文档佐证，Wasmtime fuel 文档 fetch 失败）。

#### 4. 「无前驱 ⇒ unreachable」的标注在级联死代码场景会漏报
- **原文**：“定位：preds 表里搜 `unreachable`；或对照「文本 CFG 里的块」和「执行路径里的块」。”
- **依据**：`Cfg.cpp` 的 `preds_succs_to_string`／`to_string` 只给「前驱为空且非入口」的块标 unreachable，这是「从入口不可达」的充分不必要条件：若某死块还有一条指向 b5 的边，b5 有前驱（不会被标注）但从入口同样不可达。此时「preds 表里搜 unreachable」这条定位法会漏掉 b5，只有括号里的第二种方法（对照执行路径）能发现。对第 6 节错误四的单一孤块例子完全够用，但初学者把死代码链起来时会产生「为什么这个死块没被标注」的困惑。建议在正文或第 25 天 DCE 伏笔处补一句：零前驱只是不可达的最简单形态，一般可达性要从入口做遍历。
- **置信度**：高（依据 `Cfg.cpp` 第 270～275 行的判定逻辑；中作为「是否值得写进教程」的判断）。
