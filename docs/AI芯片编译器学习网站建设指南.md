## 执行摘要

这个项目不需要把 168 篇教程搬入重型 LMS，但目标形态明确调整为**动态 Web 应用**。仓库中的 Markdown、图片、代码和冻结产物继续由 Git 管理，现有 Python 解析与校验逻辑可以复用；网站运行则改为 Django 应用、MySQL、Redis 和对象存储，由服务端提供页面、搜索、账号、学习进度和后续证据服务。GitHub 只承担代码协作、教程版本管理和可选 CI，不再使用 GitHub Pages 托管网站。公开教程仍允许免登录阅读，登录后的学习记录从首版起保存到 MySQL，并通过 revision 与 `If-Match` 处理多标签页和多设备并发([仓库 README](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/blob/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/README.md), [现有构建器](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/blob/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tools/build.py))。

网站的产品目标也不应是“把文章搬到网上”，而应是帮助学习者持续完成一条有工程证据的能力路径：从 Modern C++、Tensor 与图 IR，经过 MLIR、图优化、Lowering、Tiling、LLVM 和 Runtime，最终交付可复现的 `minic` 端到端编译器及项目文档。普通课程平台常用的视频播放、营销页和结业证书不是本项目的首要能力；**下一步该学什么、今天需要交付什么、实验怎样证明正确、性能数字怎样复现、卡住后如何回到路径**，才是网站需要优先回答的问题。每周第 6 天集成、第 7 天复盘，以及第 155—159 天的项目文档、第 160 天的干净环境复现、第 167—168 天的表达与最终验收，已经提供了很好的学习骨架，网站应把它显性化而非另造一套课程体系([仓库 README](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/blob/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/README.md), [第 160 天](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-023/day-160), [第 168 天](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-024/day-168))。

## 1. 项目基线：不是“从教程到静态页”，而是“从教程仓库到动态学习产品”

### 1.1 仓库现有资产与缺口

截至分析快照，仓库包含 168 个日课 README、554 个 SVG 文件和 2,780 个位于各日 `code/` 下的代码及产物文件，其中 111 天提供 `run_all.sh`，`outputs/` 中有 1,568 个冻结产物文件。2,780 是源码、脚本、配置、IR、测试报告和冻结产物的总数，不等于独立程序数；168 篇正文合计约 270.9 万个字符。上述数字来自指定提交的只读扫描，后续提交会改变统计结果([仓库快照](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72), [教程目录](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials))。

现有 `tools/build.py` 已解决标题、周/日编号和本地图片校验，但目标架构不再把生成静态 HTML 作为发布终点。改造时抽取其中的内容解析与校验函数，形成可重复执行的教程导入器：每次指定 Git commit 都生成不可变内容版本，校验通过后写入 MySQL 读模型，并把源码包发布到对象存储。现有前端脚本中的代码复制、图片缩放、页内目录、明暗切换和返回顶部可以复用，但学习进度、练习状态、实验结果和复习记录改由服务端 API 与 MySQL 持久化([构建脚本](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/blob/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tools/build.py), [前端脚本](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/blob/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/static/js/vp-solution.js))。

| 维度 | 仓库已经具备 | 动态网站仍需补充 | 建设判断 |
| --- | --- | --- | --- |
| 内容源 | 168 篇 Markdown；周/日目录一致；目标、时间、前置、产出齐全 | 内容版本、日课元数据、技能标签、导入事务 | 保留 Git 权威源，数据库只保存可重建读模型 |
| 视觉与代码 | 554 个 SVG；代码、IR、测试和冻结输出丰富 | 源码包对象存储、版本化下载、GitHub 深链 | P0 优先，减少手工找文件 |
| 应用运行 | Python 解析逻辑、静态资源、Actions 经验 | Django、MySQL、Redis、Nginx、部署与监控 | 动态应用从 P0 建立，不沿用 Pages |
| 学习路径 | 六阶段、24 周、每周集成与复盘、最终项目 | 服务端“继续学习”、前置检查、周任务和证据图 | 用稳定 day_id 关联内容和个人数据 |
| 练习与验收 | 日课练习、验收清单、一键脚本和真实输出 | 账号、进度 API、证据导入、卡点、阶段面板 | 区分“读过”“自报”和“已复验” |
| 用户与数据 | 本地主题偏好 | 注册登录、会话、MySQL 学习数据、导出与删除 | 公开阅读免登录；保存进度需要账号 |
| 社区与运营 | GitHub 仓库与 Issues | 内容后台、讨论入口、授权后的学习分析 | 社区后置，后台仅管理员可用 |

### 1.2 产品定位与核心学习者任务

建议把网站定位为“**AI 芯片编译器项目制学习工作台**”，而不是“168 天文章合集”或泛化 MOOC。目标用户是愿意通过编码、IR 观察和性能实验系统学习编译器的人，他们可能具备不同 C++ 与工具链基础，也可能在 Linux、WSL 或 macOS 上遇到不同环境问题。网站需要同时服务首次来访者、正在按日学习的人和回来查找某个 Pass 或排错方法的人：首次来访者要判断路线是否适合，持续学习者要迅速回到当前任务，复习者则要按概念、错误信息和项目阶段找到证据。

核心任务可以写成五个用户故事：作为新学习者，我能在开始 Day 001 前检查环境和时间投入；作为持续学习者，我打开首页就能看到“继续 Day N”和本周集成/复盘节点；作为实践者，我能下载当日代码、运行 `run_all.sh` 并导入结果；作为复习者，我能按 MLIR、Tiling、Runtime 或错误信息检索并加入复习；作为项目完成者，我能汇集代码提交、测试报告、性能口径和五份项目文档，形成可展示的学习档案。证书可以作为可选的结果展示，但**可复现的项目证据比站内证书更贴合该仓库最终目标**([最终项目说明](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/blob/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/README.md), [第 159 天性能材料](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-023/day-159))。

## 2. 市场调研：主流学习网站的功能与本项目取舍

### 2.1 代表性平台能力对比

市场调研显示，成熟产品通常围绕五条主线展开：结构化内容、明确进度、练习反馈、持续激励和学习支持。Coursera 的学习仪表盘强调课程进度、逐周任务和“下一步”入口；Duolingo 将连续学习记录与弹性保护结合；freeCodeCamp 把短讲、理解检查、逐步工作坊、空白实验、复习、测验和综合项目分层；Moodle 与 LearnDash 则提供前置条件、定时释放、成绩、证书和报表等通用 LMS 能力。它们可以证明某些交互模式已经成熟，却不能直接证明这些功能适合 AI 编译器教程([Coursera](https://blog.coursera.org/new-progress-tracking-features-on-coursera/), [Duolingo](https://blog.duolingo.com/how-duolingo-streak-builds-habit/), [freeCodeCamp](https://www.freecodecamp.org/news/christmas-2025-freecodecamp-curriculum-updates/))。

本项目的差异在于学习成果主要产生于本地工具链，而不是网页视频或选择题。Day 029 已要求 LLVM 18、`mlir-opt`、FileCheck 和 JIT，后续还涉及 MLIR/Lowering、AOT/JIT、性能回归和干净环境复现；这与完全在浏览器内运行的入门编程练习不同。因此，市场功能需要经过“是否增强工程学习闭环”的筛选：保留下一步导航、分层练习、反馈与复习，谨慎采用每日强制解锁和公开排行榜，不把通用自动判题或浏览器 IDE 当作首版前提([Day 029](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-005/day-029), [freeCodeCamp 课程结构](https://www.freecodecamp.org/news/freecodecamp-turns-10-major-curriculum-updates/))。

### 2.2 对本项目最重要的六条启示

第一条是“下一步”应强于“总目录”。168 个卡片本身就是认知负担，首页应根据学习者状态优先展示当前日、待补实验和本周复盘，完整六阶段目录退居第二层。第二条是进度需要多维表达：阅读完成、练习通过、实验已运行、证据已导入和周验收通过不是同一件事；若只显示一个百分比，会误导学习者把滚动到文末当作掌握。第三条是反馈必须尽量靠近任务，练习解析、常见报错和环境检查应在日课页面形成固定区域，而不是让学习者离开网站重新寻找。

第四条是激励应允许恢复。连续学习可以记录，但编译器实践可能因环境、工作或个人安排中断，网站要提供“从上次继续”“本周补做哪一个关键产出”和“降低节奏”的路径。第五条是社区要围绕具体工件组织，例如“Day 097 某组 tile 为何结果不同”比泛泛讨论更有价值。第六条是学习分析必须服务改进内容：搜索无结果、环境检查失败、某日反复卡住和证据导入失败，比单纯页面浏览量更能指导教程维护。上述属于产品建议，不是对平台效果的保证；上线后仍需用本站数据验证。

## 3. 建设方案决策与推荐架构

### 3.1 方案比较：动态学习应用优先

决策维度仍为 Markdown 迁移效率、每日路径适配、上线速度、学习闭环完整性、运维友好度、扩展与数据控制，但“动态网站、可引入 MySQL、不基于 GitHub Pages”成为硬约束。现有静态站增量增强、纯文档站和托管 Pages 不再进入最终推荐，只作为内容解析和页面资产来源。

| 方案 | 动态能力 | 内容复用 | 运维成本 | 对本项目的结论 |
| --- | --- | --- | --- | --- |
| Django＋MySQL＋Redis | 账号、进度、搜索、后台和 API 一体 | 可复用 Python 解析与模板资产 | 中等，可从单云主机起步 | **默认推荐** |
| Next.js＋独立 Node API＋MySQL | 前后端交互灵活 | Python 解析器需保留为内容任务 | 较高，运行时和接口更多 | 有专职前后端团队时再评估 |
| WordPress＋LearnDash＋MySQL | 通用 LMS 功能完整 | 技术正文与代码工作流迁移成本高 | 插件、安全和升级维护较多 | 不作为默认路线 |
| Moodle／Open edX | 多课程、多角色和组织管理强 | 与工程证据模型不完全匹配 | 高 | 单教程路径显得过重 |
| 原静态站＋浏览器本地数据 | 无服务端学习闭环 | 复用最多 | 最低 | **不符合本次动态化要求** |

推荐 Django 是因为它能复用现有 Python 内容解析，同时提供服务端模板、认证、ORM、迁移、管理后台和表单安全，减少首版在多个运行时之间维护重复契约。前端采用 Django Templates＋原生 ES Modules 渐进增强，不为了“动态”而强制改成 SPA。

### 3.2 推荐架构：Git 内容权威源＋动态学习服务

```text
Git 提交 / 管理后台触发
  → 教程导入任务（校验 168 天、渲染白名单 HTML、计算内容哈希）
  → MySQL：ContentRelease / DayVersion / ContentChunk / Asset
  → 对象存储：源码 ZIP、公开图片、私有证据与导出文件
  → 切换 active_release，旧版本保留用于回滚和证据追溯

浏览器 ↔ Nginx / HTTPS ↔ Django（服务端模板＋/api/v1/）
                            ├── MySQL：账号、进度、复习、卡点、证据、档案
                            ├── Redis：缓存、限流、Celery 任务与短期状态
                            └── 后续独立服务：L2 验证、AI Gateway、L3 实验
```

教程正文不以数据库为第二权威源。MySQL 中的正文读模型必须记录 `content_commit/content_sha/source_path`，能够由同一 Git 提交完整重建；后台只触发导入、检查和发布，不提供另一套正文编辑器。个人学习数据则以 MySQL 为权威源，不与公开内容混放。

| 层 | P0 职责 | 后续扩展 | 明确边界 |
| --- | --- | --- | --- |
| Git 内容层 | Markdown、SVG、代码、测试、冻结输出、覆盖配置 | 题包、技能图谱、更多版本 | 不回写学习者私密数据 |
| 内容导入层 | 全量校验、版本化读模型、源码包、搜索文档 | 差异预览、分批灰度 | 全部通过才切换 active_release |
| 动态应用层 | Django 页面、认证、学习 API、管理后台 | 教师、社区、AI 接口 | 权限、CSRF、限流和审计在服务端执行 |
| 数据层 | MySQL 权威学习数据；Redis 非权威缓存 | 只读副本、独立分析库 | Redis 丢失不得造成学习记录丢失 |
| 资源层 | Nginx 静态文件、对象存储公开/私有分桶 | CDN、签名 URL、病毒扫描 | 私有证据不能放公开静态目录 |
| 执行与验证层 | 本地 `run_all.sh`；P0 不执行陌生代码 | L2 CI、独立 L3 microVM | 不在 Django 进程中运行学习者代码 |

首版可从一台云主机或同区域托管服务起步，但 Django、MySQL 和执行环境必须边界清楚。MySQL 使用 InnoDB、utf8mb4、严格模式和 UTC；迁移采用 expand→migrate→contract，禁止删库重建。生产域名使用根路径路由，不再要求 `/ai-chip-compiler-learning-plan/` Pages 子路径。

## 4. 信息架构与功能优先级

### 4.1 页面地图：围绕学习状态组织，而不是围绕文件目录组织

首页应同时回答三个问题：“这条路是否适合我”“我现在该做什么”“最终能交付什么”。首屏保留现有六阶段与 168 天价值主张，但主按钮要从固定的“开始 Day 001”升级为状态感知：未开始时显示“从环境检查开始”，学习后显示“继续 Day N”，存在卡住任务时显示“回到卡点”，完成后显示“查看项目档案”。下方依次放置本周任务、当前阶段能力、最近复习、完整路线和日课检索，避免用户每次都在 168 个卡片中寻找位置。

日课页是核心工作台，顶部固定呈现目标、预计时间、前置准备、今日产出和内容版本，正文保持现有长文、图片与代码阅读体验；侧面或顶部任务栏呈现“阅读—练习—实验—验收”的状态。每周页汇总 Day 1—5 的能力零件、Day 6 集成和 Day 7 复盘，阶段页则汇总 28 天后的综合项目。项目作品集页集中收纳 `minic` 架构、Pass、Lowering、测试、性能材料、干净环境复现和模拟讲解，避免最终成果散落在不同日课目录中([第 155 天](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-023/day-155), [第 167 天](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-024/day-167))。

### 4.2 功能分级：P0 建立动态闭环，P1 深化练习与证据，P2 独立扩展

P0 让学习者从公开首页进入 Day 001、注册或登录、取得源码、完成本地实验并把状态保存到服务端。它包括动态内容导入、全站搜索、源码下载、账号与会话、任务面板、MySQL 学习进度、导出/导入、周/阶段导航、管理后台、部署监控和基础无障碍。公开阅读和搜索不强制登录；写进度、导入备份和管理个人数据必须认证。

P1 增加结构化自测、复习、错题/卡点、`evidence.json` 上传、L2 CI 复验、项目档案，以及可选的离线编辑和冲突恢复。跨设备在线读取已经是 P0 基础能力，不再把“账号同步”后置。P2 仍分别评审教师反馈、cohort、讨论社区、AI 助教和隔离远程实验。

| 优先级 | 功能 | 验收标准 | 暂不做的事情 |
| --- | --- | --- | --- |
| P0 | 内容发布 | 指定 commit 全量导入；失败不切换版本；可回滚 | 不在后台维护第二份正文 |
| P0 | 账号与权限 | 注册/登录/退出/会话撤销；他人数据不可访问 | 公开阅读不强制登录 |

| P0 | 代码与产物 | 版本化源码包和 GitHub 深链；下载可审计 | 不自动下载大产物 |
| P0 | 服务端进度 | 刷新和换设备可恢复；冲突不静默覆盖 | 不用“已读”替代完成 |

| P2 | 社区/教师/AI/L3 | 分别通过权限、治理、隐私、安全和成本评审 | 不捆绑上线 |

### 4.3 日课页面模板：阅读流与任务流并存

建议不要大幅改动现有正文排版，而是在文章标题下增加“今日任务卡”，在右侧目录旁增加“学习状态卡”。任务卡直接复用现有四类引用块，增加环境检查、源码下载、GitHub 查看、开始练习和导入结果按钮；状态卡显示四个独立勾选及本周位置。桌面端保持双栏，移动端把状态卡折叠为底部或顶部的可展开面板，并确保代码块、SVG 缩放和弹层不会遮挡键盘焦点。

日课类型需要差异化。普通实验日强调代码、运行、观察和修改参数；Day 6 强调集成清单与对照实验；Day 7 强调回忆、错题、复盘和下周准备；文档日强调读者是否能按文档复现；面试与最终验收日强调表达、能力证据和下一步计划。Day 161—168 没有 Markdown 代码围栏并不意味着它们“缺少实践”，网站应根据日课类型展示不同验收方式，而不是机械要求每日都上传程序运行结果([第 161 天](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-024/day-161), [第 168 天](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-024/day-168))。

## 5. Markdown 内容导入与动态数据模型

### 5.1 内容版本与读模型

168 篇正文继续以 Git 为唯一权威来源。`import_tutorial` 命令从指定 commit 解析标题、目录和四类引用块，结合 `day-overrides.json` 生成日课记录、白名单 HTML、搜索 chunk 和源码包。导入先在非活动 `ContentRelease` 中完成；168 天、资源、Schema 和样例查询全部通过后，才在短事务中切换 `SiteState.active_release_id`。失败版本只保留诊断，不对用户部分可见。

```json
{
  "day_id": "day-029",
  "day": 29,
  "week": 5,
  "phase": 2,
  "type": "environment_lab",
  "title": "搭好 MLIR 工作台",
  "objective": "从 README 的今日目标解析",
  "time": {"learning_min": 25, "practice_min": 45},
  "prerequisites": "从 README 的前置准备解析",
  "deliverable": "从 README 的今日产出解析",
  "source_path": "tutorials/week-005/day-029/README.md",
  "content_commit": "53b62f1c84223bb6ca466bb8177921ccd5d8ef72",
  "content_sha": "由导入器计算",
  "run_all": true
}
```

核心内容表包括 `content_release`、`content_day`、`content_day_version`、`content_chunk` 和 `content_asset`。当前发布指针与历史版本分离；`DayProgress` 通过稳定 `day_id` 关联，并保存最后复核的 `content_sha`，所以内容更新不会清空个人历史。

### 5.2 资源发布与搜索

源码包排除 `outputs/`、构建目录、二进制和疑似密钥，保留脚本权限并做 ZIP 路径检查；产物上传到公开对象存储，数据库记录 SHA、大小、commit 和下载键。私有证据、导出文件与公开源码使用不同 bucket/prefix 和访问策略，私有下载通过授权后的短时签名 URL。

P0 搜索由服务端完成。导入器把标题、目标、技能、正文、代码路径和错误码写入 `content_chunk` 与搜索 posting；MySQL ngram 用于中文召回，规范化完整 token 表用于 `mlir-opt`、`run_all.sh`、错误码和 IR 操作。搜索 API 做字段加权、筛选、分页和稳定排序，首页不下载全文索引。默认不保存原始搜索词；确需无结果分析时使用单独、可关闭的脱敏策略。

### 5.3 学习数据：MySQL 是权威源

最小学习实体为 `LearningPlan`、`DayProgress`、`TaskProgress`，P1 再增加 `ExerciseAttempt`、`Evidence`、`ReviewItem`、`StuckItem` 和 `PortfolioItem`。`LearningPlan` 每个用户只有一条当前计划，避免多个 `planned=true`；`DayProgress` 保存版本复核、最近访问和 revision；`TaskProgress` 分别保存 reading/exercise/experiment/acceptance 状态。整体状态仍由规则派生，不重复存储。

| 实体 | 关键字段 | 约束与原因 |
| --- | --- | --- |
| `LearningPlan` | user_id、current_day_id、revision | 每用户唯一；浏览旧课不回退计划 |
| `DayProgress` | user_id、day_id、ack_content_sha、last_visited_at、needs_review、revision | `(user_id,day_id)` 唯一；乐观锁 |
| `TaskProgress` | user_id、day_id、task_id、status、updated_at | 四任务独立；服务端校验枚举 |
| `ExerciseAttempt` | user、item、item_version、answer、result、answered_at | 追加历史，不覆盖旧尝试 |
| `Evidence` | user、day、双 commit、环境、hash、声明/有效级别 | 内容不可变；有效级别由验证方决定 |
| `ReviewItem` | user、item、due_at、algorithm_version、revision | 复习不自动完成日课验收 |
| `StuckItem` | user、day、环境、最小复现、状态、revision | 默认私密，公开前再次授权 |
| `PortfolioItem` | user、slot、artifact、evidence、visibility、revision | 默认 private；链接不等于复现 |

所有表使用服务端用户 ID 作为行级边界，业务查询必须包含 owner 条件。浏览器 localStorage 只保存主题等轻量 UI 偏好，不保存完整进度。P0 不提供离线编辑；网络失败时保留表单并明确“未保存”，不得用内存状态冒充服务端成功。

## 6. 学习体验、复习与项目转化

### 6.1 每日闭环：从“读懂”转向“能回忆、能实现、能验证”

学习科学综述将练习测试和分散练习评为高效用的学习技术，但这并不意味着给每篇文章机械附五道选择题就能保证效果。对本教程而言，更有价值的检索练习是让学习者不看正文回答：“这个 Pass 为什么语义不变”“这个优化为什么可能更快”“如何用负例和性能数据验证”“这个报错属于环境、语法还是 IR 结构问题”。每日正文后保留现有必做练习和选做挑战，网站增加先答后看解析、错题重试和来源日课回跳即可([Dunlosky 等，2013](https://doi.org/10.1177/1529100612453266))。

每日流程建议为“目标确认→前置检查→主动阅读→最小实验→修改一个变量→练习与验收→记录卡点→加入复习”。其中“修改一个变量”是编译器学习的重要桥梁：学习者不仅复现作者输出，还要观察 Shape、Tile、Pass 顺序、布局或输入规模变化后的结果。网站可提供一个简短实验记录模板，要求写出假设、修改、观察与结论；对于没有代码的复盘/表达日，则改成口头复述、概念图或验收清单，避免形式统一压倒教学目标。

### 6.2 每周与阶段：把已有节奏升级为可见的能力地图

仓库的 24 个 Day 7 都是复盘或最终验收，Day 6 则多承担集成、对照实验或阶段验收。网站应将每周页设计成“前五天的零件→第六天的组合→第七天的解释与补漏”，并允许学习者在周复盘时把未解决卡点转为下周首项任务。每周完成不应只看七篇文章是否打勾，而要显示本周关键产出是否存在，例如最小 Tensor、优化 Pass 管道、融合负例、Tiling 多配置实验或完整回归报告([教程目录](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials))。

每四周形成一个阶段，六阶段最终汇成同一项目，而不是 24 个互不相干的小课程。阶段页应呈现“我能做什么”和“用什么证明”：阶段一证明 C++ 与基础 IR/Pass 能力，阶段二证明 MLIR Dialect 与图优化能力，阶段三证明布局、代价与数值语义意识，阶段四证明 Lowering/Tiling 与性能实验能力，阶段五证明端到端编译、Runtime 和回归能力，阶段六证明扩展、归因、文档与表达能力。这样，学习者看到的不是“已读 56/168”，而是逐步接近一个可展示项目。

| 阶段 | 天数 | 网站应突出的一项综合证据 | 对应项目转化 |
| --- | ---: | --- | --- |
| 一：C++ 与编译器基础 | 1—28 | 最小 Tensor、图 IR、分析/变换 Pass、PassManager | 可构建、可测试的基础工程 |
| 二：MLIR 核心能力 | 29—56 | mini Dialect、Verifier、Shape/Canonicalization/Fold、融合负例 | 自定义 IR 与优化管道 |
| 三：AI 计算图与图优化 | 57—84 | 布局、动态 Shape、Cost Model、量化与数值验证 | 图优化器与代价解释 |
| 四：Lowering、Tiling 与性能 | 85—112 | 循环生成、多配置实验、内存复用、Roofline/调优 | 正确性与性能对照实验 |
| 五：端到端与 Runtime | 113—140 | minic、JIT/AOT、Runtime、随机测试、性能回归 | 可执行、可回归的项目冻结版 |
| 六：项目收口与面试转化 | 141—168 | 扩展、性能反例、五份文档、干净复现、模拟讲解 | 可复现作品集与下一阶段计划 |

### 6.3 激励与复习：坚持可见，但不制造断签惩罚

可以记录“本周有产出的学习天数”和“当前连续周数”，比单纯每日火焰图标更适合每次 1—1.5 小时的工程学习。漏学后首页不应只显示连续记录归零，而应提供“继续当前日”“只补关键产出”“重排本周计划”三种恢复入口。Duolingo 官方也承认断签可能削弱动机，并用弹性机制缓解；本项目可以借鉴这种宽容设计，但不应照搬其积分、 hearts 或排行榜，更不应预设某个活跃提升数字会在本站重现([Duolingo 机制说明](https://blog.duolingo.com/how-duolingo-streak-builds-habit/))。

复习节奏可先用简单可解释的规则：日课完成后 1 天、7 天、28 天各出现一次回忆机会，答错或标记生疏时提前，连续答对时延后；这些间隔是产品初始参数，不是适用于所有人的科学常数，应允许学习者调整。复习卡片优先从练习、验收、卡点和性能解释生成，并链接回具体段落。周复盘页可以混合本周与前几周问题，形成轻度交错；但不要为了凑复习量把整篇正文变成几十张卡片。

### 6.4 讨论、笔记与 AI 助教：围绕证据提供支持

笔记建议支持“个人笔记”和“卡点记录”两类：前者用于概念总结，后者必须能附日课、代码 SHA、环境、最小复现和报错。两者默认以 MySQL 私密保存，仅本人可见。讨论入口可先跳转到 GitHub 的日课相关 Issue/Discussion 模板，避免首版自建评论、审核、通知和反垃圾系统。若启用公开讨论，页面要明确代码、日志和性能数据可能公开，提醒学习者移除密钥、个人路径和公司专有代码；公开作品与私密学习记录也应分开。

AI 助教适合后置为“基于当天内容的苏格拉底式提示器”：先询问学习者假设，再提示查看某段 IR、某个测试或某条命令，不直接生成完整项目答案。每个回答应引用日课标题与段落，并允许反馈错误；性能结论必须要求环境和数据，不允许把模型猜测写成实测。对于 Pass 调试，可让 AI 帮学习者整理“现象—最小复现—假设—下一步实验”，但最终验收仍由测试和学习者解释完成。无可靠引用时，AI 应明确说不知道，而不是补造编译器行为。

## 7. 编译器实验环境与三级验收

### 7.1 本地优先：先解决环境可达性，再谈在线判题

本教程的实践依赖真实 C++/MLIR/LLVM 工具链，本地或 WSL 环境应作为首版标准路径。网站需要在阶段入口提供环境预检，在日课页提供当日预检命令，在结果导入时记录工具版本。尤其要注意，README 汇总文字称 LLVM/MLIR 工具链“第 117 天起需要”，而 Day 029 的前置准备已经要求 LLVM 18 与 MLIR 工具；这说明网站不能只展示一条全局环境说明，应从逐日“前置准备”生成准确清单，并修正汇总表述，避免学习者在第 5 周才发现环境缺口([README 环境说明](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/blob/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/README.md), [Day 029 前置准备](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-005/day-029))。

建议把 Day 001、Day 029、Day 085、Day 113 和阶段六的干净复现作为关键环境里程碑。环境检查脚本应输出非敏感信息，包括操作系统、编译器/MLIR 版本、必要命令是否可用和检查结果；路径、用户名和潜在专有环境变量默认脱敏。移动端可以用于阅读、复习和查看结果，但不应暗示手机能完成完整 MLIR 实验。对没有合适机器的学习者，网站可以提前说明远程 Linux 或容器是替代方案，而不是把“在线运行”按钮作为唯一入口。

### 7.2 三级验收：自声明、CI 复验、隔离远程复验

第一级是本地自声明与脚本证据，适合 P0/P1。学习者在本地运行 `run_all.sh`，脚本除控制台输出外生成统一 `evidence.json`，网站导入后校验 Schema、日号、命令和汇总字段，并标注“本地生成，站点未复验”。这一级实施快、隐私好、成本低，但不能防止伪造，所以只能用于个人进度和非高风险自测。网站可以提供“与冻结输出比较”的辅助视图，同时提醒不同硬件与版本可能产生合法差异。

第二级是学习者自己 fork 中的 CI 复验，适合需要公开作品证据的用户。CI 在固定容器中安装指定工具链、运行选定日的测试、上传报告和 commit SHA，网站显示工作流链接与结果；这能提高可复现性，但仍要处理 fork 修改测试、Actions 权限和公开日志问题。第三级是平台控制的隔离远程复验，只有在确有教师评估或可信证书需求时才建设。它需要平台控制测试、执行环境、资源限制和结果签名，成本与安全责任显著高于前两级。

| 级别 | 结果来源 | 页面应如何表述 | 适用场景 | 主要限制 |
| --- | --- | --- | --- | --- |
| L1 自声明 | 手动勾选或填写结果 | 学习者自报完成 | 个人学习、非实验日 | 无机器证据 |
| L1+ 本地证据 | `run_all.sh` 生成 JSON | 本地生成，站点未复验 | 默认实验验收 | 可修改脚本或结果，环境差异大 |
| L2 CI 复验 | 固定工作流与容器 | 指定 commit/工作流复验 | 公开作品集、阶段项目 | 测试可见，fork 与权限需管理 |
| L3 平台复验 | 平台隔离执行与私有测试 | 平台在声明环境中复验 | 教师评估、可信证明 | 安全、成本、排队和维护复杂 |

### 7.3 性能证据：不建立脱离环境的排行榜

性能学习需要保存基线、输入规模、Shape、Tile、硬件、编译器版本、优化开关、预热、重复次数和统计口径。第 097 天已经强调“先问怎么测”，第 159 天要求性能数字有来源，第 160 天进一步验证干净环境复现，网站应把这些内容结构化为实验记录，而不是只显示一个加速比。不同机器上的 GFLOPS、内存和异步模拟结果不能直接排名，跨环境比较应默认禁用或醒目标注不可比([Day 097](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-014/day-097), [Day 160](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/tree/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tutorials/week-023/day-160))。

如果未来提供远程执行，安全底线包括无平台密钥的短时容器/微虚拟机、非特权用户、只读基础镜像、独立临时文件系统、CPU/内存/进程/磁盘/时间配额、默认无外网、输出大小限制和全面审计。不能让学习者提交的程序与平台 API、数据库或其他学习者共享执行环境，也不能把 C++ 编译器的资源消耗当作普通网页表单处理。远程执行应是独立项目并单独威胁建模；在这些条件不具备时，坚持本地＋CI 是更可靠的方案。

## 8. 技术实施路线

### 8.1 P0：动态应用与服务端学习闭环

建议工程划分为 `config/`（Django 设置）、`apps/content/`、`apps/learning/`、`apps/accounts/`、`apps/search/`、`templates/`、`static/` 和 `tests/`。现有 `tools/build.py` 不被简单删除：先抽出可复用解析函数，再由 `manage.py import_tutorial --commit <sha>` 调用；旧静态 HTML 生成逻辑在动态站验收后退出生产发布链。

P0 顺序为“基础设施与 Schema→内容导入→动态模板与账号→进度 API→服务端搜索→数据管理→部署运维”。Django 使用服务端模板输出完整公开页面，原生 ES Modules 只增强状态操作；Gunicorn 不公网直连，由 Nginx 终止 HTTPS 并转发动态路由。MySQL 和 Redis 不暴露公网。

| 改造位置 | 建议新增/调整 | 完成标志 |
| --- | --- | --- |
| 内容导入 | release、日课版本、chunk、资源、内容 SHA | 168 天全量导入；失败不切换 active_release |
| 动态页面 | Django URL/模板、首页、日课、周/阶段、设置 | 深链由应用处理；无 Pages 子路径依赖 |
| 账号与权限 | Django Auth、HttpOnly 会话、CSRF、后台角色 | 公开可读，私有记录按 user 隔离 |
| 学习 API | progress/plan/export/import、revision＋If-Match | 换设备恢复；412 返回当前服务端版本 |
| 搜索 | MySQL ngram＋技术 token posting、筛选与分页 | 中文、命令、错误码和锚点测试通过 |
| 数据与资源 | MySQL、Redis、公开/私有对象存储 | Redis 清空不丢数据，私有文件不可直链 |
| 部署 | Nginx、Gunicorn、Celery、迁移、备份、监控 | 失败不发布；兼容回滚和恢复演练通过 |

### 8.2 P1/P2：共享主应用边界，独立高风险服务

P1 的自测、复习、证据和项目档案可在同一 Django 模块化 monolith 中实现，继续使用 MySQL；GitHub 元数据核验、artifact 下载和签名可拆成独立 Verification Worker。数据库升级采用 expand→migrate→contract，先加兼容字段和表，再回填，最后在旧代码全部退出后删除旧结构。

原“可选账号同步”不再成立：P0 已有账号与在线跨设备能力。WP-13 改为可选离线编辑与冲突恢复，仅在确有离线需求时增加 IndexedDB outbox；它不是在线模式的第二权威源。未开启离线功能时，网络失败只保留未提交表单，不写入本地业务副本。

P2 的社区、教师反馈和 cohort 可复用主站身份，但必须按公开、私密和字段级共享分别授权。AI Gateway 与 L3 Lab 独立部署，不能使用 Django Web 进程或主数据库超级权限执行学习者代码。

### 8.3 测试、发布与回滚

测试分内容导入、ORM/服务、API 权限与并发、浏览器 E2E、无障碍和部署六层。CI 启动真实 MySQL/Redis 测试服务，覆盖事务回滚、行级越权、CSRF、revision 冲突、损坏导入、迁移和备份恢复。E2E 通过 Nginx 入口验证动态深链、刷新、Cookie、搜索、下载和 API 失败提示，不再执行 Pages 双 base path 测试。

发布单元是“应用镜像＋迁移版本＋内容 active_release＋静态资源 manifest”。先部署兼容迁移，再滚动更新应用，最后切换内容版本；应用回滚不得依赖删除新表。数据库备份覆盖每日全量与 binlog/时间点恢复能力（由实际托管或自建方案实现），恢复演练必须验证用户进度和内容关联。构建、测试、迁移预检或冒烟失败均不得切换生产流量。

## 9. 隐私、安全、无障碍与公开内容质量

### 9.1 隐私与安全：服务端数据需要完整生命周期

动态站从首版开始处理账号和学习记录，隐私说明必须明确数据保存在运营方服务器、处理目的、保留期限、导出/更正/删除路径以及第三方服务商。只收集账号、会话和学习闭环所需字段，不采集真实姓名、身份证、生日等无关信息；卡点、环境、证据和项目档案默认私密，公开分享逐字段确认。个人信息保护相关规则强调明确目的、最小范围、公开透明以及撤回、更正和删除等权利，网站应把这些要求转成实际按钮和数据生命周期([国家网信办权威解读](https://www.cac.gov.cn/2021-08/21/c_1631141677655320.htm))。

Django 会话 Cookie 设置 HttpOnly、Secure、SameSite=Lax，写操作校验 CSRF 和 Origin；密码使用框架认可的哈希，登录、导入和搜索接口限流。Markdown HTML 使用白名单 sanitizer，ORM 查询不拼接 SQL，所有导入 JSON、笔记、证据、日志和附件仍按不可信输入处理：不执行命令、不自动打开链接、不注入 HTML。私钥、数据库口令、对象存储密钥和 OAuth secret 只存在服务端密钥管理，不进入 Git、镜像或浏览器。

若使用中国境内服务器或 CDN，上线前应通过实际接入服务商与工信部备案系统确认 ICP 等适用手续([工信部备案系统](https://beian.miit.gov.cn/))。生产环境启用 TLS、最小安全响应头、审计日志脱敏和备份加密；日志不记录 Cookie、令牌、完整笔记或原始证据。

### 9.2 无障碍与移动端：把标准变成日课验收用例

WCAG 2.2 可作为验收基线，重点覆盖键盘操作、焦点不被遮挡、文本/非文本对比度、目标尺寸和可访问认证。现有图片缩放、日课胶囊导航、代码复制、深色/浅色切换和返回顶部都要用键盘走查；完成状态不能只用绿/灰颜色区分，SVG 的信息不能只剩图片 alt 一句“架构图”。代码块横向滚动、长公式、目录锚点和固定头部在窄屏上也要测试，确保不会遮住当前焦点或正文([W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/), [焦点外观说明](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html))。

仓库 168 篇日课的 Markdown 图片引用均有非空 alt，这是良好基础，但仍需人工判断 alt 是否等价表达技术图含义，并为复杂图提供正文解释。移动端的首要任务是阅读、复习、查看代码和卡点，不必强行把完整终端工作流塞进手机。建议将主要触控目标做成舒适尺寸，同时至少满足 WCAG 的最低目标尺寸要求；图片缩放必须同时提供按钮与键盘方式，不能把双指或拖拽作为唯一操作。

### 9.3 搜索、SEO 与性能：让旧教程也能被重新发现

动态应用继续生成站点地图、canonical、Open Graph、面包屑和由今日目标生成的描述；公开页面由服务端输出完整 HTML，不要求搜索引擎执行 JavaScript。搜索除了标题和正文，还应索引 `mlir-opt`、错误码、命令、文件名和技能标签，并支持按阶段、周、日课类型筛选。搜索结果要显示命中上下文和来源日课，避免只返回 168 个相似标题；无结果反馈可以直接形成内容维护任务([现有构建器](https://github.com/hzchenxiaobin/ai-chip-compiler-learning-plan/blob/53b62f1c84223bb6ca466bb8177921ccd5d8ef72/tools/build.py))。

性能策略应围绕长文、动态查询与大量 SVG：公开页面使用 Redis/HTTP 缓存，图片 lazy-load，搜索在服务端分页，源码包不随页面自动下载，静态资源使用内容哈希缓存，KaTeX 等第三方依赖尽量自托管或具备失败降级。首页不要一次渲染全部 168 个长卡片和完整正文索引，阶段折叠时也应避免重复生成大量隐藏 DOM。性能验收同时看慢速移动网络、低端设备与长日课交互，而不只测首页首次加载。

## 10. 学习指标与持续运营

### 10.1 指标体系：优先衡量关键产出，不迷信停留时长

建议把漏斗定义为“访问路线→开始 Day 001→Day 001 构建测试完成→第 1 周复盘→Day 029 MLIR 环境通过→阶段三集成→Day 139 项目冻结→Day 160 干净复现→最终项目档案”。这些节点对应真实能力与项目进展，比“页面浏览量”“累计阅读字数”更能说明学习是否推进。动态站可以使用服务端聚合数据分析有效开始与关键产出，但只处理明确需要的事件，默认不记录原始搜索词、完整日志或精细设备指纹；公开阅读仍不强迫注册。

内容运营还要看搜索无结果率、源码下载后实验完成率、证据导入失败率、各日卡点数量、环境预检失败类型和复习回忆结果。指标需要按内容版本观察：某次教程修订后 Day 029 的环境失败下降，比笼统的月活增长更能证明维护价值。不要把不同硬件的性能数字汇总成学习者排名，也不要把“学习时长”当作掌握程度的替代变量。

| 指标 | 建议定义 | 用来回答的问题 | 反误读约束 |
| --- | --- | --- | --- |
| 首次有效开始 | 完成 Day 001 前置检查并开始实践 | 新用户是否真正进入学习 | 不等于打开 Day 001 |
| 第 1 周闭环率 | 完成本周关键产出与复盘的学习者/有效开始者 | 首周设计是否可执行 | 不以七篇已读替代 |
| Day 029 环境通过率 | 通过 MLIR 预检人数/运行预检人数 | MLIR 环境与文档是否清楚 | 分 OS、工具版本观察 |
| 阶段证据完成率 | 指定综合证据达到 L1+/L2 的比例 | 项目是否持续推进 | 明示证据级别 |
| 卡点解决率 | 已解决卡点/已记录卡点 | 排错支持是否有效 | 结合解决时间与复发情况 |
| 搜索无结果率 | 无结果查询/有效查询 | 内容检索与术语覆盖是否不足 | 排除空查询与明显垃圾输入 |
| 干净复现成功率 | Day 160 验收通过数/尝试数 | 项目材料能否被他人使用 | 必须记录环境和 commit |
| 复习回忆结果 | 按题目与技能统计尝试和正确性 | 哪些概念需要补救 | 不把刷题次数当掌握 |

### 10.2 迭代方法：小样本走查优先于堆功能

每轮改版选择少量代表性路径做走查：新手 Day 001、首次接触 MLIR 的 Day 029、性能实验 Day 097、阶段冻结 Day 139、项目复现 Day 160。观察学习者在哪里找代码、如何理解前置、怎样判断完成、失败后去哪求助，再决定是改文案、改导航还是改工具。对搜索、任务面板和证据导入这类基础功能，直接修复明显可用性问题通常比过早做复杂 A/B 测试更有效。

激励、复习间隔和 AI 提示可以在样本足够后做实验，但要同时观察学习质量与退出行为。比如连续学习提醒若提高回访却增加草率打勾，就不是成功；复习卡若增加次数却只让学习者记住答案，也需要改题。运营节奏建议保持“内容纠错随时发布、学习功能小步发布、阶段节点集中复盘”，让网站演进与教程本身的 Git 工作流一致。

## 11. 30/60/90 天实施路线与最终清单

### 11.1 建议里程碑

前 30 天建立动态 P0：基础设施、MySQL Schema、内容导入、账号、动态模板、源码包和服务端进度。第 31—60 天完成搜索、数据管理、备份恢复、代表日课走查与生产上线，再启动自测、复习、卡点和证据。第 61—90 天进行 L2 CI、项目档案和可选离线编辑试点。远程实验、AI 助教和原生 App 不进入默认 90 天承诺。

| 时间 | 目标 | 主要交付 | 退出条件 |
| --- | --- | --- | --- |
| 0—30 天 | 动态应用骨架可用 | Django/MySQL/Redis、内容版本、账号、动态日课、进度 API | 注册后可完成 Day 001；换设备可恢复 |
| 31—60 天 | 核心学习与发布闭环 | 搜索、源码包、导入导出、管理后台、监控备份 | 代表搜索通过；失败不发布；恢复演练成功 |
| 61—90 天 | 练习与证据深化 | 自测复习、卡点、L1/L1+、L2 试点、项目档案 | 证据边界清晰；迁移与权限测试通过 |
| 独立后续项目 | 按需扩展 | 离线编辑、社区、教师、AI、L3 | 分别通过冲突、治理、隐私、安全与成本评审 |

### 11.2 首版 Definition of Done

至少由一名未参与开发的人完成注册、Day 001、退出换设备登录、恢复进度和导出；具备 MLIR 环境的人抽查 Day 029。测试者需要在不看仓库目录说明的情况下找到源码、理解前置、运行实验并记录完成。还要覆盖移动端、键盘、恶意导入、数据库不可用、并发修改、发布失败和备份恢复。

### 11.3 最终建议

动态化后的首版可以概括为：**保留 Git 内容工作流，用 Django 和 MySQL 建立真正可持续扩展的学习系统；公开阅读保持低门槛，个人进度从首版起由服务端可靠保存。**不搬入重型 LMS，不维护双份正文，也不为了“动态”引入不必要的 SPA 和微服务。

第一批任务建议依次为“MySQL 与 Django 基础设施”“内容版本导入器”“动态日课与周/阶段模板”“账号与会话”“服务端进度 API”“对象存储源码包”“MySQL 技术搜索”“导出导入与账号删除”“CI 部署备份监控”“五条代表路径试走”。完成后，网站才从教程发布器升级为可运营、可追踪、可扩展的动态学习工作台。
