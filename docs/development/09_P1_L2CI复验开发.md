# 09：P1 L2 CI 复验与证明开发

> 工作包：WP-11（L2 CI 试点）  
> 对应需求：支撑 FR-011，服务公开项目证据  
> 前置：WP-10 证据哈希、声明/有效级别分离  
> 原则：L2 是“指定 commit、受信工作流与公开测试的复验”，不是防作弊考试或平台证书。

## 1. 可信边界与部署形态

L2 由学习者仓库准确 commit、固定维护的 caller/reusable workflow/公开测试，以及独立验证方读取 GitHub 元数据和 artifact 后签发的 attestation 共同成立。CI 链接、绿色徽章或导入 `level:L2` 都不够。

```text
学习者公开仓库/准确 commit
  → 固定 caller 模板调用固定 SHA 的 reusable workflow
  → GitHub-hosted runner 执行公开测试
  → 上传 evidence.json + run metadata（无秘密）
  → Verification API 独立读取 repo/run/jobs/workflow/artifact
  → 校验后由独立 signer 签发 Ed25519 attestation
  → 主站服务端按 evidence_hash 关联并提升 effective_level
```

动态主站只保存验证方公钥、验证记录和服务地址。签名私钥、GitHub App 私钥、artifact 下载凭证和限流管理密钥只存在 Verification/密钥系统，绝不进入浏览器 JS、Django 模板或公开仓库。

主站与 Verification 通过受控服务端 API 交互，采用短期 OIDC/mTLS 等一种明确服务身份和最小 scope。Verification 不获得 MySQL 超级权限，主站 Web 进程不代替它签发证明。

## 2. 试点范围与验证清单

首批只选 Day 029、Day 097、Day 160，覆盖 MLIR 环境、性能实验和干净复现：

```text
verification/
├── manifests/day-029.json
├── manifests/day-097.json
├── manifests/day-160.json
├── .github/workflows/learning-verify.yml
├── runner/                  # 固定测试驱动，不采用学习者可改的证据生成器
└── verifier-version.json
```

```json
{
  "manifest_version": 1,
  "day_id": "day-029",
  "tutorial_commit": "允许的教程提交或明确兼容列表",
  "test_suite": "public-mlir-smoke",
  "test_suite_sha": "测试套件内容哈希",
  "caller_template_sha": "受信caller工作流模板规范化后的SHA-256",
  "image": "ghcr.io/example/learning-verify@sha256:固定摘要",
  "timeout_seconds": 300,
  "artifact_retention_days": 30
}
```

镜像、测试、工作流和 manifest 有版本。允许教程 commit 列表必须显式维护，不用“最新 main”代替。

## 3. 受信 caller 与 reusable workflow

学习者 caller 必须匹配规范化模板，首批只支持 `workflow_dispatch`：

```yaml
name: Learning verification
on:
  workflow_dispatch:
    inputs:
      day_id:
        required: true
        type: string
      expected_head_sha:
        required: true
        type: string
permissions:
  contents: read
jobs:
  verify:
    uses: <trusted-org>/<trusted-repo>/.github/workflows/learning-verify.yml@<full-commit-sha>
    with:
      day_id: ${{ inputs.day_id }}
      expected_head_sha: ${{ inputs.expected_head_sha }}
```

不允许调用者增加 checkout 后改写源码、上传自定义 artifact 或注入秘密的步骤。Reusable workflow 负责准确 head SHA 检查、固定测试、报告生成和 artifact 上传。caller 中 `uses` 必须为完整 40 位 commit，不接受 tag/branch。

若 GitHub 实际事件元数据与模板约束不一致，验证失败而不是猜测兼容。公开测试本身不构成防作弊保证。

## 4. Artifact 契约

artifact 包含：

```text
evidence.json
run-context.json     # repo、run_id、run_attempt、head_sha、workflow、manifest 版本
manifest.json
public-test-report.json
```

验证方必须从 GitHub 指定 run/attempt 下载 artifact，不信任用户上传的同名 ZIP。检查 ZIP 路径、大小、条目、重复名和 SHA；artifact digest 与数据库绑定。artifact 过期则只能重新复验，不从学习者提供的备用链接补信。

run-context 只含公开元数据，不包含 token。日志可有大小上限和脱敏，但 L2 的核心是机器报告与来源链。

## 5. Verification API 状态机

状态：`submitted→fetching_metadata→fetching_artifact→verifying→signing→verified`，或 `failed/expired/revoked`。同一 `(repo,run_id,run_attempt,evidence_hash)` 幂等。

验证步骤：

1. 用户通过主站选择本人 EvidenceRecord 并提交公开 repo/run。
2. Verification 独立读取 run，确认结论、head SHA、事件、仓库和 attempt。
3. 读取 job 图，确认 caller 模板哈希、reusable workflow 完整 SHA 和允许步骤。
4. 对照 manifest 校验 day、教程 commit、测试 suite、镜像和超时。
5. 下载官方 artifact，验证来源、摘要和 evidence_hash。
6. 重算公开测试汇总与结果，检查无失败被改写。
7. 写入 VerificationRun，生成结构化待签 payload。
8. Signer 验明请求来自授权 verifier，再签发 attestation。
9. 主站内部接口验签、匹配 evidence_hash/commit/manifest 后更新 effective_level。

所有步骤可重试且幂等，任何一步失败不提升级别。重试使用同一 VerificationRun 或明确 attempt 历史，不能生成多个相互矛盾的有效证明。

## 6. Attestation 与密钥

```json
{
  "schema_version": 1,
  "level": "L2",
  "evidence_hash": "64位小写SHA-256",
  "day_id": "day-029",
  "learner_repository": "owner/repo",
  "learner_commit": "40位headSHA",
  "verification_run_id": "服务端随机ID",
  "manifest_sha": "64位SHA-256",
  "issuer": "verification.example",
  "kid": "2026-l2-key-01",
  "issued_at": "2026-11-25T00:00:00Z",
  "expires_at": "2027-11-25T00:00:00Z"
}
```

对 JCS(payload) 做 Ed25519 签名。主站使用 kid 定位受信公钥，校验 issuer、受众、有效期、撤销和全部绑定字段。kid 轮换不能使旧证明立即失效；撤销列表/在线状态需有缓存时限与 fail-closed 策略。

签名私钥只在 signer；GitHub App 私钥与签名私钥分离。普通管理员不能通过后台伪造 attestation。

## 7. 错误码与展示

| 错误码 | 含义 |
|---|---|
| `CALLER_TEMPLATE_MISMATCH` | caller 与受信模板不一致 |
| `REUSABLE_WORKFLOW_UNPINNED` | 未使用完整受信 SHA |
| `HEAD_SHA_MISMATCH` | run head 与用户声明不一致 |
| `RUN_ATTEMPT_INVALID` | attempt 不匹配或非指定重试 |
| `ARTIFACT_SOURCE_INVALID` | artifact 不是指定 run/attempt 的官方产物 |
| `EVIDENCE_HASH_MISMATCH` | 证据与证明摘要不匹配 |
| `PUBLIC_TEST_FAILED` | 公开测试未通过 |
| `ATTESTATION_INVALID` | 签名、有效期或绑定字段无效 |

前端显示可行动说明和公开验证范围，不暴露内部响应、token 或私有配置。失败保持 L1/L1+，成功明确“指定 commit＋受信工作流＋公开测试”。

## 8. 灰度、降级和验收

Day 029/097/160 分别设置 flag。GitHub API 限流时排队并显示等待，不降低校验。Verification 停止时，主站教程、学习进度和已有证据仍可访问；新 L2 签发暂停。

- `P1-TC-CI-01`：合法 run→artifact→attestation 全链路。
- `P1-TC-CI-02`：caller 模板、额外步骤和权限污染拒绝。
- `P1-TC-CI-03`：准确 head SHA 与 workflow 完整 SHA 校验。
- `P1-TC-CI-04`：run_attempt、artifact 来源、重放和幂等。
- `P1-TC-CI-05`：JCS/Ed25519、kid 轮换、过期与撤销。
- `P1-TC-CI-06`：无秘密 workflow，日志和 artifact 秘密扫描。
- `P1-TC-CI-07`：限流、独立回滚和主站降级。
- 导入→复验→刷新 E2E 通过，失败不提升有效级别。
