# 04：MySQL 数据、证据与后续迭代

> 范围：P0 数据底座、P1 扩展、P2 权限边界  
> 原则：MySQL 保存权威业务数据；内容读模型可重建；导出 Schema、数据库 migration 和证据 Schema 是三种不同版本。

## 1. 数据分层

| 层 | 权威源 | 保存内容 | 删除/重建规则 |
|---|---|---|---|
| 教程源 | Git 指定 commit | Markdown、图片、代码、outputs、题包源 | 按仓库生命周期 |
| 内容读模型 | 可由 Git 重建 | release、日版本、HTML、chunk、token | 未激活且不再需回滚时可清理 |
| 业务数据 | MySQL | 账号、计划、任务、复习、卡点、证据元数据、项目 | 按用户请求与保留策略 |
| 私有对象 | 私有 bucket＋MySQL 元数据 | 导入快照、导出、证据、附件 | 到期或删除任务清除 |
| 临时数据 | Redis | 缓存、限流、Celery 状态、短期锁 | 可随时失效，不是唯一记录 |
| 浏览器 | 仅 UI 偏好 | 主题、侧栏、非敏感临时视图 | 退出清空私有内存 |

## 2. P0 MySQL 模型

### 2.1 账号与内容

使用 Django User/自定义 User（首次迁移前确定，不在已有用户后轻易替换 `AUTH_USER_MODEL`）。保留 Django session、password reset 和权限框架，业务表以 user 外键关联。

内容表以 `01_构建与内容契约.md` 为准：`content_release`、`content_day`、`content_day_version`、`content_chunk`、`content_asset`、`site_state`、`search_token`、`search_posting`。学习表只引用稳定 `day_id` 或 ContentDay，不直接外键到可能替换的 DayVersion。

### 2.2 学习记录

```text
LearningPlan
  id, user_id UNIQUE, current_day_id NULL,
  revision, created_at, updated_at

DayProgress
  id, user_id, day_id, ack_content_sha NULL,
  last_visited_at NULL, needs_review,
  revision, created_at, updated_at
  UNIQUE(user_id, day_id)

TaskProgress
  id, progress_id, user_id, day_id, task_id, status, updated_at
  UNIQUE(user_id, day_id, task_id)
  progress_id 必须属于同一 user_id/day_id

LearningDataJob
  id, user_id, kind, status, schema_version,
  input_object_key NULL, output_object_key NULL,
  checksum, idempotency_key, error_code, error_detail_json,
  created_at, started_at, finished_at, expires_at

ImportConflict
  id, job_id, day_id, incoming_json, current_json,
  resolution NULL, UNIQUE(job_id, day_id)

AuditEvent
  id, actor_user_id NULL, event_type, target_type,
  target_id, request_id, safe_metadata_json, created_at
```

业务 task_id 只含 `reading/exercise/experiment/acceptance`。DayProgress revision 是整记录版本，TaskProgress 不各自做冲突版本。planned 只在 LearningPlan 中维护；API 可以映射到当前日记录。

`ack_content_sha` 可为空；浏览事件不改变它。激活新 release 时，对 `ack_content_sha` 与新版本不同的已有记录标记 needs_review，不清空任务。

### 2.3 数据任务

导出、导入、替换前快照、删除学习数据和账号清理都使用 LearningDataJob 或明确子表。状态：`queued/running/needs_confirmation/applying/succeeded/failed/expired/cancelled`。

- 预检文件存私有 bucket，设短期 TTL。
- apply 必须校验用户、预检 checksum、当前 revision 集合和 resolution。
- 合并与替换在可界定事务中执行；大型导入可分块，但激活使用 staging＋事务切换，不能暴露半批。
- 替换先完成私有快照并验证 SHA/可读取，再删除目标范围。
- 审计只记数量、范围、哈希和结果，不记正文、密码、token 或原始 IP。

## 3. P1 数据扩展

### 3.1 自测、复习和卡点

```text
QuestionSet / QuestionVersion
ExerciseAttempt(id,user_id,question_version_id,answers_json,score,passed,created_at)
ReviewItem(id,user_id,day_id,due_at,state,last_result,revision,...)
StuckItem(id,user_id,day_id,title,description,state,revision,...)
StuckEvent(id,stuck_id,event_type,safe_metadata_json,created_at)
```

题包 QuestionVersion 属于内容 release 或有独立兼容版本；作答和复习属于用户数据。再次答错只更新复习，不自动把已经完成的日验收撤销。软删 StuckItem 需要 tombstone，仅在启用离线 outbox 时参与离线冲突。

### 3.2 证据

```text
EvidenceRecord
  id,user_id,day_id,attempt_id,commit_sha,
  environment_json,summary_json,tests_json,
  evidence_hash,declared_level,effective_level,
  verification_run_id NULL,created_at,schema_version

VerificationRun
  id,learner_repo,commit_sha,caller_template_sha,
  reusable_workflow_sha,github_run_id,run_attempt,
  conclusion,started_at,completed_at,artifact_digest,
  identity_json,raw_log_object_key NULL

Attestation
  id,evidence_id,level,issuer,subject_digest,
  payload_json,signature,verified_at,valid_from,valid_to NULL,
  revoked_at NULL,verification_run_id NULL
```

EvidenceRecord 内容哈希后核心字段不可原地修改；修正创建新 attempt。公开 API 不返回私有日志、完整身份或签名校验秘密。Attestation 只能由 Verification/Lab 的内部接口创建，用户导入、项目同步和普通管理员表单均不能修改。

### 3.3 项目档案

```text
Project(id,user_id,slug,title,visibility,summary,current_revision,created_at,updated_at)
ProjectVersion(id,project_id,version,artifact_manifest_json,metrics_json,...)
ProjectSlot(id,project_version_id,slot_key,kind,value_json,evidence_id NULL)
ProjectRelease(id,project_id,version_id,visibility,published_at)
```

Project 默认 private；公开必须创建明确 ProjectRelease。私密笔记不进入公开版本。有效复现等级由匹配 commit、环境和证据决定，“每个 slot 有 URL”不构成已复现。

## 4. 数据库迁移

### 4.1 版本分工

- Django migration：真实 MySQL 表、索引、字段和数据迁移，编号连续并纳入代码评审。
- 导出 Schema：用户可下载数据的长期兼容契约，独立于表名和 migration 编号。
- Evidence/Question Schema：文件格式版本，不随 ORM 改表自动加一。

### 4.2 expand → migrate → contract

1. Expand：增加可空字段、新表、新索引；旧应用仍可运行。
2. 双写/回填：必要时分批回填，记录批次、行数和校验，不锁全表。
3. 切换读取：新应用读新结构，保留旧结构回退路径。
4. 全量比对：数量、抽样、哈希和外键完整性。
5. Contract：只有旧版本不再需回滚时才删除旧字段/表。

MySQL DDL 可能隐式提交，不能把“Django atomic migration”当作所有 DDL 都可事务回滚。大表加索引/改列先在与生产同版本、相当数据量的环境演练，必要时使用经过评审的在线 DDL 工具。

学习数据不做向下破坏性回滚。应用回滚优先选择兼容当前 Schema 的旧镜像；必须 contract 时先备份并出具专门恢复方案。

## 5. 证据可信边界

L1 为学习者自报；L1+ 为本地脚本生成但本站未复验；L2 需要受信 caller/reusable workflow、公开测试、准确 run_attempt/artifact 和独立 Ed25519 attestation；L3 需要平台强隔离、私有测试、独立验证域和独立签名。

EvidenceRecord 的 `declared_level` 与 `effective_level` 分开。用户导入可以声明本地证据，但不能产生 L2/L3。教师评论、AI 输出和附件链接都不能提升有效等级。

本地脚本只能读取选定项目文件、通过 `subprocess.run(argv, shell=False)` 执行用户明确选择的工具，不自动执行导入 JSON 中的命令。详细哈希、Schema 和验证链见 WP-10/WP-11/WP-16 文档。

## 6. WP-13 可选离线边界

主站已有账号和在线跨设备，不再开发独立“可选账号同步服务”。确有离线需求时，WP-13 才引入 IndexedDB outbox：

```text
outbox: operation_id, user_id, entity_type, entity_id,
        base_revision, full_record, created_at, state
tombstone: user_id, entity_type, entity_id, base_revision
cursor: user_id, stream, server_cursor
```

- 在线模式直接写服务端，不先写 outbox。
- 离线记录是待提交草稿，不是第二权威源。
- 重连按完整记录＋base_revision 提交；412 保留本机与服务端双方，由用户选择。
- operation_id 支持幂等；tombstone 防止已删除实体被旧草稿复活。
- 下行使用服务端游标；不在浏览器永久复制全部证据、私有日志或账号信息。
- 退出、切换账号或远程撤销后清空该用户 outbox。
- Attestation 和有效证据级别永不走 outbox 修改。

## 7. P2 服务边界

Community API 可模块化在主应用内起步，但公开 Thread、私密 Feedback 和 cohort ShareGrant 使用不同表、权限与序列化器。AI Gateway 独立保存模型密钥，只获取经过授权的内容 chunk 和最小用户上下文。Lab Controller、Executor、Signer 分权，Django/Gunicorn 不执行学习者代码。

外部服务通过短期服务身份、最小 scope、审计和撤销接入。主站数据库账号不授予 AI/Lab 全库权限；跨服务优先使用受控 API，而不是共享 MySQL root 或直接写对方表。

## 8. 备份、保留与删除

MySQL 采用定期全量＋binlog/PITR（由部署环境支持）；私有对象启用版本或受控保留。备份加密、独立访问权限并定期恢复演练。

用户删除学习数据不删除公开教程。账号删除处理用户表、学习数据、项目、复习、卡点、私有对象和会话；财务/法律必要记录如未来出现需单独说明。备份中的到期清除按隐私政策执行，不承诺无法实现的即时物理抹除。

内容读模型可从 Git 重建，但为了回滚和证据追溯保留合理历史。旧 release 清理前必须确认无 active 引用、无证据追溯需求且对象资源可重建。
